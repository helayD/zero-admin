# 编码标准与验证参考

本文件定义 issue-start Step 6/7 的编码标准、工作流和验证清单。

---

## 实现原则

1. **扩展优先于创建** — 优先修改现有文件而非新建
2. **先读后写** — 理解上下文再动手
3. **积极复用** — 利用现有工具函数和模式
4. **保持内聚** — 每个文件/函数职责单一
5. **遵循架构** — 符合项目已有的分层模式
6. **测试驱动** — 先写测试用例再实现
7. **持续更新进度** — 每次重要变更后记录

---

## 编码标准（强制）

- 所有代码必须通过 linter，零警告/错误
- 新文件必须有头部注释：`/** 文件用途简述 */`
- 移除冗余代码
- 格式化符合项目配置（Prettier/ESLint/Checkstyle 等）
- 无 TODO/FIXME 遗留（或有明确的 Issue 跟踪）

---

## 编码工作流

```
0. 文件定位
   ↓
1. Domain 层（业务逻辑、模型）
   ↓
2. Data 层（数据库、API 调用）
   ↓
3. Presentation 层（UI、Controller）
   ↓
4. 测试（MANDATORY，≥90% 覆盖率）
   ↓
5. 文档
```

---

## 业务验证（每层实现后）

- 验证业务逻辑正确性
- 测试业务规则和约束
- 验证数据校验和错误处理
- 检查用户工作流完整性
- 对照验收标准验证

---

## Step 7 验证清单

### 运行测试
Unit → Integration → E2E → Coverage report（≥90%）

### 检查 linter
零错误/警告

### 验证功能
手动测试，验收标准满足，无回归

### 业务逻辑验证
- 所有业务规则正确执行
- 数据验证正常
- 错误消息清晰友好
- 边界情况已处理
- 用户工作流端到端可用

### 性能与可扩展性验证
- API 响应时间（用户端 <2s，关键路径 <500ms）
- 数据库查询优化（无 N+1 查询）
- 内存使用可接受
- 缓存策略（如适用）
- 限流（如 API 端点）

### 编码标准验证
- 格式化、linter 零错误、新文件头部注释
- 无冗余代码、代码复用确认、函数内聚
