# Story 8.6: 多渠道与第三方集成模板

Status: ready-for-dev

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a 平台管理员,
I want 为 H5、小程序以及物流轨迹、短信或站内消息等首批集成定义统一配置模板,
so that 新渠道和新集成可以复用现有核心业务语义快速落地。

## Acceptance Criteria

1. **Given** 平台准备接入新消费渠道或第三方能力 **When** 管理员创建渠道或集成模板 **Then** 系统保存租户 / 商户映射、权限作用域和必要配置字段 **And** 不要求重写订单、商品、会员和营销的核心业务定义。

2. **Given** 某个渠道或集成模板被停用、变更或迁移 **When** 管理员查看配置 **Then** 系统展示当前生效状态和影响范围 **And** 后续接入团队可以基于模板而不是散落逻辑继续扩展。

## AC 覆盖矩阵

- **AC1（模板建模 + 作用域映射 + 核心语义复用）**：Task 1-4、5.1-5.3
- **AC2（生效状态 + 影响范围 + 后续可扩展性）**：Task 1.5、2.3-2.5、3.1-3.5、4.2-4.5、5.1-5.4

## 背景与关键风险（必须优先阅读）

> **⚠️ CRITICAL - 当前仓库的渠道枚举已经出现别名分叉：** `pkg/operatefunnel/funnel.go` 使用 `mini_program`，而 `web-admin/src/pages/system/tenant/index.tsx` 与 `web-admin/src/pages/system/merchant/index.tsx` 仍在使用 `mini-program`。8.6 必须先建立统一 canonical code 和向后兼容的 alias 归一化，否则后续筛选、模板绑定、统计和可用渠道校验会持续错位。
>
> **⚠️ CRITICAL - 模板不是第二套业务模型：** FR59 要求的是“复用现有核心业务语义”，不是为 H5 / 小程序 / 物流 / 短信 / 站内消息各造一套独立订单、商品、会员或营销定义。模板只能承载接入元数据、映射关系和配置约束，核心交易、目录、会员、营销语义仍然归属于 `oms/pms/ums/sms/cms`。
>
> **⚠️ CRITICAL - 秘钥不允许明文落库或出现在页面回显中：** 架构文档已经明确第三方支付密钥、短信等凭据只能放在配置中心 / 环境配置。8.6 中的模板必须保存 `credentialRef`、配置项标识或脱敏摘要，不能直接保存 `appSecret`、`accessKeySecret`、私钥明文或完整回调签名密钥。
>
> **⚠️ CRITICAL - 渠道入口必须遵守统一意图契约：** H5、小程序、站内消息和后续活动唤回相关模板，只能描述语义化目标，如 `intentType / targetType / targetId / fallbackType / requiresAuth / minAppVersion`。不允许把“裸 URL + 页面局部 query 参数”直接当作平台级模板真相源。
>
> **⚠️ CRITICAL - 站内消息必须复用既有消息底座：** 当前仓库已经存在 `rpc/ums/ums.proto` 中的 `MemberMessageService` 和 `rpc/ums/internal/logic/membermessageservice/`。8.6 不能再造一张平行“通知模板结果表”绕开既有会员消息链路。
>
> **⚠️ CRITICAL - 影响范围必须可计算而不是手填备注：** AC2 要求模板停用、变更或迁移后能展示当前生效状态和影响范围，因此模板和主体绑定必须有可查询真相源，不能只靠 `remark`、`status_reason` 或自由文本描述。
>
> **⚠️ CRITICAL - 模板状态变更不能静默改写主体配置：** 若模板与 `sys_tenant.available_channels`、`sys_merchant.available_channels` 存在联动，必须通过显式的绑定 / 发布动作和审计记录完成，不能让“编辑模板”默默改掉现网租户 / 商户可用渠道。
>
> **⚠️ CRITICAL - 物流轨迹 / 短信提供方在本 Story 里只落模板，不直连供应商：** 6.3 物流轨迹、8.1 消息提醒等能力仍有各自业务 story。8.6 只提供可复用的接入模板和治理元数据，不在本 Story 中顺手写第三方 SDK 调用或异步回调编排。

## 明确非目标（本 Story 不做）

- 不直接接入真实短信、物流轨迹、推送或小程序 SDK，也不在本 Story 中完成供应商联调。
- 不建设新的配置中心、密钥托管平台或统一密钥轮换系统；本 Story 只保存 `credentialRef` / 配置引用。
- 不重写 App / H5 / 小程序的页面路由体系；这里只定义统一模板和语义化入口契约。
- 不重构 `oms/pms/ums/sms/cms` 的核心业务模型，不把模板能力下沉成新的跨域数据库直连。
- 不顺手升级 `go-zero`、`goctl`、Flutter 路由栈、Ant Design Pro 或 Umi。

## 实施顺序（必须按序推进）

1. 先统一渠道 canonical code、模板领域模型、秘钥存储策略和绑定关系，再开始 API / RPC。
2. 再补 `sys` 域 migration、proto、Admin API 和服务端校验，保证模板真相源与审计链完整。
3. 再建设 Web Admin 模板治理页与影响范围预览，避免前后端对模板字段理解不一致。
4. 最后把租户 / 商户“可用渠道”选项改为复用统一模板 / 统一枚举来源，收口散落常量。

## Dev Notes

### 架构约束（必须遵守）

1. **`sys` 域是模板真相源：** 渠道 / 集成模板属于平台治理与主体映射范畴，应落在 `sys` 域，而不是塞进 `sms`、`ums` 或新的平行根模块。
2. **模板与绑定分离：** 模板主数据描述“如何接入”，绑定真相源描述“对谁生效”；不要把两者揉成一条大 JSON，导致影响范围不可查询。
3. **秘钥只存引用：** 模板里只能保留 `credentialRef`、配置项 key 或脱敏摘要，不能在 DB / API / UI / story 文档中出现明文供应商秘钥。
4. **入口只存语义目标：** H5、小程序、消息入口都必须复用意图对象，不准把裸 URL 或临时 query 拼接当成平台治理模板。
5. **渠道 vocabulary 必须全仓统一：** 8.6 需要消灭 `mini-program` / `mini_program` 分叉，后续漏斗、模板、租户、商户、移动端才能共享同一套渠道语义。
