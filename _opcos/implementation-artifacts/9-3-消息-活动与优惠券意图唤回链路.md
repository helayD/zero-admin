# Story 9.3: 消息、活动与优惠券意图唤回链路

Status: review

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a 消费者,
I want 从订单提醒、活动召回、优惠券通知、站内消息或运营入口直接回到目标页,
so that 我可以继续刚才相关的交易动作而不是重新搜索入口。

## Acceptance Criteria

1. **Given** 系统生成订单、活动、优惠券或站内消息入口 **When** 用户点击对应入口唤起 App **Then** 系统依据统一意图对象跳转到目标商品、专题、购物车、订单或售后页面 **And** 需要登录时保留原始目标上下文。

2. **Given** 目标资源已失效或最小版本不满足 **When** 唤回流程继续执行 **Then** 系统返回结构化恢复提示和替代落点 **And** 记录到达率、失败原因和落地结果埋点。

## AC 覆盖矩阵

- **AC1（统一意图对象 + 唤回目标页 + 登录后保留上下文）**：Task 1.1-1.7、2.1-2.7、3.1-3.9、4.1-4.4
- **AC2（目标失效 / 版本不满足的结构化恢复 + 埋点）**：Task 1.3-1.7、2.4-2.7、3.4-3.9、4.2-4.8、5.1-5.5

## 背景与关键风险（必须优先阅读）

> **⚠️ CRITICAL - 当前消息契约仍停留在 `linkType/linkId`，并不满足架构要求的统一意图对象：** `api/front/internal/types/member_message.go`、`api/front/internal/logic/member/message/messagelistlogic.go`、`rpc/ums/proto/member_message.proto` 与 `rpc/ums/ums.proto` 当前暴露的仍是 `linkType` / `linkId`，没有 `intentType`、`targetType`、`fallbackType`、`requiresAuth`、`minAppVersion`、`intentId` 等字段。9.3 必须先补齐统一契约，不能继续让 Flutter 端猜测跳转语义。
>
> **⚠️ CRITICAL - Flutter 恢复底座只支持 5 类 recent context 目标，尚未覆盖优惠券、售后和活动 / 专题召回：** `flutter-mall/lib/model/app_recent_context.dart` 与 `flutter-mall/lib/utils/app_recovery_router.dart` 目前只支持 `home`、`cart`、`order_list`、`product_detail`、`order_detail`。如果 9.3 直接复用现状，`coupon`、`after_sales`、`activity/subject` 入口要么丢失，要么只能回首页。
>
> **⚠️ CRITICAL - `message.dart` 现在仍混用 `MaterialPageRoute` 和未注册的 `pushNamed`：** `flutter-mall/lib/view/mine/message/message.dart` 对 `order` / `coupon` 直接页面跳转，对 `product` / `activity` 走 `pushNamed('/product')`、`pushNamed('/activity')`，而当前仓库并没有全局 `routes` / `onGenerateRoute`。9.3 必须彻底去掉这种脆弱路径，统一走语义化 intent dispatcher。
>
> **⚠️ CRITICAL - 当前 Flutter 侧没有稳定“专题 / 活动详情页”可供真实唤回：** 仓库能确认的只有首页里的 `subjectList` / `preferredAreaList` 数据与展示，未发现可直接打开的专题或活动详情页文件。9.3 不得伪造 `ActivityPage` 或死路由来“满足 AC”；若目标当前没有稳定页面，必须返回结构化 fallback，而不是静默失败。
>
> **⚠️ CRITICAL - `CouponList` 和售后链路还没有真正接入统一恢复语义：** `flutter-mall/lib/view/mine/coupon/coupon_list.dart` 没有 `intentSource` / recovery context 写入；`flutter-mall/lib/view/mine/order/apply_after_sales.dart`、`order_logistics.dart` 虽已有 `intentSource` 预留，但实际消息 / 唤回链路尚未接入。9.3 必须把这些目标纳入统一 intent contract，而不是只修 `Message` 页面。
>
> **⚠️ CRITICAL - `HttpUtil` 还没有传递架构要求的最小客户端上下文：** `flutter-mall/lib/utils/http_util.dart` 当前只统一加 `Authorization`，没有 `appVersion`、`platform`、`deviceId`、`intentSource`、`intentId`、`networkState`。架构已要求 `front-api` 识别这些字段；9.3 若不补齐，后端无法做最小版本判断、链路埋点归因和结构化恢复决策。
>
> **⚠️ CRITICAL - 当前仓库没有成型的深链 / 路由框架，不要为了 9.3 顺手引入第二套导航体系：** Flutter 端当前恢复与跳转都基于 `Navigator + MaterialPageRoute + AppRecoveryStore/AppRecoveryRouter`，仓库里也没有 `go_router`、`app_links`、`uni_links` 或统一 `onGenerateRoute` 基线。9.3 必须优先在现有共享层上完成 recall dispatcher，而不是借机把整个导航栈迁到另一套方案。
>
> **⚠️ CRITICAL - 9.1 / 9.2 的恢复与状态壳层边界不能被破坏：** 9.1 已通过 `AppRecoveryStore`、`IntentRecoveryShell`、`AppLifecycleProvider` 建立 recent context / pending intent / login restore 基座；当前工作树里 9.2 对 `Commerce State Shell` 与 `CommerceStateResolver` 的落地也已开始。9.3 必须在这两层之上扩展，不得复制第二套恢复存储、登录恢复链或错误反馈模型。
>
> **⚠️ CRITICAL - 运营入口与多渠道入口已有意图契约配置基础，不应在客户端硬编码一份“平行真相源”：** `rpc/sys/internal/logic/channelintegrationtemplateservice/service_helpers.go` 与相关 admin types 已有 `intent_contract_config` 能力。9.3 应明确优先复用 / 对齐这套契约源，避免消息、运营位、渠道模板各自定义不兼容的跳转字段。
>
> **⚠️ CRITICAL - 消息 intent 不能覆盖 recent context，除非目标真的恢复成功：** recent context 代表“最近一次有效上下文”；消息召回 intent 代表“这次想去哪里”。9.3 必须把两者分开处理，不能因为收到一条已失效的活动消息，就把 9.1 已保存的有效商品 / 订单上下文污染掉。

## 明确非目标（本 Story 不做）

- 不在本 Story 中实现 9.4 的权限请求与拒绝替代路径，或 9.5 的升级闸门完整 UI；但消息 intent 流必须为 `requiresAuth`、`minAppVersion`、权限未满足等恢复分支预留结构化结果。
- 不接入厂商推送 SDK、APNs / FCM 全量生产配置或整套原生通知投递平台；本 Story 先统一 App 内消息、通知 payload、运营入口参数和未来外部唤回入口所共用的 intent contract 与 dispatcher。
- 不重写 Flutter 全局导航体系，不把现有 `MaterialPageRoute` 一次性迁移成命名路由。
- 不虚构不存在的 `ActivityDetail` / `SubjectDetail` / `CouponDetail` 页面；当前仓库若没有稳定目标页，必须显式 fallback 到已存在页面或给出失败反馈。
- 不新增第二套本地存储、第二套恢复 store 或第二套登录恢复逻辑；继续复用 `AppRecoveryStore`、`IntentRecoveryShell`、`HttpUtil`、`Login`。
- 不顺手重构消息中心全部 UI 视觉；消息列表的状态表达优先复用 9.2 的 `Commerce State Shell` 能力，不额外造第三套空态 / 错误态 / loading 组件。

## 实施顺序（必须按序推进）

1. 先定义统一 recall intent 契约、合法目标白名单、legacy `linkType/linkId` 到新契约的兼容映射规则。
2. 再扩展 Flutter 恢复模型 / store / router，让消息 intent、pending intent、recent context 各司其职。
3. 再把 `Message` 页、优惠券页、订单 / 售后目标页和运营入口参数接入统一 dispatcher，去掉分散跳转逻辑。
4. 最后补结构化 fallback、最小版本 / 登录恢复 / 埋点与测试，不让 intent 只做到“能跳”，却不能稳定恢复和解释失败。

## Tasks / Subtasks

### 一、统一消息与运营入口的 recall intent 契约

#### Task 1 (AC: 1, 2): 在前后端补齐统一意图对象，并对 legacy 字段保持兼容

**目标：** 先把“入口给 App 的到底是什么”定义清楚，再让 Flutter 接入。不能继续依赖 `linkType/linkId` 猜页面。

- [x] 1.1 在消息相关协议中补齐统一 recall intent 字段，至少覆盖：`intentType`、`targetType`、`targetId`、`targetTab`（如需要）、`fallbackType`、`fallbackTargetId` / `fallbackTab`、`requiresAuth`、`minAppVersion`、`intentId`、`issuedAt`。
- [x] 1.2 修改源定义而不是手改生成物：优先更新 `rpc/ums/proto/member_message.proto` 与 `rpc/ums/ums.proto`，然后重新生成 client / pb / types；不要直接改 `rpc/ums/client/**` 或生成的 `*_pb.go`。
- [x] 1.3 在 `api/front/internal/types/member_message.go` 与 `api/front/internal/logic/member/message/*.go` 中把新 intent 对象透出给 Flutter，必要时保留 legacy `linkType/linkId` 仅作向后兼容字段，避免前端一次性切换期间接口断裂。
- [x] 1.4 为 legacy `linkType/linkId` 建立显式转换 helper，而不是散落在多个 handler / logic 里硬编码 `switch`。转换结果必须走白名单；非法或未知映射不能拼接裸 route name，只能生成结构化 fallback / failure reason。
- [x] 1.5 legacy 映射规则必须写死并可测试，例如：
  - `order`：优先使用 `linkId` 解析订单 ID；若缺失但 `relatedOrderId > 0`，可降级映射到 `order_detail`
  - `coupon`：按消息语义区分“我的优惠券列表”与“领券中心”，不能一律落同一页面
  - `product`：必须拿到有效商品 ID，否则走结构化 fallback
  - `activity/subject/preferred_area`：当前若无稳定详情页，只能生成 fallback，不得返回伪 target
- [x] 1.5 targetType 首批至少收敛到当前仓库可确认或可安全降级的语义目标：`home`、`cart`、`order_list`、`order_detail`、`product_detail`、`coupon_list`、`after_sales_apply`。`subject/activity/preferred_area` 若当前无稳定详情页，必须明确走 fallback 语义，不允许伪造页面。
- [x] 1.6 对齐运营 / 渠道模板里的 `intent_contract_config` 能力：查看 `rpc/sys/internal/logic/channelintegrationtemplateservice/service_helpers.go` 与 admin 对应 types，把消息 / 活动 / 运营入口 intent contract 的字段命名与语义保持一致，避免消息中心和渠道模板出现两套不兼容协议。
- [x] 1.7 `front-api` 对无效目标、最小版本不满足、未知 targetType 的返回必须带结构化恢复语义（failure reason + fallback），不要把 Flutter 逼回“看到错误文字后自己猜怎么回退”的模式。

### 二、扩展 Flutter 的 intent model / store / router，而不是污染 recent context

#### Task 2 (AC: 1, 2): 把“消息召回 intent”与“最近有效上下文”解耦，但仍复用 9.1 的恢复链

**目标：** recent context 继续代表“最后一次成功页”；recall intent 代表“这次入口想去哪里”。两者不能混成一个会互相覆盖的脏状态。

- [x] 2.1 在 `flutter-mall/lib/model/` 中新增专用 recall intent 模型，例如 `app_recall_intent.dart`；如果选择扩展现有 `AppRecentContext`，必须明确区分哪些字段只属于消息 / 运营 intent，哪些字段属于 recent context，并保证 9.1 的行为不被破坏。
- [x] 2.2 recall intent 模型至少包含：`intentType`、`targetType`、`targetId`、`targetTab`、`fallbackType`、`fallbackTargetId` / `fallbackTab`、`requiresAuth`、`minAppVersion`、`intentId`、`issuedAt`、`source`、`ownerMemberId`（如需要）。
- [x] 2.3 在 `flutter-mall/lib/utils/app_recovery_store.dart` 中增加 recall intent 的编码 / 解码 / pending 保存能力；pending recall intent 与 recent context 分开存储，避免消息 intent 覆盖最近有效上下文。
- [x] 2.4 扩展 `flutter-mall/lib/utils/app_recovery_router.dart` 或新增 `app_intent_dispatcher.dart`，统一按语义目标构建页面：`ProductDetail`、`OrderDetail`、`OrderList(tab)`、`CouponList`、`ApplyAfterSales(orderId)`、`MainTab(initialIndex)` 等；禁止再通过未注册字符串路由拼接跳转。
- [x] 2.5 `flutter-mall/lib/layout/intent_recovery_shell.dart` 必须能处理 recall intent：登录恢复后继续原始目标；目标无效或版本不满足时走明确 fallback；不要在失败时默默吞掉 intent。
- [x] 2.6 `flutter-mall/lib/utils/http_util.dart` 统一加最小客户端上下文头，如 `appVersion`、`platform`、`intentSource`、`intentId`、`networkState`；不要在页面级请求里各自拼 header。若仓库还没有稳定的运行时版本读取 helper，应优先用共享常量 / 构建元数据，而不是在 widget 里手写版本号。
- [x] 2.7 recall intent 只有在目标页真正拿到有效数据后，才允许转化成 recent context；消息 intent 失败、目标资源失效或结构化 fallback 期间，不得覆盖 9.1 已保存的 recent context。
- [x] 2.8 不要为 9.3 额外引入 `go_router`、`app_links`、`uni_links` 等新导航 / 深链框架来替代当前恢复链。若未来外部入口需要原生桥接，也必须隔离在共享适配层，不能把现有页面全部迁到另一套路由体系。

### 三、把消息页、优惠券页和可恢复目标页接到统一 dispatcher

#### Task 3 (AC: 1, 2): 先从当前仓库真实存在的入口和目标页开始，彻底移除 ad-hoc 跳转

- [x] 3.1 重构 `flutter-mall/lib/view/mine/message/message.dart` 的 `_handleMessageTap()`：不再直接 `switch(linkType)` 然后 `pushNamed('/product')` / `pushNamed('/activity')`；改为消费后端返回的 recall intent，并统一交给 dispatcher / recovery router。
- [x] 3.2 `Message` 页的加载 / 空态 / 错误态优先复用 9.2 的 `Commerce State Shell` / `CommerceStateResolver`；如果 9.2 相关文件已存在于当前代码基线，直接复用；不要为了 9.3 再写一套消息专用 loading / error / empty UI。
- [x] 3.3 `flutter-mall/lib/model/message_model.dart` 需要同步扩展 intent 字段，并对 legacy `linkType/linkId` 做兼容解析，确保旧数据下仍能回退为结构化 fallback，而不是崩溃。
- [x] 3.4 `flutter-mall/lib/view/mine/coupon/coupon_list.dart` 与 `flutter-mall/lib/view/mine/coupon/available_coupon_list.dart` 都要纳入 recall 目标设计：优惠券通知进入后必须明确是落“我的优惠券列表”还是“领券中心”，不能都粗暴落到首页，也不能都误落同一页面。
- [x] 3.5 `flutter-mall/lib/view/mine/order/apply_after_sales.dart` 已有 `intentSource` 预留，应真正纳入 dispatcher：当 recall intent 指向售后申请时，必须携带 `orderId` 并复用现有数据加载 / 提交边界，而不是在消息页里新造售后逻辑。
- [x] 3.6 `flutter-mall/lib/view/mine/order/order_detail.dart`、`order_list.dart`、`product_detail.dart` 当前已支持 `intentSource` 或 recent context 写入，9.3 需复用这些页面级恢复点，不重复发明另一套“消息版订单详情 / 商品详情”。
- [x] 3.7 对 `subject/activity/preferred_area` 类 intent 做现实约束确认：当前仓库若仍没有稳定详情页，不新增伪页面；必须落结构化 fallback，例如回到 `HomePage` 并给出“活动入口暂不可直达，已返回首页继续浏览”的明确结果，同时记录失败原因。
- [x] 3.8 若决定为专题 / 优选专区补真实落点，则必须建立真实页面与真实数据来源，优先基于现有 `api/front/doc/api/home/home_recommend_subject.api`、`home_preferred_area.api` 与首页返回结构，不允许造静态假详情页。
- [x] 3.9 `flutter-mall/lib/view/mine/message/message.dart` 标记已读的时机要与导航接受结果保持一致：至少避免“跳转目标非法但消息仍显示已处理”的误导；必要时把“已读”和“导航成功 / 已处理”的反馈分开。
- [x] 3.10 `flutter-mall/lib/view/mine/mine.dart` 的未读消息入口与计数刷新也要保持与 recall 语义一致：消息被点击、已读、fallback 或恢复失败后，未读数与消息列表状态不能长期矛盾。

### 四、补齐最小版本、登录恢复、结构化 fallback 与埋点

#### Task 4 (AC: 1, 2): 让 recall intent 不只是“能跳”，还要“跳错了能解释、能回退、可观测”

- [x] 4.1 登录恢复继续复用 `IntentRecoveryShell` + `Login(recoveryIntent: ...)` 链路；消息 / 运营 intent 在 401、冷启动和前后台切换下都必须保留原始目标，而不是回到首页。
- [x] 4.2 最小版本不满足时，不要只弹原始错误 toast；必须返回结构化恢复提示，至少说明：受影响目标、是否阻断、当前替代落点、下一步可做什么。
- [x] 4.3 目标资源失效时按目标类型做明确 fallback：
  - 商品不可见 / 已下架：复用 `ProductDetail.visibility` 的恢复语义，回到首页或可替代落点；
  - 订单不可访问 / 状态失效：回到 `OrderList(tabIndex=1 或 0)` 或 `OrderDetail` fallback；
  - 售后目标不可进入：回到 `OrderDetail` 并给出清晰提示；
  - 活动 / 专题目标当前无稳定页面：回到 `HomePage` 相关主入口并说明原因。
- [x] 4.4 `HttpUtil` / API 调用链应把 `intentSource`、`intentId` 等透传到后端，供日志、恢复分析与链路埋点使用；不要只在客户端打印日志。
- [x] 4.5 在 `AppLifecycleProvider` 或专用 telemetry helper 中记录最小指标：`intentReceived`、`intentLoginRequired`、`intentRestored`、`intentFallbackUsed`、`intentFailedReason`、`targetType`、`source`、`intentId`。
- [x] 4.6 失败原因必须是可枚举、可测试、可埋点的结构化码值，例如：`unsupported_target`、`resource_unavailable`、`min_version_unmet`、`login_required`、`invalid_payload`，而不是只保留原始字符串。
- [x] 4.7 运营入口 / 通知 payload / 站内消息点击 / 登录恢复 / resume 恢复都应汇总到同一 dispatcher，确保不同来源共享同一套成功、失败和 fallback 行为。
- [x] 4.8 不要让 9.3 自己实现一套升级闸门或权限弹窗；当失败原因属于未来 9.4 / 9.5 的边界时，先走结构化 fallback 与说明文案，并把上下文完整保留给后续故事接手。

### 五、测试、验收与回归保护

#### Task 5 (AC: 1, 2): 为 recall intent 链路补足协议、路由和恢复行为的测试

- [x] 5.1 Go 侧至少补定向测试：
  - legacy `linkType/linkId` 到 recall intent 的映射
  - 非法 targetType / 缺字段 / 不支持版本时返回结构化 fallback
  - message list / detail logic 正确映射 intent 字段
- [x] 5.2 Flutter 单测 / Widget 测试至少覆盖：

  - `Message` 点击后通过 dispatcher 跳到 `OrderDetail`、`ProductDetail`、`CouponList`、`ApplyAfterSales`

## Dev Notes

### 架构约束（必须遵守）

1. **统一 intent 契约优先于页面私有 query：** 消息、活动、优惠券、待支付订单等唤回入口统一使用 `intentType/targetType/targetId/fallbackType/requiresAuth/minAppVersion` 语义，不允许页面自己定义裸 query。
2. **recent context 与 recall intent 分离：** recent context 记录“上次成功页”，recall intent 记录“本次入口想去哪里”；消息 intent 不能在失败时覆盖 recent context。
3. **不继续放大命名路由假设：** 当前 Flutter Mall 仍以 `MaterialPageRoute` 为主，`message.dart` 中 `pushNamed('/product')` / `pushNamed('/activity')` 是必须收口的反模式。
4. **客户端上下文头只能在共享网络层统一处理：** `appVersion/platform/deviceId/intentSource/intentId/networkState` 应在 `HttpUtil` 或共享层注入，不能分散在页面里手工写。
5. **活动 / 专题目标必须现实落地：** 若当前仓库没有真实页面，则明确 fallback；不要为了“覆盖 AC 文案”加假页面。
6. **登录恢复仍走 9.1 的壳层：** 401、冷启动、resume 和消息唤回都必须复用 `IntentRecoveryShell`、`AppRecoveryStore`、`Login` 链路，不得再写消息专属登录恢复。
7. **错误与 fallback 要结构化、可观测：** UI 文案可以友好，但底层原因必须有枚举值，供日志、测试和埋点使用。
8. **页面成功后才允许转 recent context：** 商品详情需 `visibility.visible == true`，订单详情需订单可访问，售后页需参数和前置数据有效，优惠券页需目标页可展示。
9. **与 9.2 的状态壳层保持一致：** 消息页和 recall 目标页的 loading / empty / error / weakNetwork 反馈优先复用 `Commerce State Shell`。
10. **协议变更回到生成源：** 变更 `member_message` 数据结构时，必须修改 `.proto` / `.api` 源定义并重新生成，不手改客户端生成物。
11. **不要顺手迁移到新导航 / 深链框架：** 9.3 的目标是补 recall intent contract 与 dispatcher，不是把 Flutter Mall 从 `Navigator + MaterialPageRoute` 迁到 `go_router` / `app_links` / `uni_links`。
12. **优惠券存在两个真实入口：** `CouponList` 是“我的优惠券”，`AvailableCouponList` 是“领券中心”；消息 / 运营 intent 必须区分两者语义，不能混用。
13. **优先复用消息现有字段做兼容降级：** legacy 消息若 `linkId` 缺失但 `relatedOrderId` 可用，应优先降级到 `order_detail`，不要直接失败。

### 当前仓库信号与实现情报

1. **消息协议尚未结构化：** 当前 UMS / front-api 只传 `linkType/linkId`，说明 9.3 必须把协议升级纳入工作范围，而不是只改 Flutter。
2. **恢复底座已具雏形：** `AppRecoveryStore`、`IntentRecoveryShell`、`AppLifecycleProvider` 已能处理 recent context、pending intent 和 login restore，9.3 最佳路径是扩展它们，而非重做。
3. **消息页跳转存在明显断层：** `message.dart` 的 `pushNamed('/product')` / `pushNamed('/activity')` 没有全局路由注册支撑，是 9.3 最直接的功能性 bug。
4. **当前支持的目标页是有限集合：** `ProductDetail`、`OrderDetail`、`OrderList`、`Cart`、`HomePage` 已纳入 recent context；`CouponList`、`ApplyAfterSales` 仍需纳入统一 recall intent 体系。
5. **专题 / 优选专区只有首页数据，没有稳定详情页：** `HomePage` 已展示 `subjectList` 与 `preferredAreaList`，但仓库未扫描到对应详情页，这决定了 9.3 必须实现“结构化 fallback”而不是假详情。
6. **9.2 的状态壳层已经在当前工作树开始落地：** `commerce_state_shell.dart`、`commerce_state_resolver.dart`、`home_page.dart` 的接入迹象表明 9.3 应直接复用这层，而不是重新写消息中心的 loading / error UI。
7. **`ApplyAfterSales` / `OrderLogistics` 已经有 Story 9.3 预留参数：** 这说明当前代码库已经预期 9.3 会把消息 / recall 语义接进这些页面，不应忽略现有扩展点。
8. **`HttpUtil` 仍只传 token：** 若不在共享层补最小客户端上下文，后端无法做版本校验与链路归因，结构化恢复就会缺少关键输入。
9. **“领券中心”已有真实页面：** `AvailableCouponList` 已存在，说明优惠券 recall 不应只盯着 `CouponList`，而应按消息语义把“我的券”和“可领取券”分开建模。
10. **未读消息数已有独立入口状态：** `flutter-mall/lib/view/mine/mine.dart` 会请求 `unreadCountUrl`，9.3 若调整已读 / recall 时机，必须同时考虑未读角标的一致性。

### 最新技术信息（2026-04-05 调研）

1. Flutter 官方 deep linking 文档当前仍强调把外部入口统一接入同一套导航 / 状态恢复流，而不是由每个入口各自维护跳转分支。这与 9.3 的统一 recall intent dispatcher 完全一致，说明不应继续保留 `message.dart` 的页面私有跳转逻辑。  
2. Android Developers 官方 App Links 文档仍把“已验证链接直接进入应用、未命中则回到 Web / fallback”作为推荐模式，这意味着 9.3 的 intent contract 必须天然支持 success / fallback 双路径，而不是只表达“要去哪个页面”。  
3. Apple 官方 Universal Links 文档继续强调统一、可验证、跨安装状态可回退的入口语义。这进一步说明 9.3 不能写 Android 专属的临时参数协议，recall intent 必须保持平台无关和可回退。
