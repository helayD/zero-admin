# Story 1.7: 治理审计与安全事件检索

Status: review

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a 平台审计角色,
I want 查看登录日志、操作日志、安全事件和关键审批轨迹,
so that 我可以快速追溯主体变更、异常操作和治理风险。

## Acceptance Criteria

1. **Given** 审计角色进入日志与审计中心
   **When** 按平台、租户、商户、用户、时间和事件类型筛选记录
   **Then** 系统返回匹配的登录日志、操作日志和安全事件
   **And** 列表中展示主体、动作、结果、处理人和发生时间。
2. **Given** 订单状态、权限、主体启停或审批结果发生关键变更
   **When** 变更成功写入业务系统
   **Then** 审计中心保留至少 180 天可追踪记录
   **And** 相关记录可用于后续问题定位与责任追溯。

## Dev Notes

### Scope Guardrails

- 本 story 只负责“治理审计与安全事件检索”的统一读工作台，不回头重做 Story 1.6B 的写侧越权校验，也不提前扩展 Epic 7 的链路监控告警中心；它消费已有审计产物，把它们做成可查询、可串联、可追责的后台能力。[Source: `_opcos/planning-artifacts/1-new-feature/epic.md#Story-17-治理审计与安全事件检索`; `_opcos/planning-artifacts/1-new-feature/epic.md#Story-16B-核心业务对象关键写操作校验与越权审计`; `_opcos/planning-artifacts/1-new-feature/epic.md#Story-75-异步链路监控视图`]
- 本 story 不应创建新的“日志中心服务”“审计 ES 索引”或平行审计后台工程；统一审计中心必须继续落在 `sys` 域、`admin-api` 和 `web-admin/log` 体系内，沿用当前治理边界。[Source: `_opcos/planning-artifacts/1-new-feature/architecture.md#Project-Structure--Boundaries`; `_opcos/project-context.md`]

### Story Foundation / Business Context

- FR44 要求平台管理员、租户审计角色和授权商户审计角色可以在对应作用域内查看登录日志、操作日志和安全事件；FR45 要求平台对关键业务对象和作用域变更保留可追踪的状态、操作和审批记录，用于问题定位与责任追溯。Story 1.7 是这两条 FR 的直接收口。[Source: `_opcos/planning-artifacts/1-new-feature/prd.md#后台管理与权限治理`]
- Epic 1 对 Story 1.7 的 AC 明确要求：审计角色进入日志与审计中心后，需要按平台、租户、商户、用户、时间和事件类型筛选记录，返回主体、动作、结果、处理人和发生时间；同时关键变更的记录需至少保留 180 天可追踪。[Source: `_opcos/planning-artifacts/1-new-feature/epic.md#Story-17-治理审计与安全事件检索`]
- UX 把平台治理和异常追责定义为“在明确上下文里完成高风险确认”的连续流程，因此审计中心不是简单日志表堆叠，而是一个能让审计角色快速定位“谁在什么主体下，对什么资源，做了什么动作，结果怎样”的时间线工作台。[Source: `_opcos/planning-artifacts/1-new-feature/ux-design.md#Journey-Patterns`; `_opcos/planning-artifacts/1-new-feature/ux-design.md#平台开通与商户治理流`; `_opcos/planning-artifacts/1-new-feature/ux-design.md#Order-Timeline-Panel`]

### Technical Requirements

- 审计中心必须以 `sys` 域聚合查询为主，不允许前端分别调用 `login_log`、`operate_log`、`security_event`、`tenant_audit`、`merchant_audit` 后自行拼时间线。聚合、排序、scope 过滤、脱敏和 trace/resource 串联必须由后端统一完成。[Source: `_opcos/planning-artifacts/1-new-feature/architecture.md#Project-Structure--Boundaries`]
- 查询模型至少要统一支持：`scopeType/platformId/tenantId/merchantId`、`operatorId/operatorName`、`traceId`、`resourceType/resourceId`、`eventType`、`result/status`、时间范围、关键字摘要。否则审计角色无法从“主体、资源、链路”三个维度做有效追溯。[Source: `_opcos/planning-artifacts/1-new-feature/architecture.md#Authentication--Security`; `_opcos/planning-artifacts/1-new-feature/architecture.md#Observability`]
- `sys_operate_log.extra` 与 `sys_security_event.payload` 都是结构化扩展字段，审计中心必须在后端完成规范化解析，把字段收口成统一视图；不要把 JSON 解析责任交给前端页面，否则后续写入格式稍有演变就会把 UI 打碎。[Source: `script/sql/sys/sys_operate_log.sql`; `script/sql/sys/sys_security_event.sql`; `pkg/audit/governance.go`; `pkg/audit/security_event.go`]
- 180 天留痕要求不能只停留在文档层：需要明确时间索引、scope 索引、trace/resource 索引、最大查询窗口和分页策略，保证“可追踪”是能被后台真实执行的，而不是逻辑上存在。[Source: `_opcos/planning-artifacts/1-new-feature/prd.md#Security`]
- 详情页必须做到“列表可见 == 详情可见”，禁止出现列表经过 scope 过滤，但知道某条日志主键后仍能通过 detail 接口读全局数据的旁路问题。这一点对 `QueryLoginLogDetail`、`QueryOperateLogDetail` 以及后续新增的安全事件 / 审批轨迹详情尤为关键。[Inference from: `api/admin/doc/api/sys/login_log.api`; `api/admin/doc/api/sys/operate_log.api`; `_opcos/implementation-artifacts/1-6a-核心业务对象查询范围过滤与主体透传.md`]

### Architecture Compliance

- 继续遵循 `web-admin -> admin-api -> rpc/sys -> MySQL` 的现有边界。审计中心消费的真相源仍然是 `sys_login_log`、`sys_operate_log`、`sys_security_event`、`sys_tenant_audit`、`sys_merchant_audit`，不引入 ES/Mongo 作为新的审计真相源。[Source: `_opcos/planning-artifacts/1-new-feature/architecture.md#Data-Architecture`; `_opcos/planning-artifacts/1-new-feature/architecture.md#Project-Structure--Boundaries`]
- 作用域过滤必须继承 Story 1.6A 的服务端范围隔离，不允许因为“是日志”就退回前端软筛选或 URL 级权限兜底。`CheckUrlMiddleware` 只能解决入口权限，不能代替审计对象级数据隔离。[Source: `/Users/helay/Documents/GitHub/zero-admin/_opcos/implementation-artifacts/1-6a-核心业务对象查询范围过滤与主体透传.md`; `api/admin/internal/middleware/checkurlmiddleware.go`]
- 共享治理 / 审计 helper 优先放在 `pkg/audit/`、`pkg/scope/`、`api/admin/internal/common/` 或 `rpc/sys/internal/logic/common/`，不要在新审计中心逻辑里复制一份 JSON 解析或 scope 判定逻辑。[Source: `_opcos/project-context.md`; `pkg/audit/governance.go`; `pkg/audit/security_event.go`]

### Web Admin / UX Requirements

- 审计中心页面必须延续当前后台模式：`PageContainer + ProTable + Drawer/Detail`，而不是新起一套可视化监控大屏或自由布局。这样才能和现有登录日志 / 操作日志页保持同仓库一致性。[Source: `web-admin/src/pages/log/LoginLog/index.tsx`; `web-admin/src/pages/log/OperateLog/index.tsx`; `_opcos/project-context.md`]
- 页面应持续显示 `Scope Context Bar`，让审计角色始终知道自己当前查看的是平台、租户还是商户上下文；切换主体时，列表、统计角标、详情和时间线都必须同步收敛。[Source: `_opcos/planning-artifacts/1-new-feature/ux-design.md#Scope-Context-Bar`]
