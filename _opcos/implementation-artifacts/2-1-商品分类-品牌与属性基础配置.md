# Story 2.1: 商品分类、品牌与属性基础配置

Status: in-progress

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a 商户管理员,
I want 管理商品分类、品牌和关键属性,
so that 我可以先建立可检索、可运营的商品目录基础语义。

## Acceptance Criteria

1. **Given** 商户管理员具备商品管理权限
   **When** 新增或编辑分类、品牌和商品属性
   **Then** 系统保存对应目录基础数据并绑定当前商户作用域
   **And** 后续商品建档可以复用这些分类、品牌和属性配置。
2. **Given** 商品信息缺少必填字段或作用域不合法
   **When** 商户管理员尝试保存
   **Then** 系统在表单内明确指出缺失项或冲突项
   **And** 不允许生成不完整或跨主体的目录基础数据。

### Story Foundation / Business Context

- Epic 2 的目标是让商户和运营在正确作用域内发布商品与导购内容，让消费者通过首页、分类、品牌、专题与详情页发现可信、可售的商品。2.1 是这个 epic 的起点，它负责把“分类、品牌、属性”做成后续商品建档和导购浏览的基础语义层。[Source: `_opcos/planning-artifacts/1-new-feature/epic.md#Epic-2-商品目录发布与前台导购可见性`]

### Technical Requirements

- 目录基础配置必须与既有生成链兼容：新增请求字段、作用域字段或返回字段时，必须修改 `.api`、`.proto`、SQL 源，再重新生成，不手改 `types.go`、`routes.go`、`pb.go`、client 或 `gen/query` 生成物。[Source: `_opcos/project-context.md`; `_opcos/planning-artifacts/1-new-feature/architecture.md#Migration--Schema-Evolution`]
- 分类、品牌、属性、属性分组、规格等目录基础数据，要么明确是平台共享、要么明确是商户私有、要么有清晰继承关系；不能继续处在“后台能改，但不知道属于谁”的灰色状态。[Inference from multi-tenant governance requirements; Source: `_opcos/planning-artifacts/1-new-feature/prd.md#平台租户与多商户治理`]
- 这些目录配置未来会被 2.2 的 SPU/SKU 建档直接消费，因此返回结构必须为后续建档提供足够字段，如名称、状态、排序、作用域、候选值 / 可选项等，避免 2.2 再回头补接口。[Source: `_opcos/planning-artifacts/1-new-feature/epic.md#Story-22-商品规格SPUSKU-与库存建档`]
- 删除和状态切换要特别注意“被引用约束”：已经被商品建档使用的分类、品牌、属性、规格等，不应允许静默删除；至少要返回明确错误，让商户知道需要先处理引用关系。[Inference from product master data dependency; Source: `_opcos/planning-artifacts/1-new-feature/ux-design.md#Recovery-first-Feedback`]
- 后台页面服务层必须继续走 Umi `request`，不能在目录配置页面里重新写裸 `fetch` 或手工 token 流；Go 侧必须继续遵循 `handler -> logic -> svc`，不把目录业务规则塞进 handler。[Source: `_opcos/project-context.md`]

### Architecture Compliance

- 继续遵循 `web-admin -> admin-api -> rpc/pms -> MySQL` 的边界，不新增目录专用微服务或前端直连 DB/ES 的捷径。[Source: `_opcos/planning-artifacts/1-new-feature/architecture.md#Project-Structure--Boundaries`; `_opcos/planning-artifacts/1-new-feature/architecture.md#Service-Boundaries`]
- MySQL 仍然是目录基础数据的真相源；Redis 只用于缓存、协调或热点读，不能把分类/品牌/属性状态放成“缓存即真相”。[Source: `_opcos/planning-artifacts/1-new-feature/architecture.md#Data-Architecture`]
- 目录基础配置虽然属于 PMS 域，但必须继承全仓统一的 scope / audit / idempotency 约束。也就是说，商户管理员配置品牌、分类、属性时，依然要使用平台化治理模型，而不是回退到老单商户心智。[Source: `_opcos/planning-artifacts/1-new-feature/architecture.md#Decision-Priority-Analysis`; `_opcos/project-context.md`]
- Web 端保持 `index.tsx + service.ts + data.d.ts + components/*` 的既有组织模式，所有网络请求统一走 `request`；这在 2-1 不应被打破。[Source: `_opcos/planning-artifacts/1-new-feature/architecture.md#Frontend-Architecture`; `_opcos/project-context.md`]
