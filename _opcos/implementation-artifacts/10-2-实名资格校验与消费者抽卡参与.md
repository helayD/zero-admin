# Story 10.2: 实名资格校验与消费者抽卡参与

Status: review

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a 消费者,
I want 在登录并获得抽卡机会后发起抽卡,
so that 我可以在明确规则、剩余次数和结果反馈下参与提货卡活动，并在中奖后按实名要求完成兑卡或发放。

## Acceptance Criteria

1. **Given** 消费者进入抽卡活动页 **When** 页面加载完成 **Then** 系统展示活动规则、卡池说明、卡片预览、中奖记录摘要、个人参与记录和剩余抽卡次数 **And** 对未登录、次数不足、活动不可用等状态明确提示原因；未实名不阻断参与抽卡，但中奖后兑卡或发放需提示实名要求。

2. **Given** 消费者已登录、账号可用且拥有抽卡机会 **When** 发起一次抽卡 **Then** 系统以单次请求幂等方式完成资格校验、次数扣减、中奖抽样和结果返回 **And** 不会因为重复点击产生多次抽卡结果。

## AC 覆盖矩阵

- **AC2（机会发放 + 幂等抽卡 + 次数扣减 + 结果返回）**：Task 1.2-1.7、2.2-2.7、3.3-3.10、4.2-4.5、5.3-5.7、6.1-6.6

## 背景与关键风险（必须优先阅读）

> **⚠️ CRITICAL - 10.1 已经把抽卡活动配置真相源建在 `sms` 域，10.2 必须直接消费，而不是再造前台活动表。** 当前仓库已经存在 `sms_draw_activity`、`sms_draw_pool`、`sms_card_template`、`sms_draw_pool_template` 和后台聚合查询逻辑，详见 `script/sql/sms/migration_20260416_draw_activity.sql`、`rpc/sms/internal/logic/drawactivityservice/query_draw_activity_detail_logic.go`、`api/admin/internal/logic/sms/draw_activity/querydrawactivitydetaillogic.go`。10.2 要在这套配置真相源上补“前台可参与链路”，而不是复制一套 H5/Flutter 私有活动模型。
>
> **⚠️ CRITICAL - 当前仓库没有前台抽卡活动页、也没有 front 侧 draw service 注入。** `api/front/internal/handler/routes.go` 里不存在提货卡路由；`api/front/internal/svc/service_context.go` 当前也没有 `DrawActivityService`；Flutter 首页 Banner 点击仍然只弹“功能建设中”，`activity/subject` 消息召回也会 fallback 回首页。10.2 必须先打通真实前台协议与路由，再谈体验细节。
>
> **⚠️ CRITICAL - 会员实名能力目前不存在可复用真相源。** `ums_member_info` 与 `/api/member/info` 只返回昵称、手机号、积分、`lottery_times` 等基础字段，没有 `real_name_status`、`credential_ref`、`verified_at` 之类的实名状态字段。当前活动规则下，实名不作为参与抽卡的前置阻断；如中奖后兑卡或发放需要实名，必须由 `ums` 域提供可信实名状态，不能在 Flutter 本地存一个“已实名”布尔值凑合。
>
> **⚠️ CRITICAL - 10.1 的 `participant_condition_summary` / `consume_rule_summary` 目前是展示摘要，不足以直接驱动资格校验。** 如果 10.2 直接解析中文摘要文本来判断是否可参与，会变成不可测试、不可回放、不可审计的脆弱实现。必须补机器可读的资格/配额/消耗规则字段或结构化配置。
>
> **⚠️ CRITICAL - 幂等抽卡不是“前端按钮防抖”，而是服务端事务语义。** AC2 要求“重复点击不会生成多次抽卡结果”，这意味着请求必须带幂等键，服务端要以 `(activity_id, member_id, request_id)` 或等价唯一约束收口，重复请求只能返回同一结果，不能再次扣减次数或库存。
>
> **⚠️ CRITICAL - 中奖结果与资产到账是两件事。** 10.2 可以返回“未中奖”或“已中奖待到账”的抽卡结果，并把后续 10.3 的卡片实例生成、10.4 的链上 token 发放留给后续故事；但 10.2 不能提前创建链上 token，也不能在客户端把“中奖”误说成“已到账”。
>
> **⚠️ CRITICAL - Flutter 必须以后端聚合状态为准，不允许自行推断资格或到账。** UX 规范已经要求提货卡统一使用“待实名 / 可参与 / 资格不足 / 未中奖 / 已中奖待到账 / 发放处理中 / 补偿中 / 已到账”等固定状态词，页面只能消费服务端返回的资格/结果状态，不能自己拼近义词。
>
> **⚠️ CRITICAL - 活动入口必须复用现有首页 Banner / 消息召回链，而不是再造一套临时导航。** `flutter-mall/lib/model/home_model.dart` 的 `AdvertiseList` 已有 `url` 字段，消息召回已有 `activity` 目标类型和恢复闸门。10.2 应该让 Banner 和召回真正跳到抽卡页，而不是继续保留“功能建设中”的占位。

## 当前活动规则（2026-04-26 已落地）

- 每日首次登录赠送 3 次抽卡机会；注册后直接返回 token 的自动登录场景，也按当天登录发放 3 次。
- 每完成 1 笔订单额外赠送 1 次抽卡机会；以订单 ID 做幂等发放，重复确认同一订单不能重复增加次数。
- 每次抽卡消耗 1 次机会；剩余次数使用 `ums_member_info.lottery_times`，发放幂等日志使用 `ums_member_lottery_grant_log`。
- 卡池总中奖率为 30%：SSR 5%，SR 25%，未中奖 70%；`sms_draw_pool_template.probability` 总和小于 1 时，剩余权重表示未中奖概率。
- 参与抽卡不要求实名认证；中奖后的兑卡或提货卡发放阶段才需要实名状态满足要求。

## 明确非目标（本 Story 不做）

- 不生成提货卡资产实例、不分配唯一编号；这些属于 Story 10.3。
- 不接入链上 token 发放、回执写回、失败补偿任务；这些属于 Story 10.4。
- 不完成“我的提货卡资产页”和后台审计工作台；这些属于 Story 10.5。
- 不重做 10.1 的后台抽卡配置工作台，只允许补最小必要的结构化规则字段与前台消费契约。
- 不在 Flutter 端直接接第三方实名 SDK、也不在页面内拼蚂蚁链调用；所有外部实名/链上能力都必须经服务端统一集成层接入。
- 不顺手升级 go-zero、Flutter、Umi、Ant Design、GORM 或项目部署拓扑。

## 实施顺序（必须按序推进）

1. 先补会员实名真相源、活动机器可读规则和抽卡参与记录表，确保“能否抽”与“抽了什么”都有落库依据。
2. 再补 `ums` / `sms` 的 `.proto` 与 front `.api` 源定义，让前台协议、服务端协议和生成链来源唯一。
3. 然后实现 `ums` 实名状态查询、`sms` 资格预检/参与抽卡/个人记录聚合逻辑，并以事务与唯一键收住幂等。
4. 再接 `front-api` 聚合层，把匿名访问、登录态、资格失败原因、参与结果和个人记录整理成 Flutter 直接可用的协议。
5. 最后建设 Flutter 抽卡活动页、Banner/消息唤回跳转和结果反馈，并补齐最小测试与回归验证。

## 完成判定（Definition of Done）

- 开发环境下可以通过真实 front 路由打开抽卡活动页，而不是继续停留在首页 Banner 的“功能建设中”占位。
- 未登录用户可以查看活动规则与卡片预览，并收到稳定的 `need_login` 或等价状态，而不是 401 后直接白屏或跳错页。
- 已登录未实名用户可以查看活动页并参与抽卡；若中奖，结果或后续动作必须提示完成实名后才能兑卡或发放。
- 每日首次登录、注册自动登录和订单完成都会按规则幂等发放抽卡机会，重复登录或重复确认同一订单不会重复发放。
- 同一 `requestId` 的重复抽卡请求只会返回同一条参与结果，会员次数与库存只扣减一次。
- 中奖结果只展示“已中奖待到账”或等价服务端状态，不提前显示资产编号或链上到账状态。
- `activity` 消息召回与首页活动入口都能进入真实抽卡页或明确 fallback，不再一律回首页。
- 新增接口、模型、DDL、生成产物和测试都能通过最小验收命令验证。

### 三、UMS / SMS 服务端实现

#### Task 3 (AC: 1, 2): 落地实名判断、资格预检、幂等参与与结果返回

- [ ] 3.1 在 `rpc/ums/internal/logic/` 下新增 `memberidentityservice/` 或等价逻辑，负责实名状态查询/发起入口/回执写回；若复用 `memberinfoservice/`，也必须保证职责边界清晰，不要把敏感实名逻辑硬塞进现有 `info` 查询函数里。
- [ ] 3.2 `QueryMemberInfoDetail` / `Info` 映射层如需扩展实名字段，只返回展示用与资格判断所需字段，不允许泄露原始实名数据。
- [ ] 3.3 在 `rpc/sms/internal/logic/` 下新增 `drawparticipationservice/`，专门处理前台落地页查询、资格预检、参与抽卡和个人记录查询；不要把前台参与逻辑混进后台 `drawactivityservice/`。
- [ ] 3.4 资格校验至少覆盖：
  - 活动已发布、已启用、当前时间在有效窗口内
  - 当前 scope 可见且活动未下线
  - 会员账号可用
  - 参与阶段不因未实名阻断；实名状态随落地页返回，中奖后兑卡或发放阶段再使用
  - 会员剩余抽卡次数 `lottery_times >= consume_amount`
  - 每日登录、注册自动登录和订单完成发放记录已按 `ums_member_lottery_grant_log` 幂等收口
  - 配额未耗尽（全局次数、活动次数、日次数等）
  - 卡池模板仍有可用库存
- [ ] 3.5 抽卡参与必须在事务中完成，至少锁定或等价保护：会员次数、参与记录幂等键、活动/卡池库存；同一请求不得出现“扣了次数但没结果”或“返回结果但没落记录”的半成功状态。
- [ ] 3.6 同一 `(activity_id, member_id, request_id)` 重复请求必须直接返回同一条参与记录对应的结果，不再次扣减次数、库存或重复抽样。
- [ ] 3.7 中奖抽样必须完全在服务端完成，并将命中的 `pool_id/template_id/rarity` 持久化到参与记录中；Flutter 只展示结果，不参与随机逻辑。
- [ ] 3.8 若消耗规则复用 `ums_member_info.lottery_times`，则必须由服务端原子扣减并记录 before/after；每日登录 3 次、注册自动登录 3 次、订单完成 1 次的发放必须写入 `ums_member_lottery_grant_log` 并以唯一键保证幂等；若改为活动维度次数，也必须落结构化计数真相源，禁止只在客户端减数字。
- [ ] 3.9 返回结果时必须区分：
  - `not_won`
  - `won_pending_asset`
  - `won_pending_real_name`
  - `rejected_quota_exhausted`
  - `rejected_activity_offline`
  - 以及其他稳定错误码
- [ ] 3.10 如需记录运营漏斗，扩展 `pkg/operatefunnel` 增加 `draw_activity` 或等价活动类型，并用统一事件链记录曝光/点击/参与，不要新造平行埋点体系。
