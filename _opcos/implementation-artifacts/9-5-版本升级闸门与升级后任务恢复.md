# Story 9.5: 版本升级闸门与升级后任务恢复

Status: review

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a 消费者,
I want 在版本不满足关键交易、合规或接口兼容要求时看到明确升级闸门,
so that 我能理解受影响范围，并在升级后继续原任务。

## Acceptance Criteria

1. **Given** 当前 App 版本不满足关键交易、合规或接口兼容要求 **When** 用户启动 App 或进入关键交易前置校验 **Then** 系统展示 `Upgrade Gate`，明确受影响功能、最迟生效时间、是否阻断和升级入口 **And** 阻断策略与后端兼容窗口保持一致。

2. **Given** 用户完成升级并重新进入 App **When** 升级后恢复流程执行 **Then** 系统优先返回升级前的目标上下文 **And** 记录升级拦截次数、完成率和恢复结果指标。

## AC 覆盖矩阵

- **AC1（版本不足时展示 Upgrade Gate + 与后端兼容窗口一致）**：Task 1.1-1.8、2.1-2.8、3.1-3.9
- **AC2（升级完成后恢复原任务 + 指标可观测）**：Task 1.4-1.8、3.4-3.9、4.1-4.8、5.1-5.6

## 背景与关键风险（必须优先阅读）

> **⚠️ CRITICAL - 当前仓库已经具备“版本不足”信号，但没有真正的升级门闸：** `rpc/ums/proto/member_message.proto`、`api/front/internal/types/member_message.go`、`flutter-mall/lib/model/app_recent_context.dart` 都已经包含 `minAppVersion`，`api/front/internal/logic/member/message/recall_intent_helper.go` 也会把版本不足映射成 `blocked=true` + `failureReason=min_version_unmet`；但 `flutter-mall/lib/utils/app_intent_dispatcher.dart` 当前在版本不足时只会直接 fallback 到可用页面，不会显示 `Upgrade Gate`，更不会引导升级后恢复原任务。
>
> **⚠️ CRITICAL - 启动恢复主干已经统一，但还没有升级节点：** `flutter-mall/lib/layout/app_bootstrap.dart` 当前只把启动流程收口到 `IntentRecoveryShell`，`flutter-mall/lib/layout/intent_recovery_shell.dart` 只认识 `login / target / fallback` 三类结果，没有“展示升级闸门后继续恢复”的分支。9.5 必须复用这条主干扩展升级流程，不能绕开主入口在页面里各自判版本。
>
> **⚠️ CRITICAL - 前台只在消息 recall 链路解析了客户端版本，关键交易链路尚无统一门闸：** `api/front/internal/handler/member/message/request_context.go` 目前会提取 `X-App-Version`、`X-Client-Platform`、`X-Intent-Id` 等请求头，但这是消息模块私有处理，不是 front-api 全局客户端元数据契约。9.5 如果只修消息列表而不补齐启动与交易前置校验，AC1 无法成立。
>
> **⚠️ CRITICAL - 当前“检查更新”仍是静态占位，不能被误判为已有能力：** `flutter-mall/lib/view/mine/setting/settings.dart` 的“检查更新”条目只展示固定文案 `当前版本 1.0.0`，没有策略拉取、没有升级入口、没有恢复逻辑，也没有复用已存在的恢复存储。
>
> **⚠️ CRITICAL - 当前 Flutter 端 app 版本真相源仍是手工常量，存在漂移风险：** `flutter-mall/lib/config/constant_param.dart` 里把 `appVersion` 硬编码成 `1.0.0`。它与 `pubspec.yaml` 当前 `version: 1.0.0+1` 看上去一致，但一旦发版只改 `pubspec.yaml` 或原生构建号，就会出现 header、门闸判断和显示文案不一致的问题。
>
> **⚠️ CRITICAL - AppRecoveryStore/IntentRecoveryLoop 已经是第一真相源，9.5 不允许另起炉灶：** `AppRecoveryStore` 已承接 `recentContext`、`pendingIntent`、`activeIntentCandidate`、权限上下文与草稿恢复；`IntentRecoveryShell` 已承接启动恢复与登录恢复。9.5 只能在这套共享层上扩展“升级待完成上下文 / 升级完成后的恢复结果”，不能新建第二套 VersionManager/UpgradeStore 来绕开既有恢复链。
>
> **⚠️ CRITICAL - 当前仓库还没有升级元数据接口或下载入口真相源：** `flutter-mall/lib/config/service_url.dart` 中没有版本策略接口、下载地址接口或商店入口常量，Go 侧也没有 front-api 的统一升级策略接口。这意味着 9.5 必须明确新增契约与来源，不能让开发者在 Widget 里硬编码 URL 或把 `minAppVersion` 当作唯一策略真相源。
>
> **⚠️ CRITICAL - Android Play In-App Updates 不是默认可用答案：** 官方 Android In-app Updates 只适用于 Google Play 分发场景；而当前仓库移动端接口和静态资源都指向私有服务地址，不能在未确认分发渠道前把“立即升级”直接实现为 Play Core 流程。9.5 必须先把“升级门闸 UI + 结构化元数据 + 升级后恢复”做成渠道无关能力，再决定 Android 是否额外接入 Play 内更新。

## 明确非目标（本 Story 不做）

- 不在本 Story 中顺手升级 Flutter SDK、Android Gradle Plugin、Kotlin、Go、go-zero、React、Umi 或 Ant Design；9.5 是业务闭环故事，不是技术升级 Epic。
- 不在本 Story 中接入完整推送系统、应用市场后台、灰度平台或二进制热更新方案。
- 不把 Android Google Play In-app Updates 作为默认实现前提；若未确认分发渠道，优先落地通用 `Upgrade Gate + 外部升级入口 + 恢复上下文`。
- 不新增并行的恢复存储、并行路由壳层或页面私有版本判断逻辑；继续复用 `AppBootstrap`、`IntentRecoveryShell`、`AppRecoveryStore`、`AppRecoveryRouter`。
- 不把“检查更新”页面做成独立视觉重设计需求；9.5 聚焦策略真相、门闸体验、升级后恢复和关键交易保护。
- 不在本 Story 中发明新的请求头命名或页面级 `Dio` 调用；客户端元数据仍通过共享 HTTP 层透传。
- 不要求消息 recall 之外的所有接口一次性全部强制接入版本阻断；优先覆盖启动入口、消息 recall 和关键交易前置校验，再按共享契约扩展。

## 实施顺序（必须按序推进）

1. 先定义统一升级策略契约、共享数据模型和版本真相源，明确“什么情况下需要建议升级/限时升级/强制升级”。
2. 再实现共享 `Upgrade Gate` 组件及其打开升级入口的能力，确保文案、状态与可访问性完整。
3. 然后把版本门闸接入 `AppBootstrap/IntentRecoveryShell`、消息唤回和关键交易前置校验，而不是先散落到单页。
4. 再补齐“升级完成后恢复原任务”的存储、生命周期判断、清理和 fallback 语义。
5. 最后补测试、埋点、设置页入口和回归保护，确保 9.1 / 9.3 / 9.4 已有恢复链路不被打断。

## Tasks / Subtasks

### 一、统一升级策略契约与共享版本数据模型

#### Task 1 (AC: 1, 2): 为升级门闸建立统一的策略真相源与结构化返回契约

**目标：** 把“版本是否满足要求”“是否阻断”“升级到哪里”“升级后恢复什么”从零散字段提升为共享契约，避免客户端靠字符串猜业务。

- [x] 1.1 在 front-api 的源定义层新增统一升级策略响应模型，优先落位到 `api/front/doc/api/app/app_version.api`（若命名上更适合 `app/version.api` 也必须保持同级 app 模块结构），定义例如 `AppVersionPolicyResp` / `UpgradeGatePolicyResp`，至少包含：`currentVersion`、`minSupportedVersion`、`recommendedVersion`、`updateMode`（recommended / deadline / force）、`effectiveAt`、`deadlineAt`、`affectedCapabilities`、`blocking`、`releaseNotesSummary`、`upgradeUrl` / `storeTarget`、`recoveryHint`、`traceId`。
- [x] 1.2 为关键移动入口提供统一的版本策略来源：优先新增独立查询接口（例如 `GET /api/app/version/policy`）或统一的前置校验逻辑；若新增 front-api 路由，必须先在 `api/front/doc/api/front.api` 增加 import，再走 goctl 生成链产出 handler/routes/types，禁止直接手改 `api/front/internal/handler/routes.go`。
- [x] 1.3 在 Go 侧抽出共享客户端元数据解析能力，把 `X-App-Version`、`X-Client-Platform`、`X-Intent-Source`、`X-Intent-Id`、`X-Network-State` 从消息模块私有逻辑提升为可复用 helper / middleware；共享能力优先落在 `api/front/internal/middleware/`、`api/front/internal/logic/common/` 或等价共享层，并通过 `api/front/front.go` / 生成链接入，不能只在 `member/message` handler 中可见。
- [x] 1.4 保持现有消息 recall 契约兼容：`minAppVersion`、`failureReason`、`recoveryHint`、`blocked` 继续可用，但当失败原因是版本不足时，需能够映射到共享 `Upgrade Gate` 数据模型，而不是停留在普通 fallback 字符串。
- [x] 1.5 统一版本比较逻辑：Go 与 Flutter 端必须复用同一套“点分版本 + 前缀数字截取”语义，避免服务端判阻断、客户端判通过的分叉；优先把 `api/front/internal/logic/member/message/recall_intent_helper.go` 中现有 `compareVersion/splitVersion` 语义抽到共享 helper 或对齐到等价实现，禁止在消息、启动、交易前置校验里各写一份略有差异的比较器。
- [x] 1.6 统一阻断级别与兼容窗口语义：建议升级不阻断浏览；限时升级允许提醒和稍后继续；强制升级必须阻断关键交易或启动恢复；这些规则需与后端兼容窗口保持一致。
- [x] 1.7 若升级策略按渠道或安装来源区分，必须显式建模 `platform`、`channel`、`installerStore` / `distributionSource`，禁止仅凭字符串 URL 推断。
- [x] 1.8 契约设计必须支持升级后恢复：响应中至少能让客户端知道“原目标是否允许恢复”“目标若失效该回到哪里”“恢复失败时如何给出替代落点”。

### 二、落地共享 Upgrade Gate 与版本真相源

#### Task 2 (AC: 1, 2): 在 Flutter 端新增可复用的版本门闸组件与统一版本信息来源

**目标：** 让版本阻断从“页面里一个 snackbar”升级为共享的、可访问的、可恢复的系统门槛组件。

- [x] 2.1 替换当前仅靠 `flutter-mall/lib/config/constant_param.dart` 的手工版本常量方案，建立统一 `AppVersionInfo` / `AppVersionService` 真相源；若继续保留 `appVersion` 常量，也必须把它变成 fallback，而不是唯一来源。
- [x] 2.2 在 `flutter-mall/lib/layout/` 或 `flutter-mall/lib/widgets/` 新增共享组件，例如 `upgrade_gate_dialog.dart` / `upgrade_gate_sheet.dart`，承接建议升级、限时升级、强制升级、升级完成待恢复等状态。
- [x] 2.3 `Upgrade Gate` 至少展示：受影响功能、最迟生效时间、是否阻断、升级入口、稍后继续（若允许）、恢复说明、失败后的替代路径；不可只显示“请更新到最新版本”。
- [x] 2.4 升级入口必须走共享能力（如 `url_launcher` 或统一外部跳转 helper），禁止在 Widget 中拼接平台特定 URL 并直接裸调。
- [x] 2.5 若升级入口缺失、下载 URL 为空或当前渠道不支持自动打开市场，必须展示结构化失败提示和替代说明，而不是保留一个死按钮。
- [x] 2.6 门闸组件必须可读屏、可聚焦、可键盘操作，并为受影响功能、阻断级别和主次动作提供明确文本语义。
- [x] 2.7 设置页“检查更新”必须复用同一套策略查询与 `Upgrade Gate` 组件，不允许再保留与主流程无关的静态占位逻辑。
- [x] 2.8 Android 与 iOS 的升级入口必须复用同一套 Flutter 编排接口；平台差异只能在共享 helper 中收敛，不得散落到多个页面判断。

### 三、把升级门闸接入启动恢复、消息唤回和关键交易前置校验

#### Task 3 (AC: 1, 2): 让版本门闸成为 `Intent Recovery Loop` 的正式节点

**目标：** 版本不足时不能再“直接退回 fallback 页面”，而是要在升级完成后优先回到原任务。

- [x] 3.1 扩展 `flutter-mall/lib/layout/intent_recovery_shell.dart` 的决策分支，使其在检测到 `min_version_unmet` 或全局版本策略阻断时，进入 `upgrade-gate` 分支，而不是立刻走 `fallback`。
- [x] 3.2 扩展 `flutter-mall/lib/layout/app_bootstrap.dart`，让启动流程支持：`splash -> login gate -> upgrade gate -> target restore / fallback` 的完整链路。
- [x] 3.3 改造 `flutter-mall/lib/utils/app_intent_dispatcher.dart`：当目标因版本不足被阻断时，返回结构化“show upgrade gate”计划，而不是把 `blocked=true` 简化成普通 fallback；计划对象继续沿用 9.1 / 9.3 的语义化字段（`targetType`、`targetId`、`fallbackType`、`fallbackTargetId`、`recoveryHint`），不得退回字符串 route name 或页面私有跳转参数。
- [x] 3.4 消息 recall 链路必须保留原始 intent、fallback 和 `recoveryHint`，但在版本不足时优先展示 `Upgrade Gate`，升级完成后再回到原目标，而不是一开始就标记已读并把用户送去 fallback 页。
- [x] 3.5 关键交易前置校验至少覆盖：启动恢复、消息唤回后的关键目标、确认订单、支付发起、订单恢复与售后申请等高价值链路；不能只把门闸挂在“检查更新”入口。
- [x] 3.6 对“建议升级但不阻断”的场景，App 仍可继续浏览或执行低风险流程，但必须记录门闸展示与用户选择；不能把所有升级都做成强制。
- [x] 3.7 对“强制升级”的场景，必须阻断继续进入关键交易或不兼容接口调用，且在 UI 上说明是因为交易/合规/API 兼容原因，而不是笼统失败。
- [x] 3.8 若用户从升级门闸进入登录恢复、权限恢复或弱网重试链路，完成系统门槛后仍应回到升级前保存的原始目标，而不是丢失上下文。
- [x] 3.9 若后端版本策略与消息 recall 的 `minAppVersion` 同时存在，优先以共享升级策略真相源输出最终阻断结果，但必须保留现有 recall 字段的向后兼容。

### 四、升级完成后的任务恢复、清理与观测

#### Task 4 (AC: 2): 在现有恢复存储上扩展升级完成后的回流能力

**目标：** 升级不只是“跳出去下载”，而是“回来之后继续刚才那件事”。

- [x] 4.1 在 `AppRecoveryStore` 现有键空间内扩展升级相关上下文（如 `pendingUpgradeContext` 或等价结构），记录：原目标、fallback、阻断原因、进入门闸时间、用户选择、策略版本；字段格式应直接复用 9.1 / 9.3 已有语义化恢复对象，不得新建平行恢复系统，也不得退化成只存 `routeName/url` 的弱结构。
- [x] 4.2 升级前必须保存可恢复的原始目标意图；升级后启动时应先判断当前版本/策略是否已满足，再决定恢复 target、恢复 fallback 还是继续提示升级。
- [x] 4.3 “升级完成”判定不能只依赖按钮点击；需要结合当前安装版本或门闸策略重新校验，防止用户点击升级入口后未成功安装却被误判为已完成。
- [x] 4.4 若升级后目标页已失效、订单已关闭或入口已下线，必须沿用现有 `fallbackType / fallbackTargetId / recoveryHint` 语义给出替代落点，不能让恢复链再次中断。
- [x] 4.5 清缓存、退出登录、账号切换和不可恢复版本 mismatch 时，要同步清理升级待恢复上下文，避免冷启动误回流到旧任务。
- [x] 4.6 生命周期恢复必须继续复用 `AppLifecycleProvider`，记录升级门闸相关埋点：`upgradeGateShown`、`upgradeGateBlocked`、`upgradeActionTapped`、`upgradeCompleted`、`upgradeRestoreSucceeded`、`upgradeRestoreFallbackUsed`。
- [x] 4.7 关键埋点至少带上：`scene`、`intentId`、`source`、`targetType`、`blocking`、`currentVersion`、`requiredVersion`、`platform`、`channel`，方便后续按版本分布与恢复成功率复盘。
- [x] 4.8 recent context 的成功态规则必须继续生效：只有真正恢复到目标页或稳定 fallback 后才更新 recent context；展示门闸、点击升级按钮、升级失败都不能污染“最近有效上下文”。

### 五、测试、验收与回归保护

#### Task 5 (AC: 1, 2): 为升级门闸与升级后恢复补齐测试闭环

**目标：** 9.5 的风险不在“能不能弹窗”，而在“版本不足时是否阻断正确、升级后是否真的能继续原任务”。

- [x] 5.1 为版本比较与策略解析补单元测试，至少覆盖：`1.0.0 < 1.2.0`、`1.2 == 1.2.0`、前缀数字混合、空版本、非法版本、建议升级/限时升级/强制升级判定。
- [x] 5.2 为 `AppIntentDispatcher` / `IntentRecoveryShell` 补测试，覆盖：正常恢复、登录后恢复、版本不足触发 upgrade gate、升级后恢复 target、恢复失败走 fallback。
- [x] 5.3 为消息页补 Widget / 集成测试，验证 `min_version_unmet` 不再直接 fallback，而是进入 `Upgrade Gate` 并保留原目标 intent。
- [x] 5.4 为设置页“检查更新”补测试，验证它复用共享策略与门闸组件，而不是继续展示静态版本占位。
- [x] 5.5 为 front-api 补 Go 测试，至少覆盖：客户端元数据提取、版本阻断策略映射、消息 recall 兼容旧字段、无版本策略时不误阻断。
- [x] 5.6 回归验证 9.1 / 9.3 / 9.4：`AppRecoveryStore` 仍是统一真相源；`IntentRecoveryShell` 仍是统一启动恢复入口；权限/登录/升级不会互相覆盖导致上下文丢失。

## Dev Notes

### 架构约束（必须遵守）

1. **升级门闸必须成为 `Intent Recovery Loop` 的正式节点：** 登录恢复、消息唤回、升级完成和弱网重试都要回到原目标页，而不是互相覆盖。
2. **版本策略必须有共享真相源：** 不允许消息页一套判断、启动页一套判断、交易页再一套判断。
3. **继续复用现有共享层：** `AppBootstrap`、`IntentRecoveryShell`、`AppRecoveryStore`、`AppRecoveryRouter`、`HttpUtil` 是第一真相源，不新增并行系统。
4. **当前项目决策仍是“业务闭环优先、升级后置”：** 9.5 只做 App 版本治理，不顺手发起全栈技术升级。
5. **消息 recall 的 `minAppVersion` 是既有契约，不要推翻：** 9.5 应在其上扩展统一 `Upgrade Gate`，而不是让老数据失效。
6. **设置页必须诚实表达：** 没有策略、没有升级入口、没有渠道信息时不能假装“已接入自动更新”。
7. **多渠道分发必须显式建模：** Google Play 内更新只在确认 Play 分发时可选，默认能力仍应是通用升级入口与恢复链路。
8. **recent context 仍只允许在成功态落盘：** 展示升级门闸、升级被阻断、升级跳转中都不算“恢复成功”。
9. **共享 HTTP 头保持唯一入口：** 客户端版本、平台和意图上下文继续由 `HttpUtil` 透传，不允许页面自己拼 header。
10. **升级提示不是 toast：** 必须使用结构化、可读屏、可聚焦、可恢复的共享 UI。

### 技术要求与 Guardrails

1. **优先扩展既有客户端元数据链：** `HttpUtil` 已经透传 `X-App-Version`、`X-Client-Platform`、`X-Network-State`、`X-Intent-Source`、`X-Intent-Id`；9.5 应在这条链上继续加策略消费，而不是重新发明另一套 header。
2. **版本策略不能只靠消息接口：** `recall_intent_helper.go` 当前只覆盖消息 recall 的版本阻断，9.5 需要把启动和关键交易前置校验纳入共享契约。
3. **升级策略必须与目标恢复绑定：** 任何阻断都要保留原始 target/fallback；否则“升级成功后恢复原任务”无法落地。
4. **不要把 `appVersion` 常量继续当成唯一真相源：** 至少要让显示文案、header 透传和本地门闸判断共享同一套运行时版本读取逻辑。
5. **推荐升级与强制升级必须区分：** 推荐升级允许稍后继续；强制升级必须阻断不兼容链路；限时升级介于两者之间。
6. **策略缺失时要优雅降级：** 没有策略、网络失败或返回字段缺失时，浏览与低风险能力不能被误阻断，但要保留“稍后检查更新”的可恢复说明。
7. **升级入口必须是可配置元数据：** 不允许把 App Store、下载页或渠道 URL 写死在单个页面。
8. **先守住共享层，再接页面：** `AppBootstrap/IntentRecoveryShell`、`AppRecoveryStore`、`AppIntentDispatcher` 是关键文件，先改这些，再接设置页、消息页和交易页。

### 明确反模式（命中任一项都不算完成）

1. **只改消息模块就宣称完成：** 仅修改 `api/front/internal/logic/member/message/`、`request_context.go` 或 `flutter-mall/lib/view/mine/message/`，但未把门闸接到启动恢复与关键交易前置校验，不算完成 9.5。
2. **只把门闸挂在设置页：** 仅把 `settings.dart` 的“检查更新”改成可点入口，但未接 `AppBootstrap`、`IntentRecoveryShell`、消息 recall 或关键交易前置校验，不算满足 AC1/AC2。
3. **新造并行版本治理系统：** 新增 `VersionManager`、`UpgradeStore`、`UpgradeRouter`、页面私有 `Dio` 或页面私有 header 拼装来绕开既有共享层，属于错误实现。
4. **恢复链退回字符串路由：** 用 `pushNamed`、裸 route name、页面标题字符串或临时 query 参数恢复升级前目标，违反 9.1 / 9.3 既有约束。
5. **把 Google Play In-app Updates 当默认答案：** 在未确认分发渠道前默认接入 Play Core、把“立即升级”写死成 Google Play 流程，属于错误前提。
6. **污染 recent context 成功态：** 展示门闸、点击升级按钮、升级失败或仅落到门闸页时就写入 recent context / 清掉原始 intent，都会破坏恢复真相源。

### Architecture Compliance

- **Client Context & Recovery Contract：** 继续遵守架构要求，客户端最小上下文必须包括 `appVersion`、`platform`、`deviceId`、`intentSource`、`intentId`、`networkState`，且在目标失效、版本不兼容或权限未完成时返回结构化恢复提示。
- **Flutter Mall Shared Stack：** 保持 Provider + Dio + `HttpUtil` + `service_url.dart` 集中式网络模式，不在 `Widget` 里创建私有网络栈。
- **Intent Recovery Loop：** 登录恢复、消息唤回、版本升级、权限授权与弱网重试必须串成一条链，系统门槛完成后优先回到原目标页。
- **Upgrade Gate Placement：** 架构文档已预留 `flutter-mall/lib/layout/app_bootstrap.dart` 与 `upgrade_gate_dialog.dart` 落点；9.5 应在这些共享位置实现，而不是把门闸埋在页面内部。
- **Business Closed-Loop First：** 当前项目架构明确“不做全栈大版本升级”，所以 9.5 的新增依赖、平台改动和接口设计都应服务于版本治理闭环，而不是顺手升级工程骨架。

| 消息 recall 契约 | `rpc/ums/proto/member_message.proto` | 保持 `min_app_version` 向后兼容 |
| 消息模块版本阻断 | `api/front/internal/logic/member/message/recall_intent_helper.go` | 抽共享逻辑，避免只在消息目录生效 |
| 版本策略接口 | `api/front/internal/...`（建议新增） | 独立接口或共享前置校验，不能埋在单页 |
| 升级组件落位 | `flutter-mall/lib/layout/` 或 `flutter-mall/lib/widgets/`（建议新增） | 保持共享组件，不在页面内联实现 |

### Project Context Reference

- 当前项目移动端基线是 Flutter stable + Dart `^3.7.0` + Provider + Dio + `HttpUtil` + `service_url.dart`，这决定了 9.5 应优先在共享层实现版本治理，而不是引入新的状态管理或网络框架。
- 当前项目规则要求与用户沟通、文档和交付默认使用中文，并优先遵循现有生成链和共享 helper；9.5 的接口、proto 或共享模型变更都应改源定义，不手改生成产物。
- 当前项目明确禁止把 handler 当业务编排层，因此 front-api 的升级策略与客户端元数据解析应放在 logic / helper / middleware，而不是散落在 handler。
