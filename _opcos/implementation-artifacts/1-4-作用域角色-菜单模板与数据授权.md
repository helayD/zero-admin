# Story 1.4: 作用域角色、菜单模板与数据授权

Status: ready-for-dev

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a 平台管理员,
I want 为平台级、租户级和商户级角色配置菜单模板、数据范围和关键动作权限,
so that 各类后台用户只看到并操作自己被授权的能力。

## Acceptance Criteria

1. **Given** 平台管理员在角色配置页选择目标主体类型
   **When** 分配菜单模板、数据范围和关键操作权限
   **Then** 权限保存后对对应后台用户即时生效
   **And** 平台、租户、商户三级菜单和数据范围不会串用同一套默认值。
2. **Given** 未被授权的用户访问受保护页面或接口
   **When** 发起列表查询、导出或关键写操作
   **Then** 系统返回明确的权限拒绝结果
   **And** 服务端校验生效，不依赖前端隐藏按钮实现安全控制。

## Dev Notes

### Scope Guardrails

- 本 story 的目标是把现有"全局单空间"的角色 + 菜单 + 数据范围模型升级为"平台/租户/商户三级作用域"的 RBAC 能力，包括菜单模板（限定各级可用菜单范围）、角色作用域绑定（角色归属哪个主体）和数据范围在作用域内的语义重定义。[Source: `_opcos/planning-artifacts/1-new-feature/epic.md#Story-14-作用域角色菜单模板与数据授权`]
- 本 story 不负责：商户入驻审核与主体启停（Story 1.5）、核心业务对象（商品/订单/优惠券等）的作用域隔离（Story 1.6）、治理审计与安全事件检索（Story 1.7）。不要把这些工作打包进"角色与菜单管理"里一并做完。[Source: `_opcos/planning-artifacts/1-new-feature/epic.md`]
- 不要新造平行的 `tenant-role-service` 或 `merchant-role-service`，所有角色治理继续落在 `rpc/sys` 的 `RoleService` 和 `MenuService` 内，通过 scope 字段区分主体级别。[Source: `_opcos/planning-artifacts/1-new-feature/architecture.md#Project-Structure--Boundaries`]
- 菜单模板是"平台管理员为下级主体预配的菜单可用范围"，不是"菜单的完整副本"。租户/商户角色从模板范围内选取菜单，而不是从全量菜单树中自由选取。[Source: `_opcos/planning-artifacts/1-new-feature/prd.md#FR43`; `_opcos/planning-artifacts/1-new-feature/prd.md#FR50`]

### Story Foundation / Business Context

- FR42 要求平台管理员可以统一管理角色和菜单模板；FR43 明确平台可以为三级角色分配可见菜单、数据范围和可执行操作范围；FR50 要求角色和权限作用域按平台/租户/商户定义，并确保后台菜单、数据查询、导出和操作权限与作用域一致。[Source: `_opcos/planning-artifacts/1-new-feature/prd.md#FR42`; `#FR43`; `#FR50`]
- Story 1.3 已经为后台用户、部门、岗位、通知和字典补齐了主体范围和审计上下文；Story 1.4 在此基础上让角色本身也具备主体归属，从而把"用户 + 角色 + 菜单 + 数据范围"这条完整的授权链路全部接入作用域模型。[Source: `_opcos/implementation-artifacts/1-3-后台用户-组织元数据与系统字典管理.md`]
- PRD 的技术成功指标明确要求"高严重级跨主体泄漏缺陷为 0"，因此角色-菜单-数据范围的作用域隔离必须在服务端强制执行，不能只靠前端过滤。[Source: `_opcos/planning-artifacts/1-new-feature/prd.md`]

### Existing Repository Reality

- `sys_role` 表当前没有 `scope_type`、`platform_id`、`tenant_id`、`merchant_id` 或 `is_admin` 字段；`role_name` 有全局唯一约束，这会阻止不同租户创建同名角色。`data_scope` 字段已存在且有 4 种取值（1=全部 2=自定 3=本部门 4=本部门及以下），但其语义是全局的，不区分主体级别。[Source: `script/sql/sys/sys_role.sql`]
- `sys_role_menu` 关联表只有 `role_id` 和 `menu_id`，没有主体范围字段；`sys_user_role` 同样只有 `user_id` 和 `role_id`，没有校验用户和角色是否在同一主体范围内。[Source: `script/sql/sys/sys_role_menu.sql`; `script/sql/sys/sys_user_role.sql`]
- `sys_menu` 表是全量菜单的单一池子，没有 `scope_type` 或菜单可见级别字段；当前所有角色从同一棵菜单树选取权限。仓库中不存在"菜单模板"概念的任何表或代码。[Source: `script/sql/sys/sys_menu.sql`]
- 登录逻辑 `loginlogic.go` 的 `queryApiUrls` 使用裸 SQL 查询 `sys_user_role → sys_role → sys_role_menu → sys_menu`，不带任何主体过滤；`IsAdmin` 判断直接查全量 `background_url`，超级管理员拿到所有菜单的 API 地址。[Source: `rpc/sys/internal/logic/userservice/loginlogic.go:114-135`]
- JWT claims 只有 `userId`、`userName`、`deptID`、`deptName`，没有 scope / tenant / merchant 信息。`CheckUrlMiddleware` 从 Redis `zero:mall:token` 的 `userId` key 取 URL 列表，不理解主体上下文。[Source: `rpc/sys/internal/logic/userservice/loginlogic.go:158-173`; `api/admin/internal/middleware/checkurlmiddleware.go`]
- Web Admin 角色页 `system/role/index.tsx` 当前没有主体类型筛选列，`SetMenuForm.tsx` 直接展示全量菜单树供勾选，`data.d.ts` 的 `RoleListItem` 接口只有 `id/status/roleName/remark/dataScope`。[Source: `web-admin/src/pages/system/role/index.tsx`; `web-admin/src/pages/system/role/components/SetMenuForm.tsx`; `web-admin/src/pages/system/role/data.d.ts`]
- `role.api` 中 `AddRoleReq` 和 `UpdateRoleReq` 均无 scope 相关字段，`QueryRoleListReq` 也只支持 `roleName/roleKey/dataScope/status` 过滤。[Source: `api/admin/doc/api/sys/role.api`]

### Technical Requirements

- 角色表 scope 扩展必须向后兼容：现有角色 id=1（超级管理员）和 id=2（演示角色）必须在 migration 中赋予 `scope_type=platform, platform_id=1`；`is_admin` 字段对 id=1 设为 1。不能让现有角色变成无主体的悬浮记录。[Source: `script/sql/sys/sys_role.sql`]
- JWT claims 扩展必须兼容旧 token：中间件在解析 JWT 时如果发现缺少 scope 字段，应默认 `scope_type=platform, platformId=1`，不能导致旧登录态直接 401。新登录产生的 token 必须包含完整 scope 信息。[Source: `rpc/sys/internal/logic/userservice/loginlogic.go`; `api/admin/internal/middleware/checkurlmiddleware.go`]
- Redis 权限缓存 key 升级需要考虑过渡期：如果直接改 key 结构，已登录用户的缓存会失效。建议登录时同时写新旧两种 key，CheckUrl 优先读新 key、fallback 到旧 key；或在部署时清理 Redis 权限缓存并要求重新登录。[Source: `api/admin/internal/middleware/checkurlmiddleware.go`]
- 菜单模板的设计不应把 `sys_menu` 全表复制一份；建议 `sys_menu_template` 存储 `scope_type` + 模板名 + 允许的 `menu_id` 集合（关联表或 JSON），模板本身是对全量菜单的子集引用。[Source: `_opcos/planning-artifacts/1-new-feature/prd.md#FR43`]
- `data_scope` 字段在新作用域下的语义：
  - `scope_type=platform, data_scope=1`：可看全平台所有主体的数据
  - `scope_type=tenant, data_scope=1`：可看本租户下所有商户的数据
  - `scope_type=merchant, data_scope=1`：可看本商户全部数据
  - `data_scope=3/4`（本部门/本部门及以下）在所有 scope_type 下含义不变，但查询范围受限于当前 scope_type 内的部门树
  - `data_scope=2`（自定数据权限）需要配合 `sys_role_dept` 等关联表；如果当前仓库没有该表，本 story 不需要实现自定数据权限，只需保留字段并在 UI 上标注"待后续实现"
- `queryApiUrls` SQL 改造：在 JOIN 链中增加 `sys_role.scope_type` / `sys_role.tenant_id` / `sys_role.merchant_id` 的过滤条件，或在 login 逻辑中先确定用户的 scope，再只查该 scope 下的角色-菜单关联。[Source: `rpc/sys/internal/logic/userservice/loginlogic.go:126-132`]

### Architecture Compliance

- 继续遵循 `admin-api → rpc/sys → MySQL` 链路，不允许 Web 页面直连数据库或 RPC。[Source: `_opcos/planning-artifacts/1-new-feature/architecture.md#Project-Structure--Boundaries`]
- 网关负责协议转换与错误包装，服务端负责业务编排与数据一致性；角色作用域校验、菜单模板范围限制和数据范围过滤必须在 `logic` / RPC 服务端完成，不能只靠前端过滤或 handler 拦截。[Source: `_opcos/project-context.md`]
- 生成链仍以 `.api`、`.proto`、`rpc/sys/proto/main.go`、`rpc/sys/sys.proto`、`rpc/sys/gen/generator.go` 为源定义入口；不能手改 `routes.go`、`types.go`、`*_pb.go` 或 `rpc/sys/client/**/*` 生成物来实现 scope 扩展。[Source: `_opcos/project-context.md`]
- 对外 JSON 保持 `camelCase`，兼容现有 system 模块的 `current/pageSize` 请求风格和 ProTable 交互。[Source: `api/admin/doc/api/sys/role.api`; `web-admin/src/pages/system/role/index.tsx`]
- 共享能力优先放在 `pkg/scope/` 和 `pkg/audit/`，本 story 新增的 `role_scope.go` 等工具函数应与 Story 1.2 / 1.3 已落地的 `governance.go`、`tenant_admin.go`、`tenant.go` 保持一致的命名风格和导入路径。[Source: `pkg/scope/governance.go`; `pkg/scope/tenant_admin.go`; `pkg/audit/tenant.go`]

### UX / Interaction Requirements

- 角色管理页面需要在列表顶部或筛选区增加"主体类型"选择器（平台级/租户级/商户级），让管理员明确知道当前查看和操作的是哪一级角色。[Source: `_opcos/planning-artifacts/1-new-feature/ux-design.md#Scope-Context-Bar`]
- 创建/编辑角色时，主体类型选择后应联动可选的租户/商户列表和可分配的菜单树（受菜单模板限制）。如果选择"租户级"则必须选择目标租户，菜单树只展示该租户对应模板允许的菜单；如果选择"商户级"则必须选择目标商户。[Source: `_opcos/planning-artifacts/1-new-feature/ux-design.md#Form-Patterns`]
- 分配菜单时，`SetMenuForm.tsx` 的菜单树节点需要根据菜单模板过滤：超出模板范围的菜单节点应隐藏或标记为不可选（disabled + tooltip 提示"超出模板范围"），而不是全量展示让用户误选。[Source: `_opcos/planning-artifacts/1-new-feature/ux-design.md#Component-Strategy`]
- 菜单模板管理页面采用标准 `PageContainer + ProTable + Modal` 模式，创建模板时通过 Tree 组件勾选允许的菜单集合，体验与分配角色菜单一致。[Source: `web-admin/src/pages/system/role/components/SetMenuForm.tsx`; `web-admin/src/pages/system/tenant/index.tsx`]
- 高风险操作（删除角色、修改角色作用域、清空菜单模板）需要 `Consequence Preview`，说明影响的用户数量和权限变更范围。[Source: `_opcos/planning-artifacts/1-new-feature/ux-design.md#Component-Strategy`]
- 权限拒绝反馈必须符合 `Recovery-first Feedback`：指出是"缺少菜单权限""角色作用域不匹配""数据范围不足"等具体原因，不要只返回裸 403 或通用提示。[Source: `_opcos/planning-artifacts/1-new-feature/ux-design.md#Feedback-Patterns`]
