# Story 3.1.1: 手机号验证码登录注册合并

## 状态: ready-for-review

## Story

**As a** 消费者,
**I want** 只用手机号 + 短信验证码就能进入 App，不用记密码，也不用分别走「注册」和「登录」两个入口,
**So that** 我可以在最短路径下进入自己的账户开始购物；已注册账号直接登录，未注册账号在第一次进入时自动建号并立即登录。

## Epic 上下文

**Epic 3: 会员账户、地址与用户资产中心**
本 Story 是对已 done 的 Story 3.1（手机号+密码 注册/登录）的认证模式升级，**完全替换密码登录**，统一为「手机号 + 短信验证码」的合并接口（注册即登录）。

**FRs impacted:** FR8（会员注册/登录基础认证）

**与 Story 3.1 的关系:** 3.1 的 bcrypt 密码、JWT、首登优惠券、登录日志、is_enabled 校验、Flutter 401 意图恢复等基础设施**继续复用**，本 Story 仅在认证入口处替换为验证码模式；JWT claims 结构（`memberId/memberName/mobile`）保持不变，已发放 token 不失效。

## 验收标准

### AC-1: 发送验证码 — 成功
**Given** 消费者输入有效的中国大陆手机号（`^1[3-9]\d{9}$`）
**When** 调用 `POST /api/member/auth/sms/send`
**Then** 服务端通过 `pkg/sms.Sender` 公共接口发送：
  - 当前激活模板 `providerCode=mock` → 验证码**固定为 `123456`**（6 位，前期调试），写入服务端日志 `[MOCK-SMS] mobile=xxx, code=123456`
  - 当前激活模板 `providerCode=aliyun/tencent/...` → 内部 `crypto/rand` 生成 6 位数字验证码，调用对应 SDK 下发
**And** 验证码与对应错误计数写入 Redis（key: `ums:sms:login:{mobile}`，TTL 5 分钟）
**And** 接口返回 `{ code: 0, message: "验证码已发送", data: { expireSeconds: 300 } }`
**And** 响应体**绝不**包含验证码原文（即使 mock 模式）

### AC-2: 发送验证码 — 频控
**Given** 同一手机号 60 秒内多次请求发送验证码
**When** 第二次及以后请求
**Then** 系统返回 `{ code: 1, message: "验证码请求过于频繁，请稍后再试" }`，不真实下发
**And** Redis key `ums:sms:cooldown:{mobile}` 控制 60 秒冷却窗口

### AC-3: 发送验证码 — 手机号格式错误
**Given** 消费者输入非中国大陆手机号格式的字符串
**When** 调用发送接口
**Then** front-api 层直接拦截，返回"手机号格式不正确"，不调用 RPC、不下发短信

### AC-4: 合并接口 — 已注册账号验证码登录
**Given** 数据库 `ums_member_info` 中已存在该手机号的会员记录
**When** 调用 `POST /api/member/auth/login`，传入正确的手机号 + 验证码
**Then** 系统识别为登录场景，返回 JWT 登录态（`{ token, tokenHead: "Bearer", isNewUser: false }`）
**And** Redis 中的验证码被立即消费删除，不允许重复使用
**And** `ums_member_login_log` 写入一条登录日志（IP、login_type=source）
**And** 若 `first_login_status=1` 则异步发送首登优惠券 RabbitMQ 消息（复用 Story 3.1 既有链路）

### AC-5: 合并接口 — 未注册账号自动建号登录
**Given** 数据库中**不存在**该手机号的会员记录
**When** 调用 `POST /api/member/auth/login`，传入手机号 + 正确验证码
**Then** 系统自动创建新会员：
  - `member_id` 通过 Redis `INCR ums:member_id_seq` 生成（复用 Story 3.1 既有机制）
  - `nickname` 自动生成为 `"用户_" + 手机号后4位`（例如 13800138001 → `用户_8001`），若昵称冲突追加 4 位随机数字
  - `password` 字段写入随机生成的 bcrypt 哈希（兼容历史 schema，但不用于认证）
  - `level_id=1`、`is_enabled=1`、`first_login_status=1`、`source` 取请求体 `source`
**And** 返回 JWT 登录态 `{ token, tokenHead: "Bearer", isNewUser: true }`
**And** 异步发送首登优惠券消息（复用 Story 3.1 既有 RabbitMQ 链路）

### AC-6: 合并接口 — 验证码错误
**Given** 消费者输入手机号正确但验证码错误
**When** 调用合并接口
**Then** 系统返回"验证码错误或已过期"，不创建账号、不返回 token
**And** Redis 中的验证码**不被消费**（保留剩余尝试机会），但累计错误次数超过 5 次则强制删除并要求重新获取

### AC-7: 合并接口 — 验证码已过期
**Given** Redis 中该手机号的验证码 key 已过期或不存在
**When** 调用合并接口
**Then** 系统返回"验证码错误或已过期"，提示用户重新获取

### AC-8: 合并接口 — 账号禁用拦截
**Given** 已存在的会员记录 `is_enabled=0`（被禁用）
**When** 验证码正确，但调用合并接口尝试登录
**Then** 系统返回"账号已被禁用，请联系客服"，不返回 token
**And** 验证码仍被消费（避免被遍历探测）

### AC-9: 旧密码接口直接下线
**Given** 旧 `POST /api/member/login`（密码登录）与 `POST /api/member/register` 接口
**When** Story 3.1.1 上线
**Then** 旧两个接口**直接下线**，不保留兼容窗口：
  - `routes.go` 中删除旧路由注册
  - 删除 `login_handler.go` / `register_handler.go` 文件
  - 删除 `login_logic.go` / `register_logic.go` 文件
  - 删除对应 `*_test.go` 单测文件
  - RPC 层 `Login(LoginReq)` 与 `Register(RegisterReq)` 方法可保留 proto 定义（不破坏向后二进制兼容），但 front-api 不再调用
**And** Flutter 端不再保留任何指向旧接口的代码（service_url.dart 中删除 `loginUrl` `registerDataUrl` 常量）

### AC-10: Flutter 移动端验证码登录流程
**Given** 消费者打开 Flutter 登录页（`flutter-mall/lib/view/mine/login/login.dart`）
**When** 输入手机号 → 点击「获取验证码」按钮 → 60 秒倒计时启动 → 输入收到的 6 位验证码 → 点击「登录」
**Then** App 通过 `HttpUtil.post('/api/member/auth/sms/send')` 发送验证码请求，倒计时期间按钮禁用
**And** 然后通过 `HttpUtil.post('/api/member/auth/login')` 提交手机号+验证码，成功后将 `Bearer <token>` 存入 SharedPreferences 并执行登录后路由恢复（复用 Story 3.1 的 redirectRoute 机制）

### AC-11: Flutter 注册页下线
**Given** Story 3.1 引入的独立注册页 `flutter-mall/lib/view/mine/login/register.dart`
**When** Story 3.1.1 上线
**Then** 删除 `register.dart` 文件
**And** `login.dart` 移除「还没有账号？立即注册」入口
**And** `service_url.dart` 移除 `registerDataUrl` 常量
**And** 登录页页眉文案改为"输入手机号即可登录，未注册手机号将自动创建账号"

### AC-12: 验证码输入校验
**Given** 消费者在 Flutter 端输入验证码
**When** 验证码不是 6 位纯数字
**Then** 前端拦截不提交，输入框下方显示红色错误提示「请输入 6 位验证码」

## 任务与子任务

### 任务 1: 公共 SMS 抽象层 — 新建 `pkg/sms` 包 [backend-shared]

本任务是**全项目共享基础设施**，不限于会员登录场景。后续物流通知、订单提醒、密码找回等任何短信发送需求均必须复用本包，禁止任何业务模块绕过本包直接调用第三方 SDK。

#### 1.1 包结构与接口定义
- **包路径**: `pkg/sms/`（与 `pkg/antchain`、`pkg/fisco`、`pkg/chainclient` 同级）
- **文件结构**:
  ```
  pkg/sms/
    ├── doc.go              # 包文档
    ├── types.go            # Scene/Result/Config 类型定义
    ├── sender.go           # Sender 接口（业务层调用入口）
    ├── provider.go         # Provider 接口（供应商实现入口）
    ├── registry.go         # Provider 注册中心
    ├── mock.go             # MockProvider 实现（固定 1234）
    ├── default_sender.go   # 默认 Sender 实现（路由到 Provider）
    └── *_test.go           # 单元测试
  ```
- **核心接口**:
  ```go
  // Scene 短信场景枚举
  type Scene string
  const (
      SceneMemberLogin Scene = "member_login"
      // 预留扩展: SceneOrderShipped / SceneSecurityAlert / SceneRealName
  )

  // SendResult Sender 返回值，code 是实际生成并发出的验证码（业务侧写 Redis 用）
  type SendResult struct {
      Code          string  // 实际下发的验证码（mock=1234，aliyun=随机6位）
      ExpireSeconds int     // 过期秒数（默认 300）
      ProviderCode  string  // 实际使用的 provider（用于审计）
  }

  // Sender 业务层使用的统一发送入口
  type Sender interface {
      Send(ctx context.Context, mobile string, scene Scene) (*SendResult, error)
  }

  // Config 通过 sys-rpc 从 sys_channel_integration_template 取出的运行时配置
  type Config struct {
      ProviderCode   string  // mock / aliyun / tencent
      SignName       string  // 阿里云签名
      TemplateCode   string  // 阿里云模板
      CredentialRef  string  // 秘钥引用，格式 credential://xxx 或 ref:env:ALIYUN_AK
      TimeoutSeconds int
      ExpireSeconds  int     // 验证码 TTL，默认 300
  }

  // Provider 供应商实现入口，每个真实网关实现一个
  type Provider interface {
      Code() string
      Send(ctx context.Context, mobile string, scene Scene, cfg Config) (*SendResult, error)
  }

  // ConfigResolver 由调用方注入，从 sys-rpc 拉取激活模板
  type ConfigResolver interface {
      Resolve(ctx context.Context, scene Scene) (Config, error)
  }
  ```

#### 1.2 MockProvider 实现（前期调试默认）
- **文件**: `pkg/sms/mock.go`
- **行为**:
  - `Code() string` 返回 `"mock"`
  - `Send(ctx, mobile, scene, cfg)`：
    - 验证码**固定为 `"123456"`**（6 位，与生产 provider 一致，前期调试用）
    - `logc.Infof(ctx, "[MOCK-SMS] mobile=%s, scene=%s, code=123456", mobile, scene)`
    - 不调用任何外部网关，不引入任何外部 SDK
    - 返回 `SendResult{Code: "123456", ExpireSeconds: cfg.ExpireSeconds, ProviderCode: "mock"}`
- **安全约束**: 该实现**仅供开发/测试环境**。生产环境通过 `sys_channel_integration_template.status=enabled` 的模板控制实际激活的 Provider，不能在生产环境激活 `providerCode=mock` 的模板（运维约束，通过审计告警实现，本 story 不做强制阻断）。

#### 1.3 Registry 与 DefaultSender
- **`registry.go`**: 进程级 Provider 注册中心
  ```go
  var registry = map[string]Provider{}
  func RegisterProvider(p Provider) { registry[p.Code()] = p }
  func ProviderOf(code string) (Provider, bool) { p, ok := registry[code]; return p, ok }
  ```
- **`default_sender.go`**: Sender 默认实现
  ```go
  type defaultSender struct { resolver ConfigResolver }
  func NewSender(resolver ConfigResolver) Sender { ... }
  func (s *defaultSender) Send(ctx, mobile, scene) (*SendResult, error) {
      cfg := s.resolver.Resolve(ctx, scene)
      p := registry[cfg.ProviderCode]
      return p.Send(ctx, mobile, scene, cfg)
  }
  ```
- **init**: `pkg/sms/mock.go` 的 `init()` 自动注册 MockProvider，未来 `pkg/sms/aliyun.go` 同样自动注册

#### 1.5 RPC 新增 `SendSmsCode` 方法
- **proto 修改**: `rpc/ums/ums.proto`（手动编写，严禁 goctl 生成）
  ```proto
  rpc SendSmsCode(SendSmsCodeReq) returns (SendSmsCodeResp);

  message SendSmsCodeReq {
      string mobile = 1;
      int32 scene = 2;   // 1=login, 预留其他场景
  }
  message SendSmsCodeResp {

  ```
- **Logic 文件**: `rpc/ums/internal/logic/memberinfoservice/sendsmscodelogic.go`（新增，手写）
  - 校验冷却 key `ums:sms:cooldown:{mobile}`（60s TTL）— Redis Setnx，已存在则返回频控错误

- **client/server stub**: 在 `rpc/ums/umsclient/`、`rpc/ums/internal/server/memberinfoservice/` 中**手动追加**新方法封装（参照同模块既有方法风格，禁止 protoc 全量再生成）

  - `rpc/ums/internal/server/memberinfoservice/send_sms_code_service_server.go`（新增）

#### 1.6 RPC 新增 `LoginByCode` 方法
- **proto 追加**:
  ```proto
  rpc LoginByCode(LoginByCodeReq) returns (LoginByCodeResp);

  message LoginByCodeReq {
      string mobile = 1;
      string code = 2;
      int32 source = 3;
      string ip = 4;
  }
  message LoginByCodeResp {
      string token = 1;
      bool isNewUser = 2;
      int64 memberId = 3;
  }
  ```
- **Logic 文件**: `rpc/ums/internal/logic/memberinfoservice/loginbycodelogic.go`（新增，手写）
- **流程**:
  1. 从 Redis 读取 `ums:sms:login:{mobile}`，按 `:` 分割得到 `code` 和 `errCount`
  2. key 不存在 → 返回 `errors.New("验证码错误或已过期")`
  3. code 不匹配：
     - 自增 `errCount`，回写 key（保留原 TTL）
     - 若 `errCount >= 5`，Del key
     - 返回"验证码错误或已过期"
  4. code 匹配：立即 `Del` key（一次性）
  5. 查询 `ums_member_info` by mobile：
     - 命中且 `is_enabled=0` → 返回"账号已被禁用，请联系客服"
     - 命中且 `is_enabled=1` → 走登录分支：写登录日志、首登优惠券（复用既有逻辑）、生成 JWT、返回 `isNewUser=false`
     - 未命中 → 走自动建号分支：
       - `member_id` 来自 Redis INCR
       - `nickname = "用户_" + mobile[-4:]`，冲突追加 4 位随机数
       - `password` 写入 `bcrypt.GenerateFromPassword([]byte(uuid.NewString()), bcrypt.DefaultCost)` 随机哈希
       - 插入会员，写登录日志，发送首登优惠券，生成 JWT，返回 `isNewUser=true`
- **复用既有代码**:
  - JWT 生成：`createtoken.go` 既有 `CreateToken`
  - 写登录日志、首登优惠券消息：抽取 `loginlogic.go` 中现有逻辑为内部公共方法 `(l *baseLogic) postLoginActions(ctx, member, ip, source) error`（**重构提示**：可在本 story 中把这部分提取为 `memberinfoservice/login_common.go`，供 `loginlogic.go` 和 `loginbycodelogic.go` 共享，避免重复）
- **涉及文件**:
  - `rpc/ums/ums.proto`
  - `rpc/ums/umsclient/*`（手动追加）
  - `rpc/ums/internal/logic/memberinfoservice/loginbycodelogic.go`（新增）
  - `rpc/ums/internal/logic/memberinfoservice/login_common.go`（新增，公共方法）
  - `rpc/ums/internal/server/memberinfoservice/login_by_code_service_server.go`（新增）

## 开发说明

### 架构约束

| 约束项 | 说明 |
|--------|------|
| **API 边界** | Flutter 仅访问 `front-api`，绝不直接打 RPC |
| **通信链路** | `flutter-mall → front-api → ums-rpc → (内部) sys-rpc(ChannelIntegrationTemplate) + pkg/sms` |
| **认证方式** | 全站统一为「手机号 + 短信验证码」，密码字段在表中保留但不再用于认证 |
| **SMS 抽象** | 所有短信发送**必须**走 `pkg/sms.Sender`，禁止业务模块直接 import 第三方 SDK；新增供应商通过 `pkg/sms.RegisterProvider` 接入 |
| **配置真相源** | SMS 网关配置**唯一**来自 `sys_channel_integration_template` 中 `target_code='sms_provider' AND status='enabled'` 的模板；禁止在 yaml/env 中重复配置 |
| **秘钥规范** | 模板 `credential_refs_json` 只存引用前缀（`credential://` / `secret://` / `vault://` / `kms://` / `ref:env:XXX`），禁止明文 AK/SK；mock 模板不需要任何凭据 |
| **JWT 兼容** | JWT claims 结构（`memberId/memberName/mobile`）保持不变，已发放 token 不失效；旧 RPC `Login`/`Register` 方法保留但 front-api 不再调用 |
| **Redis key 规范** | 验证码 `ums:sms:login:{mobile}` TTL 5min；冷却 `ums:sms:cooldown:{mobile}` TTL 60s；会员 ID 序列 `ums:member_id_seq`（复用 3.1） |
| **错误响应一致性** | 所有业务失败统一 `errorx.NewDefaultError`，不混用 `{code:1}` |
| **日志安全** | 验证码 mock 日志在 dev 环境可见，生产环境的 SmsSender 实现**禁止打印验证码原文** |
| **生成代码** | 严禁运行 `goctl api go` 或 `protoc` 重新全量生成；types.go、pb.go、smsclient 仅手动追加新增方法 |
| **频控** | 同手机号 60s 内只能发送一次验证码；同手机号验证码错误 5 次锁定，需重新获取 |

**复用 `ums_member_info`**（无 schema 变更）：

**复用 `ums_member_login_log`**（无 schema 变更）：

### Redis Key 设计

| Key | 类型 | TTL | 说明 |
|-----|------|-----|------|
| `ums:sms:login:{mobile}` | string `{code}:{errCount}` | 300s | 验证码 + 错误计数 |
| `ums:sms:cooldown:{mobile}` | string `1` | 60s | 发送冷却窗口 |
| `ums:member_id_seq` | int | 永久 | 会员 ID 自增（复用 Story 3.1） |

## 关键风险与防护

| 风险 | 防护措施 |
|------|----------|
| Mock 验证码生产环境泄漏 | Mock 模式由 DB 模板 `status='enabled'` 控制激活，运维上线前必须改为真实 provider；`pkg/sms.MockProvider` 仅日志输出验证码，response body **永远**不含 code 原文 |
| SMS 配置真相源分裂 | 严禁在 yaml/env 中重复配置 provider 字段；唯一真相源是 `sys_channel_integration_template`；ConfigResolver 加 30s 内存缓存避免 RPC 风暴 |
| 8.6 模板治理边界冲突 | 本 story 仅消费 8.6 已建好的模板表，**不修改** 8.6 的模板治理 CRUD 逻辑；如需扩展模板字段必须通过 8.6 后续迭代 |
| 验证码暴力破解 | 错误 5 次锁定 key；冷却 60s；验证码 6 位数字熵约 20bit，配合 5 次锁定足够 |
| 自动建号被滥用 | 60s 冷却 + 5 次错误锁定可缓解；后续可在 Story 中接入图形验证码或滑块（非本 story 范围） |
| 已发放 JWT 失效 | 严禁修改 JWT claims 结构和签名密钥；token 验证逻辑不变 |
| 旧密码登录接口残留 | 任务 4 在本 story 中直接删除 front-api 层路由、handler、logic、types 和 .api 定义；RPC 层 proto 保留以不破坏二进制兼容，但 front-api 不再引用。编译验证 `go build ./api/front/...` 作为验收門槛 |
| 昵称冲突 | "用户_"+手机号后4位仍可能撞库（虽小概率），冲突时追加 4 位随机数字 |
| Redis 异常导致登录不可用 | RPC 层对 Redis Get/Setnx 失败要返回明确错误，不静默通过 |
| protoc/goctl 误用 | **严格禁止**运行任何自动生成命令；所有新增方法手动追加到生成文件相关位置，参照同模块既有方法风格 |
