# Story 1.2: 租户创建与管理员初始化

Status: review

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a 平台管理员,
I want 创建租户并初始化首个租户管理员,
so that 新租户可以在不依赖研发脚本的情况下正式进入平台经营体系。

## Acceptance Criteria

1. **Given** 平台管理员拥有租户治理权限
   **When** 提交租户基础资料、可用渠道、数据保留策略和业务开关
   **Then** 系统创建租户主体并生成唯一租户标识
   **And** 初始化首个租户管理员账号、默认作用域和开通审计记录。
2. **Given** 新建租户被停用或归档
   **When** 平台管理员执行启停或归档动作
   **Then** 主体状态在后台查询与监控面板中 1 分钟内可见
   **And** 相关变更保留可追踪的操作人与时间信息。

## Tasks / Subtasks

- [x] 1. 建立租户主体与生命周期源定义（AC: 1, 2）
  - [x] 在 `script/sql/sys/` 新增租户主体与生命周期相关 SQL 源定义，延续 `sys_*` 命名并包含唯一租户标识、状态字段、渠道配置、数据保留策略、业务开关、`created_by` / `updated_by` / `created_at` / `updated_at`
  - [x] 在 `rpc/sys/proto/` 补充租户创建、查询、启用、停用、归档与首个管理员初始化所需的 proto 定义，并在需要时同步更新 `api/admin/doc/api/sys/*.api`
  - [x] 如涉及生成链变更，只修改 `.api`、`.proto`、`rpc/sys/gen/generator.go` 与 SQL 源定义，不手改 `pb`、`query`、`routes.go`、`types.go`
- [x] 2. 实现平台端租户创建与状态流转编排（AC: 1, 2）
  - [x] 在 `api/admin/internal/logic/sys` 与 `rpc/sys/internal/logic` 中实现租户创建、详情、列表和状态变更编排，保持 `handler -> logic -> svc` 结构
  - [x] 创建流程必须一次性落租户主体、唯一租户标识、操作人/时间、默认生命周期状态，并返回后续治理可用的主键/标识信息
  - [x] 启用、停用、归档动作必须把状态变化写入持久化真相源，并确保后台查询路径和后续监控消费链可在 1 分钟内读到一致状态
- [x] 3. 初始化首个租户管理员与默认作用域元数据（AC: 1）
  - [x] 优先复用现有 `sys_user`、`sys_role`、`sys_user_role`、`sys_menu` 与 `data_scope` 语义，不单独再造一套租户后台账号体系
  - [x] 为首个租户管理员建立明确的租户绑定、默认作用域元数据和开通审计记录，并保证重复提交不会生成脏账号/脏绑定
  - [x] 在 Story 1.4 / 1.6 完成前，不要直接赋予该管理员平台级全量菜单或跨租户数据访问；若完整权限模板尚未就绪，应使用受控的 bootstrap / pending-activation 状态
- [x] 4. 扩展最小必要的鉴权、作用域与审计上下文（AC: 1, 2）
  - [x] 如创建链路需要补充 claim 或上下文字段，应在现有 admin JWT 与中间件链上做最小增量扩展，落点优先为 `rpc/sys/internal/logic/userservice/loginlogic.go`、`api/admin/internal/middleware/checkurlmiddleware.go`、`api/admin/internal/middleware/addloglmiddleware.go`
  - [x] 如本 story 需要提前引入共享 helper，可最小化落地 `pkg/scope` / `pkg/audit`，但只覆盖租户创建与审计链路，不在本 story 内完成全域作用域改造
  - [x] 不把 JWT 三方库迁移、全量 RBAC 重构或跨域数据隔离改造混入本 story；若必须触及 JWT，保持与当前仓库实现一致或拆成独立受控变更
- [x] 5. 交付后台治理入口与租户创建交互（AC: 1, 2）
  - [x] 在 `web-admin/src/pages/system` 下新增租户治理页面，沿用 `index.tsx + service.ts + data.d.ts + components/*` 模式，并通过现有 `request` / `/api/` 代理访问 `admin-api`
  - [x] 表单与列表交互需要覆盖租户基础资料、可用渠道、保留策略、业务开关、首个管理员初始化信息，以及启用/停用/归档动作
  - [x] 页面体验应体现 UX 文档中的 `Scope Context Bar`、`Consequence Preview`、`Recovery-first Feedback`，并在成功态给出下一步治理动作提示
- [x] 6. 补充验证与回归覆盖（AC: 1, 2）
  - [x] 为 `rpc/sys` / `admin-api` 增加针对唯一租户标识、重复管理员初始化、状态流转、审计落库、查询过滤与权限拒绝的测试
  - [x] 验证现有系统用户登录、角色菜单授权和 `system/user|role|menu|dept|dict|post` 页面不因租户治理接入而回归
  - [x] 若监控面板本体尚未在本 story 内交付，至少验证状态与审计事件已经以稳定字段落库/出站，供 Story 7.5 直接消费

## Dev Notes

### Scope Guardrails

- 本 story 的目标是“创建租户 + 初始化首个租户管理员 + 持久化生命周期与审计上下文”，不是一次性完成整套多租户隔离、角色模板中心、监控大盘或跨域治理改造。[Source: `_opcos/planning-artifacts/1-new-feature/epic.md#Story-12-租户创建与管理员初始化`]
- Epic 对 Story 1.2 的主 FR 覆盖是 `FR46`；但为了满足 acceptance criteria 中的默认作用域、可追踪审计和 1 分钟可见性，本 story 需要为后续 `FR44`、`FR47`、`FR50`、`FR52` 预埋稳定的生命周期与审计数据，而不是提前把这些 story 全做完。[Source: `_opcos/planning-artifacts/1-new-feature/epic.md`; `_opcos/planning-artifacts/1-new-feature/prd.md`]
- 禁止把“租户创建”落成研发脚本、一次性 SQL 手工操作或新的独立平台后台；入口必须仍在既有 `admin-api + web-admin system 域` 内。[Source: `_opcos/planning-artifacts/1-new-feature/prd.md`; `_opcos/planning-artifacts/1-new-feature/architecture.md#Project-Structure--Boundaries`]

### Story Foundation / Business Context

- 平台管理员需要在后台直接提交租户基础资料、渠道、保留策略和业务开关，并同步开通首个租户管理员，避免依赖线下脚本或研发介入。[Source: `_opcos/planning-artifacts/1-new-feature/epic.md#Story-12-租户创建与管理员初始化`; `_opcos/planning-artifacts/1-new-feature/prd.md`]
- 停用或归档后的租户状态必须在后台查询与监控视图中 1 分钟内可见，因此本 story 的状态字段、审计字段和事件输出必须从一开始就采用稳定结构。[Source: `_opcos/planning-artifacts/1-new-feature/epic.md#Story-12-租户创建与管理员初始化`; `_opcos/planning-artifacts/1-new-feature/prd.md`]
- UX 已把平台治理流定义为“平台控制台工作台 -> 创建租户 -> 初始化租户管理员 -> 后续商户治理/授权/审计查看”，因此成功页和失败反馈都应服务这条主体流，而不是只做一个孤立表单。[Source: `_opcos/planning-artifacts/1-new-feature/ux-design.md#平台开通与商户治理流`]

### Existing Repository Reality

- 当前 `sys` 域只存在用户、角色、菜单、部门、岗位、字典、登录日志、操作日志等治理源文件；还没有租户实体、租户 API 或租户 proto 定义，因此 Story 1.2 需要从现有 `sys` 结构内增量扩展，而不是假设仓库已经具备多租户骨架。[Source: `script/sql/sys/`; `api/admin/doc/api/sys/`; `rpc/sys/proto/`]
- 当前 Web Admin 的 `system` 路由仅覆盖 `user`、`role`、`menu`、`dept`、`dict`、`post`，没有租户治理页面；新入口应在既有 `system` 域下扩展，而不是再开一个平行后台信息架构。[Source: `web-admin/config/routes.ts`]
- 当前 admin 登录要求用户已经具备角色/菜单 URL 权限，JWT claims 只有 `userId`、`userName`、`deptID`、`deptName`。这意味着“首个租户管理员初始化”不能简单理解为插入一条用户记录；还必须考虑菜单权限来源、登录可用性和受控开通状态。[Source: `rpc/sys/internal/logic/userservice/loginlogic.go`; `api/admin/internal/middleware/checkurlmiddleware.go`]
- 当前操作日志中间件只读取 `userName` 和 `deptName`，还不是作用域感知的审计上下文。因此如果本 story 要求保留租户开通/停用/归档可追踪信息，需要显式补充租户维度或复用统一审计 helper，而不是假设现有日志已经天然满足需求。[Source: `api/admin/internal/middleware/addloglmiddleware.go`; `_opcos/planning-artifacts/1-new-feature/architecture.md#Authentication--Security`]
- 架构文档规划了 `pkg/scope`、`pkg/audit` 和作用域中间件，但当前仓库的 `pkg/` 只有基础工具包，尚未落地这些平台化共享能力；本 story 若引入它们，应保持最小可用范围，避免在一个 story 内把整套 scope 基础设施全部铺完。[Source: `_opcos/planning-artifacts/1-new-feature/architecture.md#Project-Structure--Boundaries`; `pkg/`]

### Technical Requirements

- 租户主体设计必须延续现有 `sys_*` 命名风格，并显式携带生命周期、操作人和审计字段；不要为平台治理再引入第二套命名体系或“tenant-center”平行表前缀。[Source: `_opcos/planning-artifacts/1-new-feature/architecture.md#Data-Architecture`; `_opcos/planning-artifacts/1-new-feature/architecture.md#Implementation-Patterns--Consistency-Rules`]
- 新增平台化实体必须采用统一作用域字段命名：`platform_id`、`tenant_id`、`merchant_id`；审计字段统一使用 `created_by`、`updated_by`、`created_at`、`updated_at`。[Source: `_opcos/planning-artifacts/1-new-feature/architecture.md#Data-Architecture`; `_opcos/planning-artifacts/1-new-feature/architecture.md#Implementation-Patterns--Consistency-Rules`]
- 后端实现仍需经过 `admin-api -> rpc/sys` 链路完成。网关负责请求解析与权限上下文，`logic` 层负责租户创建/状态流转编排，不能把业务逻辑塞进 `handler` 或前端脚本里。[Source: `_opcos/project-context.md`; `_opcos/planning-artifacts/1-new-feature/architecture.md#Project-Structure--Boundaries`]
- 数据真相源仍是 MySQL；Redis 可以参与登录态、缓存或幂等键，但不能成为租户状态的唯一判断依据。[Source: `_opcos/planning-artifacts/1-new-feature/architecture.md#Data-Architecture`]
- 若需要幂等或审计事件，请沿现有生成链和共享包约定落地，不要手写绕过 `gorm/gen`、绕过 RPC 或把核心状态只写到日志系统。[Source: `_opcos/planning-artifacts/1-new-feature/architecture.md#Data-Architecture`; `_opcos/project-context.md`]
- Story 1.2 可以为后续 Story 1.4 / 1.6 留下 default scope metadata、bootstrap 状态或最小角色模板绑定，但不应在这里一次性完成全量租户级 RBAC、菜单模板中心和跨域数据隔离。[Source: `_opcos/planning-artifacts/1-new-feature/epic.md`; `_opcos/planning-artifacts/1-new-feature/prd.md`]

### Architecture Compliance

- 保持现有 REST gateway + gRPC service 拓扑，不新增第二套路由命名空间，也不要让前端直接访问 RPC 层。[Source: `_opcos/planning-artifacts/1-new-feature/architecture.md#Project-Structure--Boundaries`]
- 对外 JSON 字段继续使用 `camelCase`，分页与列表交互沿用现有 `pageNum` / `pageSize` 风格；如果 proto 使用 `snake_case`，在网关层完成映射。[Source: `_opcos/planning-artifacts/1-new-feature/architecture.md#Implementation-Patterns--Consistency-Rules`]
- 架构已把 `pkg/scope`、`pkg/audit`、`api/*/internal/middleware/scope.go` 列为平台化治理首批落点；Story 1.2 若实现其中任意一项，应聚焦租户开通链路，不要顺手扩散到 `oms/pms/sms/cms/ums` 全域查询写入校验。[Source: `_opcos/planning-artifacts/1-new-feature/architecture.md#Requirements-to-Structure-Mapping`; `_opcos/planning-artifacts/1-new-feature/architecture.md#Completion-Summary--Next-Workflow-Recommendations`]
- 当前系统登录仍依赖旧 JWT 库与现有 claims 结构。若本 story 需要 tenant context，优先做兼容性扩展；不要在没有专门迁移 story 的情况下同时切换 JWT 库、重写鉴权中间件和替换登录协议。[Source: `rpc/sys/internal/logic/userservice/loginlogic.go`; [golang-jwt releases](https://github.com/golang-jwt/jwt/releases/tag/v5.3.0)]

### UX / Interaction Requirements

- 租户治理页面应遵循 UX 的平台主体流，让管理员在同一条治理路径内完成“建租户 -> 初始化管理员 -> 查看状态/下一步动作”，而不是跳到脚本、外部后台或多个无上下文页面。[Source: `_opcos/planning-artifacts/1-new-feature/ux-design.md#平台开通与商户治理流`]
- 高风险操作页头应展示 `Scope Context Bar`，明确当前平台主体、影响范围和可执行动作；切换、停用或归档动作时需要明确的主体上下文提示。[Source: `_opcos/planning-artifacts/1-new-feature/ux-design.md#Scope-Context-Bar`]
- 提交前需要有 `Consequence Preview`，说明本次操作将创建哪些主体、默认管理员和状态变更；失败反馈必须符合 `Recovery-first Feedback`，给出修复动作和可回退线索，而不是只吐一个错误码。[Source: `_opcos/planning-artifacts/1-new-feature/ux-design.md`]
- Web 组件优先复用 `PageContainer`、`ProTable`、`ProForm`、`Drawer`、`Modal`、`Descriptions`、`Tag`、`Result` 等既有基础组件，不要为了租户治理单独引入新组件栈。[Source: `_opcos/planning-artifacts/1-new-feature/ux-design.md#Component-Strategy`]
