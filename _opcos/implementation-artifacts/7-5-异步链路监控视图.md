# Story 7.5: 异步链路监控视图

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a 技术运营人员,
I want 统一查看搜索同步、支付回调、补偿任务和主体治理事件的链路状态,
So that 我可以在异常影响用户之前快速发现问题。

## Acceptance Criteria

1. **Given** 技术运营进入链路监控视图 **When** 按租户、商户、链路类型和时间筛选 **Then** 系统展示状态、失败原因、重试次数、最近执行时间和处理结果 **And** 支持区分同步中、失败、延迟和需人工处理状态。

2. **Given** 某条链路进入异常状态 **When** 监控阈值被触发 **Then** 系统生成告警或明显状态提示 **And** 告警信息可关联到具体 `traceId` 或业务对象。

    StageUnknown         int32 = 0
    StagePending         int32 = 1  // 待处理

// ConsistencyResult（复用自7.3B）
const (
    ResultUnknown        int32 = 0

#### Task 9: NFR12 验收检查清单

**NFR12 要求："关键异步链路在 1 分钟内识别失败状态，10 分钟内完成自动重试或进入人工介入队列"**

| 检查项 | 实现要求 | 验证方式 |
|-------|---------|---------|
| 失败识别延迟 | Job/Consumer 失败后，监控视图最迟 1 分钟可见 | 观察 Job 日志时间 vs 监控视图 LastExecuteAt |
| 自动重试频率 | Job 每 1 分钟扫描一次，失败后下次扫描自动重试 | Job Cron 配置 = `*/1 * * * *` |
| 人工介入阈值 | `retryCount >= 3` 自动标记 `manualRequired=true` | 7.4 已实现 |
| 人工介入可见 | `manualRequired=true` 的订单必须出现在监控视图 | Task 4 已要求 |
| 监控视图延迟 | 补偿链路状态变化后，监控视图最多 1 分钟刷新可见 | admin-api 列表查询延迟 |

- [ ] 9.1 确认 Job 超时扫描 Cron 频率 = `*/1 * * * *`
- [ ] 9.2 确认 `retryCount >= 3` → `manualRequired=true` 逻辑在 Job 和 Consumer 中均已实现
- [ ] 9.3 确认监控视图的列表查询**不需要**人工刷新，最迟 1 分钟内可见最新状态

## Dev Notes

### 架构约束与边界（继承自 Epic 7 + Architecture）

**约束 1：必须复用 7.3B 的一致性阶段模型，禁止发明第四套状态语义**

- `ConsistencyStage` / `ConsistencyResult` 是订单权益一致性的唯一语义
- 监控视图中的补偿链路状态必须复用这些字段，**不能**发明新枚举
- 其他链路（搜索同步/支付回调）使用等价 `stage`/`result` 表达，不强制要求枚举值一致

**约束 2：traceId 是链路追踪的唯一入口**

- 所有链路入口必须生成并持久化 `traceId`
- 监控视图的详情必须能通过 `traceId` 关联到完整日志
- **禁止**：只在日志中打印 traceId 但不持久化到可查询载体

**约束 3：主体范围是强制过滤条件**

- 所有链路查询必须强制带上 `platformId/tenantId/merchantId`
- 禁止在监控视图中展示跨租户/跨商户的链路数据

**约束 4：Flutter 不是监控视图的承载端**

- 7.5 的监控视图是**运营侧**需求，由 web-admin 承载
- Flutter 只需要展示"自己订单的补偿状态"，不需要完整的链路监控能力

**约束 5：NFR12 是验收硬约束，不是可选项**

- 1 分钟内识别失败 → Job 每 1 分钟扫描一次，失败状态必须持久化
- 10 分钟内进入人工介入 → `retryCount >= 3` 自动标记 `manualRequired=true`
