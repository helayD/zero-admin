# Story 7.4: 超时订单关闭与资源补偿

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a 技术运营人员,
I want 在订单超时、支付异常或交易取消时自动执行补偿,
So that 库存、优惠券、积分和订单状态不会长期不一致。

## Acceptance Criteria

1. **Given** 订单在配置超时时间内未完成支付 **When** 超时任务触发 **Then** 系统自动关闭订单 **And** 触发库存释放、优惠券回退和积分返还链路。

2. **Given** 补偿任务执行失败 **When** 技术运营查看补偿状态 **Then** 系统记录失败原因，重试次数和最近执行时间 **And** 将异常任务送入人工介入队列。

### 二、为 job 超时补偿添加幂等保护

> **核心原则：** 7.3B 的 consumer `OrderDelayCancel` 已通过 Redis key 实现了幂等。7.4 **必须**复用同一套幂等语义。

**必须复用的幂等模式（来自 7.3B）：**
- Redis key：`order:cancel:compensation:{orderId}`
- TTL：`86400` 秒（1天）
- 三状态：`processing` → `completed` 或 `failed`
- 使用 `SetnxExCtx` 实现

**Redis 幂等实现代码参考：**

```go
const (
    cancelCompensationKeyPrefix = "order:cancel:compensation:"
    cancelCompensationTTL       = 86400  // 1天
)

idempotentKey := fmt.Sprintf("%s%d", cancelCompensationKeyPrefix, orderId)
set, err := rds.SetnxExCtx(ctx, idempotentKey, "processing", cancelCompensationTTL)
if err != nil {
    return err
}
if !set {
    logc.Infof(ctx, "取消补偿幂等命中 orderId=%d，已处理过，跳过", orderId)
    return nil
}
```

- [x] 3.1 在 `job/internal/svc/service_context.go` 中初始化 Redis 客户端（参考 consumer 的初始化方式）
- [x] 3.2 把幂等逻辑添加到 `cancel_timeout_order_logic.go`
- [x] 3.3 **幂等状态流转：**
  - `processing` → `completed`（成功）
  - `processing` → 保留（失败时 key 不过期，下次扫描可重试）
- [x] 3.4 **关键约束：** job 和 consumer 的超时取消**必须**使用完全相同的 Redis key 前缀和 TTL

### 五、为失败补偿提供可见性与人工介入队列

> **NFR11 要求：** "超时未支付订单必须在配置超时时间到达后的 5 分钟内自动关闭"。

**NFR11 实现策略：**

1. **扫描频率保证：** job 每 `1` 分钟扫描一次，`NormalOrderOvertime` 通常为 `30` 分钟（用户可配置），因此超时订单会在 `1~2` 分钟内被发现
2. **补偿链路性能：** 串行执行 CancelOrder → ReleaseStock → UpdateCoupon → UpdatePoints，预计 `500ms~2s` 完成
3. **失败重试策略：**
   - `RetryCount < 3`：下次扫描时自动重试
   - `RetryCount >= 3`：标记 `ManualRequired = true`，进入人工介入队列
4. **5 分钟 SLA 验证：** 从 `超时时间点 + 1分钟扫描延迟 + 2秒补偿执行 = 1~3 分钟`，远低于 5 分钟要求

**人工介入队列实现：**

```go
// 当 RetryCount >= 3 时，设置 ManualRequired
if retryCount >= 3 {
    manualRequired = true
    logc.Errorf(ctx, "订单 %d 补偿失败超过 3 次, 请人工介入", orderId)
}
// ManualRequired = true 的订单应出现在 Story 7.5 的监控视图中
```

**最小可观测字段（必须在 OMS 订单/操作日志中记录）：**

| 字段 | 说明 |
|------|------|
| `traceId` | 关联到整条补偿链路的追踪 ID |
| `retryCount` | 已重试次数（初始 0，每次失败 +1） |
| `lastError` | 最近一次失败的**业务摘要**（如"库存服务超时"），不是 full stack trace |
| `lastCompensationAt` | 最近一次补偿执行时间 |
| `manualRequired` | 是否需要人工介入（`retryCount >= 3` 时为 true） |

- [x] 6.2 ~~当 `RetryCount >= 3` 时，设置 `ManualRequired = true`，并在日志中输出 `"订单 %d 补偿失败超过 3 次, 请人工介入"`~~ ✅ **已修复：补偿链路中实现，Job 和 Consumer 均已添加**

#### Task 7: 关键验收场景

| 场景 | 步骤 | 预期结果 |
|------|------|---------|
| 正常超时关闭 | 超时任务触发，订单未支付 | 订单关闭，库存释放，优惠券回退，积分返还，一致性阶段更新为 `succeeded` |
| 重复触发幂等 | 同一订单被 job 和 consumer 重复触发 | 仅一方实际执行，另一方跳过，不重复扣减资源 |
| 库存释放失败 | 模拟 PMS `ReleaseSkuStockLock` 返回错误 | `ConsistencyResult = failed`，`lastError` 记录原因，`retryCount +1` |
| 优惠券回退失败 | 模拟 SMS `UpdateCouponRecord` 返回错误 | 同上 |
| 积分返还失败 | 模拟 UMS `UpdateMemberPoints` 返回错误 | 同上 |
| 部分成功恢复 | 上次积分返还失败，本次重试成功 | 幂等键保留，`retryCount` 累计，补偿最终成功 |
| 5分钟内必须关闭 | NFR11 验证 | 从超时时间点到补偿完成，不超过 5 分钟 |
| 人工介入触发 | 连续失败 3 次 | `ManualRequired = true`，订单出现在监控视图 |
| 前后台一致性 | 补偿完成后查询订单 | 一致性阶段与实际执行结果一致 |
