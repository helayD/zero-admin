# Story 10.3: 卡片实例生成、唯一编号与本地资产台账

Status: in-progress

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a 平台系统,
I want 在用户中奖后先生成本地卡片资产实例和唯一编号,
so that 链上发放之前就有稳定、可追踪的资产真相源。

## Acceptance Criteria

1. **Given** 某次抽卡结果为中奖 **When** 系统完成开奖结算 **Then** 系统生成唯一的卡片实例、唯一编号和本地资产记录 **And** 记录所属活动、卡片模板、用户归属和当前发放状态。

2. **Given** 抽卡请求重复提交、消息重复消费或补偿任务重放 **When** 系统再次处理同一中奖结果 **Then** 系统保持卡片实例和编号幂等不重复 **And** 不会为同一中奖结果生成多张资产。

## AC 覆盖矩阵

- **AC1（中奖即建本地资产实例 + 唯一编号 + 台账落库）**：Task 1.1-1.7、2.1-2.5、3.1-3.9、4.1-4.5、5.1-5.4
- **AC2（重复请求 / 重放 / 补偿幂等不重复发卡）**：Task 1.3-1.7、2.2-2.4、3.2-3.10、5.1-5.6

## 背景与关键风险（必须优先阅读）

> **⚠️ CRITICAL - 10.2 已经把“中奖真相源”固定在 `sms_draw_participation_record`，10.3 必须直接消费，而不是重新开奖。** 当前 `rpc/sms/internal/logic/drawparticipationservice/participate_draw_logic.go` 会在中奖时写入 `result_type = won`、`result_status = won_pending_asset`，并持久化 `pool_id/template_id/rarity/request_id`。10.3 的资产建账必须以这条中奖记录为唯一上游事实，不允许再次随机抽样或重新推断模板。
>
> **⚠️ CRITICAL - 本地资产台账才是链上发放前的真相源，不能等 10.4 成功后才第一次落库。** 架构文档已经明确采用“链下主台账 + 链上确权凭证”模型；如果 10.3 把实例创建延后到链上成功回执之后，一旦链路抖动，用户和运营都会看到“已中奖但资产不存在”的断层。
>
> **⚠️ CRITICAL - 幂等主键必须绑定到中奖记录，而不是绑定到前端按钮。** 10.2 的幂等键 `(activity_id, member_id, request_id)` 只保证“抽卡不重复”；10.3 还必须保证“同一中奖记录不重复建资产”。建议以 `participation_record_id` 或等价唯一来源键作为资产实例唯一约束，覆盖重复请求、消息重放和补偿重跑三类场景。
>
> **⚠️ CRITICAL - 唯一编号不是数据库自增 ID 的换皮。** 对外可见的资产编号必须稳定、可审计、不可轻易枚举，且与实例表主键解耦；不能直接把 `sms_card_instance.id` 暴露给前台当作“唯一编号”。
>
> **⚠️ CRITICAL - 10.3 只创建本地资产，不执行链上 token 发放。** `sms_card_mint_task`、蚂蚁链调用、回执写回、失败补偿属于 Story 10.4。10.3 最多把实例状态推进到 `asset_created` / `mint_pending` 或等价本地状态，为 10.4 提供稳定起点，但不能在本 story 里直连 `pkg/antchain` 或承诺 token 已到账。
>
> **⚠️ CRITICAL - 10.2 当前前台结果文案仍是“已中奖待到账”，10.3 必须把“资产已创建”这层服务端事实补出去。** 当前 `draw_participation.proto`、front `draw_activity.api`、Flutter `draw_result_sheet.dart` 只认识 `won_pending_asset`，还拿不到资产编号或资产状态。10.3 至少要把 `assetNo/assetStatus/assetStatusText` 之类的最小字段透给现有抽卡结果页和记录列表，否则用户仍无法确认“资产真相源已经存在”。
>
> **⚠️ CRITICAL - `rpc/sms/internal/svc/service_context.go` 全局开启了 `SkipDefaultTransaction: true`。** 这意味着 10.3 任何“创建实例 + 写日志 + 更新参与记录快照”的多表写入都必须显式放进事务，否则极易出现实例已建但日志缺失、或日志已写但参与记录没回填的半成功状态。
>
> **⚠️ CRITICAL - 如果测试/灰度环境已经跑过 10.2，可能已经存在 `won_pending_asset` 但尚无实例的历史中奖记录。** 10.3 不能只覆盖“新中奖实时建账”，还要提供可重入的回填/重放路径，把历史中奖记录补齐到本地资产台账，否则上线后会出现“同一环境里新中奖有资产、旧中奖没资产”的双轨状态。
>
> **⚠️ CRITICAL - 资产编号属于用户私有资产字段，不能在匿名落地页、最近中奖榜单或跨会员记录里泄露。** 10.3 扩展 front/RPC 字段时，只能在“当前登录会员自己的记录”范围内返回 `assetNo` 和实例状态，不能顺手把这些字段扩散到 `recent_wins` 或运营摘要接口。

## 明确非目标（本 Story 不做）

- 不接入蚂蚁链开放联盟链 SDK，不执行 token 发放、回执写回、失败补偿；这些属于 Story 10.4。
- 不建设“我的数字卡片资产列表 / 详情页”与后台审计检索工作台；这些属于 Story 10.5。
- 不把抽卡参与逻辑再重做一遍，不修改 10.2 已有的资格校验、次数扣减和开奖规则，只在中奖后的本地资产建账链路上增量扩展。
- 不把资产编号生成依赖到客户端、Flutter 本地缓存、消息文案或第三方链上返回值。
- 不在匿名活动页、最近中奖榜单或跨会员查询接口中暴露 `assetNo`、`assetInstanceId` 等用户私有资产标识。
- 不顺手升级 go-zero、GORM、Flutter、Umi、Ant Design Pro、RabbitMQ 或数据库中间件。

## 实施顺序（必须按序推进）

1. 先补本地资产实例/资产日志 DDL、唯一约束和 GORM 生成链，明确“哪条中奖记录只能生成一张资产”。
2. 再补 `sms` 域内部协议与聚合返回字段，把资产编号和资产状态最小化透出给现有抽卡记录。
3. 然后把中奖路径里的资产创建收口成可复用 helper/service，并在显式事务中接入 `ParticipateDraw` 的中奖分支。
4. 再补“重放 / 修复”入口，保证历史 `won_pending_asset` 记录可重复执行但不会重复建账。
5. 再补历史中奖记录回填脚本/任务或等价修复入口，确保已存在的 `won_pending_asset` 记录能被补齐建账。
6. 最后补前台结果页最小展示、服务端/聚合层映射和幂等测试。

## 完成判定（Definition of Done）

- 任意一次中奖抽卡在返回成功结果时，数据库中已经存在一条对应的本地卡片资产实例，而不是只存在“中奖记录”。
- 同一中奖记录被重复处理时，返回同一资产实例与唯一编号，不会新增第二张资产。
- 资产实例表、资产状态日志表和参与记录之间可以串起完整链路：活动、用户、模板、中奖记录、资产编号、当前本地状态。
- 前台抽卡结果或个人记录至少能拿到“资产已创建 / 唯一编号或待生成说明”的服务端确认信息，而不是继续只能看到“待到账”。
- 不会出现“重复发卡”“同一编号对应多资产”“实例存在但没有状态日志”“日志存在但实例缺失”的数据破坏。
- 10.4 可以在不重新开奖的前提下，基于 10.3 的本地资产真相源继续创建链上发放任务。
- 历史 `won_pending_asset` 中奖记录可以通过回填/重放入口补齐资产实例，且重复执行不会重复建账。
- `assetNo` 等私有资产字段只会在当前会员自己的记录中返回，不会出现在匿名落地页或最近中奖摘要里。

### 架构约束（必须遵守）

1. **本地资产台账仍归 `sms` 域，不新拆微服务。**
2. **链下主台账优先于链上状态。** `sms_card_instance` 才是 10.3 的真相源，链上 token 只是 10.4/10.5 的附加状态。
3. **中奖记录是资产实例的唯一上游输入。** 任何资产创建都必须可追溯到 `sms_draw_participation_record`。
4. **抽卡结果状态与资产生命周期状态分离。** `result_status` 不等同于 `asset_status`、更不等同于链上 token 状态。
5. **10.3 只做本地建账，不做链上发放。**
6. **事务必须显式声明。** 由于 `SkipDefaultTransaction: true`，多表写入不能依赖 GORM 默认事务。

### 技术要求与 Guardrails

1. **优先复用 10.2 的 `ParticipateDraw` 中奖分支，而不是另写一条平行中奖链。**
   - 当前 `ParticipateDraw` 已有显式 `DB.Transaction(...)`
   - 当前 `draw_participation_helper.go` 已定义 `won_pending_asset`
2. **资产实例的幂等唯一键应绑定中奖来源。**
   - 推荐 `participation_record_id` 唯一
   - `request_id` 可作为辅助追踪，不单独承担“建账唯一”责任
3. **唯一编号生成器必须与表主键解耦。**
   - 不暴露自增 ID
   - 需要数据库唯一约束 + 应用层重试
4. **状态日志必须追加写。**
   - 不能只改 `sms_card_instance.asset_status` 而不留首条创建日志
   - 后续 10.5 会直接依赖这条时间线
5. **参与记录上的资产字段若扩展，只能做快照，不得反客为主。**
6. **前台展示必须服务端确认优先。**
   - `assetNo`
   - `assetStatus`
   - `assetStatusText`
   都应来自服务端聚合返回
7. **不要提前创建 `sms_card_mint_task`。**
   - 这是 10.4 的责任
   - 10.3 只需让 10.4 能“读到一个稳定可发放的本地实例”
8. **修复/重放能力必须复用同一建账函数。**
   - 不要实现两套“在线中奖建账”和“后台修复建账”逻辑
9. **Front / Flutter 仅做最小展示修正。**
   - 不要在本 story 顺手开做资产列表页
   - 不要让客户端推断“编号大概已经生成”
10. **Scope 快照必须保留。**
   - 实例表或日志表至少应能反映中奖时的平台/租户/商户归属，避免后续审计只能依赖外部关联推断。
11. **资产字段必须遵守会员隔离。**
   - `assetNo`、`assetInstanceId` 只能出现在“当前会员自己的记录”查询结果里
   - `recentWins`、匿名落地页和公共摘要接口继续保持脱敏、去私有资产标识
12. **历史回填与实时建账必须共用实现。**
   - 发布前若需要补历史数据，必须调用同一个 `EnsureCardInstanceByParticipationRecord` 入口，避免线上/线下两套行为不一致

### 明确反模式（命中任一项都不算完成）

1. **用 `sms_card_instance.id` 直接充当用户可见唯一编号。**
2. **重复执行同一中奖记录时再次生成第二条资产实例。**
3. **把链上 token 状态写进 10.3 作为已完成事实。**
4. **只建实例不写资产状态日志。**
5. **只在 Flutter 文案层把“待到账”改成“已创建”，但服务端没有真实资产记录。**
6. **把中奖记录状态直接覆盖成链上状态，导致开奖结果语义丢失。**
7. **为修复任务单独再写一套建账逻辑。**
8. **把 `assetNo` 暴露到匿名活动页、最近中奖榜单或其他会员可见接口。**

### Latest Technical Information（2026-04-17 调研）

1. **go-zero 官方 GitHub Releases 当前最新版本为 `v1.10.1`，发布日期是 2026-03-28；仓库当前仍固定在 `go-zero 1.9.3`。**  
   因此 10.3 应继续基于当前仓库栈做增量实现，不把资产建账与框架升级绑定。  
   参考：[go-zero Releases](https://github.com/zeromicro/go-zero/releases)
2. **GORM 官方索引文档在 2026-03-30 仍明确区分普通 `uniqueIndex` 与“唯一复合索引”，并强调复合索引列顺序会影响性能。**  
   对 10.3 来说，这意味着“中奖来源唯一约束”和“资产编号唯一约束”应在 DDL/模型层明确设计，而不是只靠应用逻辑约定。  
   参考：[GORM Database Indexes](https://gorm.io/docs/indexes.html)
3. **GORM 官方事务文档明确说明：在 `db.Transaction(func(tx *gorm.DB) error { ... })` 中返回任意错误都会回滚，且支持嵌套事务。**  
   由于当前 `rpc/sms` 全局关闭了默认写事务，10.3 的多表写入必须显式包进事务中。  
   参考：[GORM Transactions](https://gorm.io/docs/transactions.html)
4. **蚂蚁数字科技开放联盟链官方页面仍强调“开通体验或购买 / 业务和合约开发 / 接入业务端上链”的三步接入路径。**  
   这进一步说明 10.3 应先把链下资产真相源建稳，把链上接入保留给 10.4，不要在本 story 提前硬接上链流程。  
   参考：[蚂蚁数字科技开放联盟链](https://www.antdigital.com/products/openchain)
