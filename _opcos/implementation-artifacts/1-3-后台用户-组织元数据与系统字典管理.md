# Story 1.3: 后台用户、组织元数据与系统字典管理

Status: review

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a 平台管理员,
I want 管理平台、租户和商户后台用户，以及部门、岗位、通知和字典等治理元数据,
so that 各主体的后台可以在统一治理规则下稳定运行而不依赖线下维护。

## Acceptance Criteria

1. **Given** 平台管理员进入主体治理后台
   **When** 创建或维护平台级、租户级、商户级后台用户，以及部门、岗位、通知和字典元数据
   **Then** 系统按主体范围保存对应治理数据
   **And** 这些元数据可被后续后台用户、表单和消息能力复用。
2. **Given** 后台用户资料、组织关系或字典项缺少必填字段或主体范围冲突
   **When** 平台管理员尝试保存
   **Then** 系统返回明确校验结果
   **And** 不会生成跨主体或缺少审计信息的治理元数据。

## Dev Notes

### Scope Guardrails

- 本 story 的目标是把现有 `sys` 域后台用户、部门、岗位、通知和字典能力升级成“带主体范围、带审计、可复用”的治理能力，不是一次性完成角色模板中心、数据授权矩阵、商户入驻工作流或全域业务对象隔离。[Source: `_opcos/planning-artifacts/1-new-feature/epic.md#Story-13-后台用户组织元数据与系统字典管理`]
- Story 1.4 负责菜单模板、数据范围和关键操作权限；Story 1.5 负责商户入驻与主体启停；Story 1.6 负责商品/订单/营销等核心对象隔离。本 story 不能把这些工作打包进“用户与字典管理”里一并做完。[Source: `_opcos/planning-artifacts/1-new-feature/epic.md`]
- 平台、租户、商户三类后台治理必须继续落在既有 `admin-api + rpc/sys + web-admin/system` 结构内，不得新造第二套平台后台、租户后台或独立管理服务。[Source: `_opcos/planning-artifacts/1-new-feature/prd.md`; `_opcos/planning-artifacts/1-new-feature/architecture.md#Project-Structure--Boundaries`]
- 当前仓库并不存在明确的商户治理真相源与商户管理模块；如果本 story 需要承接 merchant scope，请以“兼容未来商户实体”的方式设计绑定和字段，不要在 `sys` 域私自再造一套 merchant 主体表。[Source: `_opcos/planning-artifacts/1-new-feature/epic.md#Story-15-商户入驻审核与主体启停`; `script/sql/`; `api/`; `rpc/`; `web-admin/src/pages/`]

### Story Foundation / Business Context

- FR42 要求平台管理员可以统一管理平台、租户、商户后台用户、角色、菜单模板、部门、岗位、通知和字典数据；Story 1.3 负责把其中“后台用户 + 组织元数据 + 通知 + 字典”这一半治理底座先落地。[Source: `_opcos/planning-artifacts/1-new-feature/prd.md#FR42-Epic-1`; `_opcos/planning-artifacts/1-new-feature/epic.md#Story-13-后台用户组织元数据与系统字典管理`]
- PRD 明确要求平台、租户、商户三级作用域下的关键写操作必须带经过校验的主体标识，并证明高严重级跨主体泄漏缺陷为 0，因此本 story 的用户与元数据写入不能继续沿用“全局单空间”的假设。[Source: `_opcos/planning-artifacts/1-new-feature/prd.md`]
- 后台运营闭环目标强调：商品、订单、营销、内容、会员与系统配置的常规操作都不应依赖直接改库。用户、组织和字典这些系统元数据是后续后台表单、消息能力和作用域治理的基础设施，必须先从脚本时代升级为正式产品能力。[Source: `_opcos/planning-artifacts/1-new-feature/prd.md`]

### Existing Repository Reality

- `sys` 域已经具备用户、部门、岗位、字典类型、字典项和通知的 API / RPC / SQL 基础能力：`api/admin/doc/api/sys/{user,dept,post,dict_type,dict_item,notice}.api`、`rpc/sys/proto/{user,dept,post,dict_type,dict_item,notice}.proto`、`script/sql/sys/{sys_user,sys_dept,sys_post,sys_dict,sys_notice}.sql` 都已存在。[Source: `api/admin/doc/api/sys/`; `rpc/sys/proto/`; `script/sql/sys/`]
- Web Admin 当前已有 `system/user`、`system/dept`、`system/post`、`system/dict` 页面，但并没有 `system/notice` 页面；与此同时，`script/sql/sys/sys_menu.sql` 已经插入了 `/system/notice/list` 的菜单种子，说明“后端契约/菜单已在，前端入口缺失”。[Source: `web-admin/config/routes.ts`; `web-admin/src/pages/system/`; `script/sql/sys/sys_menu.sql`]
- 现有 `sys_user`、`sys_dept`、`sys_post`、`sys_notice`、`sys_dict_type`、`sys_dict_item` 均沿用旧式 `create_by/create_time/update_by/update_time` 字段，且没有 `platform_id` / `tenant_id` / `merchant_id` 等主体范围列；`sys_dict_type` 还对 `dict_type` 做了全局唯一约束，这会阻断同名字典在不同主体范围下复用。[Source: `script/sql/sys/sys_user.sql`; `script/sql/sys/sys_dept.sql`; `script/sql/sys/sys_post.sql`; `script/sql/sys/sys_notice.sql`; `script/sql/sys/sys_dict.sql`]
- 用户登录与权限校验链仍然是“全局用户 + 全局 URL 权限”的旧模型：`loginlogic.go` 的 JWT claims 只有 `userId`、`userName`、`deptID`、`deptName`；`CheckUrlMiddleware` 也只按 `userId` 去 Redis 中取 URL 列表，不理解租户/商户主体上下文。[Source: `rpc/sys/internal/logic/userservice/loginlogic.go`; `api/admin/internal/middleware/checkurlmiddleware.go`]
- `AddLogMiddleware` 目前只记录 `userName` 和 `deptName`，尚未记录 `platformId`、`tenantId`、`merchantId` 或 subject 级别信息；如果本 story 需要“不会生成缺少审计信息的治理元数据”，就必须显式补齐作用域审计上下文，而不能假定旧日志结构已经够用。[Source: `api/admin/internal/middleware/addloglmiddleware.go`; `_opcos/planning-artifacts/1-new-feature/architecture.md#Authentication--Security`]
- 现有 Web Admin `system/user`、`system/dict`、`system/role` 等页面采用 `PageContainer + ProTable + Modal/Drawer + service.ts` 的标准模式，Story 1.3 应在这套成熟模式上做 scope-aware 增量，而不是引入另一套 UI 组织结构。[Source: `web-admin/src/pages/system/user/index.tsx`; `web-admin/src/pages/system/dict/index.tsx`; `web-admin/src/pages/system/role/index.tsx`; `_opcos/project-context.md`]

### Technical Requirements

- 优先复用现有 `sys_user` 身份表与 Story 1.2 已建立的租户绑定思路，不要新建平行 `tenant_user` / `merchant_user` 账号主表。若需要承载主体绑定，优先考虑兼容性的 binding / metadata 扩展，并与 Story 1.2 的 `sys_tenant_user` 模式保持一致。[Source: `_opcos/implementation-artifacts/1-2-租户创建与管理员初始化.md`; `script/sql/sys/sys_user.sql`; `script/sql/sys/sys_tenant_user.sql`; `pkg/scope/tenant_admin.go`]
- 如果实现方案选择直接给 `sys_user` 增加主体范围字段，必须同步解决 `mobile` / `user_name` 的全局唯一、登录 claims、角色关联和跨主体切换的一致性；不能只加字段、不处理旧链路冲突。[Source: `script/sql/sys/sys_user.sql`; `rpc/sys/internal/logic/userservice/loginlogic.go`; `api/admin/internal/logic/sys/user/adduserlogic.go`; `rpc/sys/internal/logic/userservice/adduserlogic.go`]
- 对于 `sys_dict_type`、`sys_dict_item`、`sys_notice`、`sys_dept`、`sys_post` 这类治理元数据，应优先让“同一业务语义可在不同主体下并存”成为设计目标，而不是继续假设所有主体共享同一份全局字典/通知/组织树。[Source: `_opcos/planning-artifacts/1-new-feature/prd.md`; `script/sql/sys/sys_dict.sql`; `script/sql/sys/sys_notice.sql`; `script/sql/sys/sys_dept.sql`; `script/sql/sys/sys_post.sql`]
- 现有 legacy 表普遍使用 `create_by/update_by/create_time/update_time` 命名。本 story 以兼容现有 schema、生成链和业务逻辑为优先，不要为了追求新命名一次性做仓库级重命名；但新增绑定表、扩展 DTO 与审计 helper 仍要清晰表达 created/updated 语义，避免继续扩大历史负担。[Source: `_opcos/planning-artifacts/1-new-feature/architecture.md#Implementation-Patterns--Consistency-Rules`; `script/sql/sys/`]
- 服务端必须校验组织/元数据的主体关系一致性，例如：
  - 平台用户不能被错误绑定到停用或归档租户
  - 租户级部门/岗位不能引用平台级或其他租户的组织节点
  - 字典项不能挂到其他主体的字典类型上
  - 缺少主体范围或审计操作者信息时不得写库
  这些校验必须在 `logic` / RPC 服务端完成，而不是只靠前端禁选。[Source: `_opcos/planning-artifacts/1-new-feature/prd.md`; `_opcos/planning-artifacts/1-new-feature/architecture.md#Authentication--Security`]
- 角色模板与数据范围最终落地在 Story 1.4；因此 Story 1.3 只需要把用户与治理元数据做成可被角色授权直接消费的结构，不要在本 story 内新造完整权限矩阵中心。[Source: `_opcos/planning-artifacts/1-new-feature/epic.md#Story-14-作用域角色菜单模板与数据授权`; `script/sql/sys/sys_role.sql`]

### Architecture Compliance

- 继续遵循 `admin-api -> rpc/sys -> MySQL` 链路完成用户与元数据治理，不允许 Web 页面直连数据库、直连 RPC 或用脚本替代正式接口。[Source: `_opcos/planning-artifacts/1-new-feature/architecture.md#Project-Structure--Boundaries`; `_opcos/project-context.md`]
- 网关负责协议转换与错误包装，服务端负责业务编排与数据一致性；不要把主体校验、组织冲突检测或字典唯一性逻辑写进 handler 或 React 组件。[Source: `_opcos/project-context.md`; `_opcos/planning-artifacts/1-new-feature/architecture.md#Implementation-Patterns--Consistency-Rules`]
- 对外 JSON 仍需保持 `camelCase`，但要兼容当前 system 模块广泛使用的 `current/pageSize` 请求风格和 ProTable 交互，不要在单个 story 中混入另一套分页参数命名导致现有页面断裂。[Source: `api/admin/doc/api/sys/user.api`; `api/admin/doc/api/sys/notice.api`; `web-admin/src/pages/system/user/index.tsx`]
- 生成链仍以 `.api`、`.proto`、`rpc/sys/proto/main.go`、`rpc/sys/sys.proto`、`rpc/sys/gen/generator.go` 为源定义入口；不能手改 `routes.go`、`types.go`、`*_pb.go` 或 `rpc/sys/client/**/*` 生成物来实现 scope 扩展。[Source: `_opcos/project-context.md`; `rpc/sys/proto/main.go`; `rpc/sys/sys.proto`]
- 若需要补充共享能力，优先放在 `pkg/scope`、`pkg/audit` 与 admin middleware 中，并限制在 `sys` 域治理链路内，不要顺手扩散到 `pms/oms/sms/cms/ums` 全域查询写入。[Source: `_opcos/planning-artifacts/1-new-feature/architecture.md#Requirements-to-Structure-Mapping`; `_opcos/implementation-artifacts/1-2-租户创建与管理员初始化.md`]

### UX / Interaction Requirements

- 所有高风险后台治理页面页头都应显式展示当前主体上下文，至少要让管理员看见当前是平台级、租户级还是商户级，以及本次操作将影响谁。[Source: `_opcos/planning-artifacts/1-new-feature/ux-design.md#Scope-Context-Bar`; `_opcos/planning-artifacts/1-new-feature/prd.md`]
- 创建/更新后台用户、部门、岗位、通知和字典时，应优先展示“核心字段 + 主体范围 + 复用目标”，把高级配置折叠到后段，避免表单一开始就把所有技术字段堆给用户。[Source: `_opcos/planning-artifacts/1-new-feature/ux-design.md#Form-Patterns`; `_opcos/planning-artifacts/1-new-feature/ux-design.md#Component-Strategy`]
- 高风险动作如停用用户、切换主体、删除字典、关闭通知等，需要给出 `Consequence Preview`，说明本次操作会影响的主体、后续登录/表单/消息能力和恢复路径。[Source: `_opcos/planning-artifacts/1-new-feature/ux-design.md#Component-Strategy`; `_opcos/planning-artifacts/1-new-feature/ux-design.md#Feedback-Patterns`]
- 失败反馈必须符合 `Recovery-first Feedback`：指出是“缺少必填字段”“主体冲突”“引用了停用主体”“名称重复”“越权访问”等哪一类问题，并保留当前表单上下文，不得只给技术错误或空 toast。[Source: `_opcos/planning-artifacts/1-new-feature/ux-design.md#Component-Strategy`; `_opcos/planning-artifacts/1-new-feature/ux-design.md#Feedback-Patterns`]
- 现有租户治理页已经使用 `Alert`、`DrawerForm`、`Descriptions`、`Tag` 和“影响预览”文案建立了一套可复用的治理体验语法；Story 1.3 的系统页应优先延续这套表达，而不是改回无上下文的 CRUD 表单。[Source: `web-admin/src/pages/system/tenant/index.tsx`; `web-admin/src/pages/system/tenant/components/CreateTenantDrawer.tsx`]
