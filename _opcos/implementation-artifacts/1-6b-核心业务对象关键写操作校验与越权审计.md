# Story 1.6B: 核心业务对象关键写操作校验与越权审计

Status: review

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a 平台管理员,
I want 对商品、订单、优惠券、库存和内容配置的关键写操作执行资源级作用域校验,
so that 不同租户和商户不能修改不属于自己的业务对象。

## Acceptance Criteria

1. **Given** 用户发起商品发布、订单处理、优惠券配置、库存调整或内容上下架等关键写操作
   **When** 服务端执行保存、发布、关闭、回退或删除逻辑
   **Then** 系统校验目标资源归属与当前主体范围一致
   **And** 仅允许在授权作用域内完成变更。
2. **Given** 用户尝试跨租户或跨商户修改不属于自己的资源
   **When** 发起关键写操作或敏感配置变更
   **Then** 系统拒绝请求并返回可理解的错误反馈
   **And** 越权尝试被记录到安全或审计日志中。

### Technical Requirements

- 写侧 scope 必须在网关或服务入口被归一化一次，然后显式透传给 RPC；禁止在每个逻辑里零散地用 `userId -> sys_user.platform_id/tenant_id/merchant_id` 去推断最终授权结果。[Source: `api/admin/internal/common/query_scope.go`; `_opcos/planning-artifacts/1-new-feature/architecture.md#Authentication--Security`]
- “写前校验”必须针对真实目标资源或父资源，而不是只校验操作者主体。例如：
  - 更新 / 上下架 / 删除商品时，先验证 SPU/SKU 归属
  - 发货 / 关单 / 改备注时，先验证订单归属
  - 更新优惠券时，先验证优惠券归属，且不要把优惠券“业务适用范围”`couponScopeData` 与治理 scope 混淆
  - 更新专题 / 上下架内容时，先验证专题或内容资源归属
  [Source: `rpc/pms/proto/product_spu.proto`; `rpc/pms/proto/product_sku.proto`; `rpc/oms/proto/order_main.proto`; `rpc/sms/proto/coupon.proto`; `rpc/sms/proto/coupon_scope.proto`; `rpc/cms/proto/subject.proto`]
- 批量写操作必须做全量 preflight 校验，并在任一 ID 越权时整体回滚；不能先成功更新一部分，再返回一部分失败，因为这会让治理状态和审计结论都不可信。[Inference from: `_opcos/planning-artifacts/1-new-feature/epic.md#Story-16B-核心业务对象关键写操作校验与越权审计`; `_opcos/planning-artifacts/1-new-feature/ux-design.md#Journey-Patterns`]
- 当前 `ApplyProductScope`、`ApplyCouponScope`、`ApplySubjectScope` 只能作为“成功写入后的 scope 继承收口”，不能代替真正的授权。新实现应先 `EnsureScopeMatch` 或等价校验，再决定是否执行写入与是否调用这些 helper。[Source: `rpc/pms/internal/logic/common/write_scope.go`; `rpc/sms/internal/logic/common/write_scope.go`; `rpc/cms/internal/logic/common/write_scope.go`; `pkg/scope/governance.go`]
- 异步消息必须携带已验证 scope 和 trace 语义。尤其是订单关单链路，当前 `close_order_logic.go` 用 `for id := range in.Ids` 发送的是切片下标，不是真实订单 ID；1.6B 触达该文件时必须顺手校正，否则审计和异步补偿都会指向错误对象。[Source: `rpc/oms/internal/logic/orderservice/close_order_logic.go`]
- 越权拒绝和敏感写入的审计必须是“可查询的结构化持久化”，不能仅依赖 `logc.Errorf` 或控制台日志。Story 1.7 要消费这些记录，所以 1.6B 现在就要同时固定两类真相源：成功高风险写操作进入 `sys_operate_log`，越权 / 拒绝类事件进入新增的 `sys_security_event`，两者共享统一 trace / scope payload 约定。[Source: `_opcos/planning-artifacts/1-new-feature/epic.md#Story-17-治理审计与安全事件检索`; `pkg/audit/governance.go`; `script/sql/sys/sys_operate_log.sql`]

### Architecture Compliance

- 继续遵循 `web-admin / admin-api -> rpc/pms|oms|sms|cms|sys -> MySQL/Redis/MQ/ES` 的边界，不允许前端直接查库、直接判断归属或直接拼 ES 条件绕过后端授权。[Source: `_opcos/planning-artifacts/1-new-feature/architecture.md#Project-Structure--Boundaries`; `_opcos/project-context.md`]
- MySQL 仍是业务与治理写入真相源。作用域字段、审计记录和安全事件必须先落 MySQL，再考虑异步通知、读模型同步或审计中心展示。[Source: `_opcos/planning-artifacts/1-new-feature/architecture.md#Data-Architecture`]
- 共享 helper 优先放在：
  - `api/admin/internal/common/`：写侧 scope 解析、proto scope 构建
  - `pkg/scope/`：通用治理判断与批量校验
  - `pkg/audit/`：治理 payload、安全事件编码
  - `rpc/*/internal/logic/common/`：域内资源查询 / scope 继承 helper
  不要在每个业务目录里复制一套 `currentTenant()` / `matchMerchant()` 私有实现。[Source: `_opcos/project-context.md`; `_opcos/planning-artifacts/1-new-feature/architecture.md#Project-Structure--Boundaries`]
- 所有 schema / API / proto 变更必须回到 SQL、`.api`、`.proto`、生成入口处理，不手改生成物；这条对 1.6B 尤其关键，因为会同时触达 admin API、多个 RPC 和可能新增的 sys 审计表。[Source: `_opcos/project-context.md`; `_opcos/planning-artifacts/1-new-feature/architecture.md#Migration--Schema-Evolution`]
