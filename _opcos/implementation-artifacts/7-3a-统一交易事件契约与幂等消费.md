# Story 7.3A: 统一交易事件契约与幂等消费

Status: ready-for-dev

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a 技术运营人员,
I want 为订单、优惠券、积分和库存链路建立统一事件契约与幂等消费规范,
So that 各服务可以基于一致业务事实同步状态而不产生重复副作用。

## Acceptance Criteria

1. **Given** 订单创建、支付结果、订单取消或售后状态触发了库存、优惠券或积分变更 **When** 这些状态需要同步到其他服务或读模型 **Then** 系统使用统一事件命名与 payload 结构传递业务事实 **And** 事件中包含作用域、追踪和版本信息。

2. **Given** 某个消费方重复接收消息或发生临时故障 **When** 消费逻辑执行 **Then** 系统通过幂等控制避免重复副作用 **And** 不会因为单个消费者异常放大错误状态。

## Tasks / Subtasks

### 二、幂等消费与重复副作用防护

#### Task 4: 建立消费者幂等判定规则

**必须围绕“副作用幂等”而不是“消息只来一次”设计：**

- 重复消息不应重复扣减库存
- 重复消息不应重复核销/回退优惠券
- 重复消息不应重复增减积分
- 中间失败重试不应把订单推进到错误的最终态

**现有可复用证据：**

- 商品 ES 同步链路已经依赖“目标写操作天然幂等”完成重复保护（见 Story 7-1）
- 订单相关代码已存在 `status/version/updated_at/updated_by` 这一类状态流转字段约束（Architecture 明确要求）
- `api/front/internal/middleware/idempotency.go` 已提供 Redis 三状态机（`PROCESSING / COMPLETED / FAILED`）与 TTL 管理，可作为消息幂等状态记录参考
- `api/front/internal/logic/order/order/order_status_service.go` 已落地“`OrderId + Action` 命中直接返回当前状态”的幂等语义，可作为交易动作幂等判定参考
- `api/front/internal/logic/order/pay/paymentoperations.go` 已对 `pay:notify:{outTradeNo}` 实现回调幂等，说明仓库允许按业务事实设计专用幂等键，但不能把支付回调 key 直接照搬到 MQ 消费链

- [ ] 4.1 为每类消费者定义“幂等键”来源，优先使用稳定业务事实（如 eventId + entityId + action 或版本）而非瞬时请求参数
- [ ] 4.2 幂等检查必须发生在副作用之前，不能先扣库存再判断重复
- [ ] 4.3 对“已处理但部分下游失败”的场景给出明确记录方式，防止简单布尔标记掩盖半成功状态
- [ ] 4.4 如果依赖 Redis/DB 记录幂等状态，必须明确 TTL/清理/冲突处理策略，避免短期成功长期失忆

#### Task 5: 修复或封装当前 Consumer 鲁棒性缺口

> **已知仓库风险（来自 Story 7-1 落地结果）：** Consumer 侧仍存在 `auto-ack=true`、失败不 requeue、`context.Background()` 丢失 traceId 的问题。7.3A 需要把这些问题纳入交易事件消费规范，而不是继续默许。

**必须直接检查的现有 wiring：**

- `pkg/mq/rabbitmq_util.go`：`ConsumeSimple` 与 `ConsumeTopicQueue` 当前都使用 `auto-ack=true`
- `consumer/internal/svc/service_context.go`：当前所有 order 队列都通过 `ConsumeSimple(..., func(body []byte) { order.Xxx(context.Background(), body) })` 启动，traceId 在进入 consumer 时被丢失

- [ ] 5.1 梳理 `pkg/mq/rabbitmq_util.go` 当前消费模式，明确哪些消费者仍然自动 ACK
- [ ] 5.2 对订单权益类消费者切换为“成功后 ACK、失败时可重试/转人工”的模式，禁止自动 ACK 后静默丢消息
- [ ] 5.3 消费端上下文必须注入 payload 中的 traceId，保证日志、审计和链路诊断能串起来
- [ ] 5.4 为临时失败与不可恢复失败定义不同处理策略：重试、死信、人工介入不能混为一谈

#### Task 6: 约束 Job/补偿与 MQ 消费的职责边界

- [ ] 6.1 MQ consumer 负责响应单个业务事实并推进直接副作用；Job 负责扫描遗漏、修复悬挂、重放失败，不要把两者写成同一套职责
- [ ] 6.2 若消费者无法确认最终成功，不要伪造“已完成”状态；应显式留下待补偿/待重试标记供 Story 7-4/7-5/7-6 继续接管
- [ ] 6.3 对“支付成功后的券使用确认/积分扣减确认/库存占用确认”与“订单取消后回券/返积分/释放库存”分别定义阶段入口与补偿入口，避免一个 job 模糊处理所有交易异常

## Dev Notes

### 架构约束与边界（继承自 Epic 7 + Architecture）

**约束 1：统一拓扑不可改写**

- 后端通信拓扑固定为 `REST 网关 + gRPC 服务 + RabbitMQ 异步事件 + Job 补偿`
- 交易事件必须由领域服务在业务真相源写成功后发布，不允许由前端、网关或脚本侧伪造业务事实

**约束 2：事件命名与 payload 必须复用 Architecture 规范**

- 命名格式：`{domain}.{entity}.{action}.v{n}`
- payload 至少包含：`eventId`、`occurredAt`、`traceId`、`platformId/tenantId/merchantId`、`actorId`、`entityId`、`action`、`version`、`data`
- 不允许继续在订单、库存、优惠券、积分链路里并存多套风格各异的事件 JSON

**约束 3：MySQL 是真相源，事件是状态传播，不是主状态本身**

- 订单、优惠券、积分、库存核心状态以 MySQL 为准
- Redis 只能用于幂等键、协调和短期缓存，不能替代交易真相
- MQ 消息与读模型更新失败时必须进入补偿/重试/人工介入，而不是把 MQ 当真相源

**约束 4：Scope 是强制字段，不是可选装饰**

- 所有交易事件必须显式透传 `scopeType/platformId/tenantId/merchantId`
- 下游不得靠订单号或商户表反查去“猜”当前主体

**约束 5：幂等保护是交易正确性的组成部分**

- 不允许把“MQ 理论上只投一次”当作幂等策略
- 幂等检查必须覆盖创建、支付成功、取消回退、售后变更等所有会产生副作用的事件

**约束 6：禁止手改生成文件**

- 如需改契约，优先修改 `.proto` / `.api` / 生成源并重新生成
- 不要直接修改 `*_pb.go`、`gen/`、客户端生成文件来临时塞字段

### 通信拓扑

```text
订单创建 / 支付结果 / 订单取消 / 售后状态变化
  → OMS 持久化主状态成功
  → OMS 统一事件发送层发布交易事件
  → RabbitMQ 交换机 + 路由键按业务事实分发
  → 库存 / 优惠券 / 积分 / 补偿消费者按契约消费
  → 成功后 ACK，失败时重试 / 死信 / 人工介入
  → Story 7-5 / 7-6 监控与回放链路消费这些可观测状态
```

- 最近交付重点已从搜索同步过渡到搜索入口与配置修正，说明 Epic 7 正在沿“事件 → 搜索 → 交易一致性”顺序推进
- 7-2 的修复显示：当前仓库容易出现“路由/配置/默认值”这类小缺口；7.3A 必须把事件交换机、routing key、ACK 策略、幂等键定义写清楚，避免 dev agent 只做一半

### Latest Tech Information

**当前仓库内已知可复用实现信号：**

- 商品事件链已经使用 topic 交换机与规范路由键，说明交易事件链不需要另造第二套基础设施
- `consumer/internal/mq/order/event_payload.go` 与 `rpc/oms/internal/logic/orderservice/event_payload.go` 提示订单域已有事件入口，优先在此基础上收口
- `pkg/scope/product_es_sync.go` 证明仓库倾向把事件 payload 放到 `pkg/scope` 或共享包中复用；交易事件也应采用类似方式沉淀共享契约，而不是散落在多个 consumer 文件中
- `consumer/internal/svc/service_context.go` 表明 order consumer 仍是“队列直绑 + `context.Background()` + `ConsumeSimple`”模式，交易事件链不能继续停留在这个可靠性级别
- `consumer/internal/mq/order/order_delay_cancel_logic.go` 已经是现成的库存释放 / 优惠券回退 / 积分返还编排参考，但它目前依赖简化 payload，且没有通用事件契约与统一幂等保护

**本 story 要明确暴露给 dev agent 的风险：**

1. 不能照搬商品 ES 同步链路的 `auto-ack=true` 缺陷到交易权益链
2. 不能把订单、库存、优惠券、积分各自写成不同 payload 风格
3. 不能只做“发消息”而不定义消费幂等和失败语义
4. 不能把 Trace/Scope 记录留到后续监控 story 再补；最小字段必须从 7.3A 开始带上
5. 不能误以为现有 `sendOrderEvent` 已经满足目标契约；它目前仍是简化 payload helper
6. 不能误以为 order consumer 已经具备完整副作用处理；除延时取消链路外，大多数 order consumer 目前只是占位逻辑
