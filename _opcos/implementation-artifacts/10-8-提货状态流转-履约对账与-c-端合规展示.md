# Story 10.8: 提货状态流转、履约对账与 C 端合规展示

Status: ready-for-dev

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a 领取人、客服和技术运营人员,
I want 追踪提货卡从领取到提货完成的状态，并确保消费者端只展示合规信息,
so that 提货过程可解释、可补偿、可对账且不暴露底层链路信息。

## Acceptance Criteria

1. **Given** 领取人已成功绑定提货卡 **When** 进入提货流程并提交必要提货信息 **Then** 系统驱动待领取、已领取、待提货、提货中、已提货、已失效、已冻结等状态流转 **And** 订单、资产、提货卡和履约视图保持一致。

2. **Given** 提货卡处于冻结、失效、退款处置、补偿中或已提货状态 **When** 用户或客服查看状态 **Then** 系统展示可理解的处理结果、下一步动作或不可提货原因 **And** 不允许已提货后再次提货或退款后仍可提货。

3. **Given** 消费者端展示提货卡或提货卡 **When** 页面渲染卡片详情、列表或领取结果 **Then** 页面只展示卡片编号、模板名、商品或活动来源、获取时间、发放状态、领取状态、提货状态、展示状态和合规提示摘要 **And** 不展示底层链路、token 标识、链上交易编号、链上状态详情或链上回执内容。

## 背景与关键风险（必须优先阅读）

> **⚠️ CRITICAL - 10.8 是 Epic 10 中负责"状态闭环"的故事。** 10.7 完成了提货单创建、分享凭证生成和领取绑定，但 10.7 明确声明"不建设提货状态流转的完整对账和 C 端合规展示"。10.8 必须在此基础上补全状态机、对账能力和合规展示边界，形成可信的履约闭环。

> **⚠️ CRITICAL - 状态流转必须同时覆盖"订单视角"和"资产视角"。** 从订单视角看，提货卡履约对应 OMS 的一条特殊订单（`activity_type = digital_card_redemption`，金额为 0）；从资产视角看，`sms_card_instance` 的 `asset_status` 和 `sms_card_redemption_order` 的 `status` 必须始终保持映射关系，不能出现"资产说已提货、订单说待发货"的矛盾。

> **⚠️ CRITICAL - 10.8 必须定义完整的提货卡状态机。** 目前 `sms_card_instance` 的 `asset_status` 字段已有部分状态（如 `claimed`、`pending_redemption`），但 10.8 需要定义并驱动完整的状态矩阵：
> - `pending_claim`：待领取（购买人持有，未分享也未提货）
> - `claimed`：已领取（领取人绑定成功，尚未提货）
> - `pending_redemption`：待提货（已创建提货单，等待发货）
> - `processing_redemption`：提货中（OMS 已发货，物流在途）
> - `completed_redemption`：已提货（已签收，履约完成）
> - `expired`：已失效（超过有效期或售后退款后失效）
> - `frozen`：已冻结（退款处置、合规冻结或人工冻结）

> **⚠️ CRITICAL - OMS 发货状态回传是状态一致性的关键。** 10.7 的 `RedemptionRequested` consumer 创建了 OMS 订单，但 OMS 发货、签收的状态变更目前没有任何机制回写到 `sms_card_redemption_order`。10.8 必须建立 OMS -> SMS 的状态回传链路（事件或回调），并同步更新 `sms_card_instance.asset_status`。

> **⚠️ CRITICAL - 退款/售后后的提货卡处置是合规重点。** 如果用户申请了订单退款（购买型提货卡的原始订单），已发放但未提货的提货卡必须被冻结或回收；已提货（已完成履约）的提货卡不允许退款。这个逻辑必须在前端（隐藏退款入口）和后端（强制校验）同时生效。

> **⚠️ CRITICAL - C 端字段边界必须强制执行。** 消费者端任何页面（资产列表、资产详情、提货状态、履约时间线）都不得展示 `chain_type`、`chain_tx_id`、`token_id`、`last_receipt_json`、`mint_task_status` 等底层字段。这些字段只允许在后台运营/客服/技术运营视图中展示。

> **⚠️ CRITICAL - 履约对账必须可解释。** 技术运营和客服需要能在后台看到：订单 -> 提货卡实例 -> 提货单 -> OMS 订单 -> 发货状态的完整映射关系，并能在状态不一致时定位问题。

> **⚠️ CRITICAL - 10.8 不能破坏 10.7 建立的分享凭证和持有人变更模型。** 10.7 的 `sms_card_claim_token` 和 `sms_card_asset_log` 已记录了持有人变更历史。10.8 在状态流转时仍要保留这些审计线索，并在状态变更时追加新的 `asset_log` 记录。

## 完成判定（Definition of Done）

**状态流转场景：**
- 购买人支付成功后，提货卡状态为 `pending_claim`（待领取）或 `claimed`（如自动入账）。
- 领取人绑定成功后，状态为 `claimed`（已领取）。
- 领取人发起提货后，状态变为 `pending_redemption`（待提货）。
- OMS 发货后，状态变为 `processing_redemption`（提货中）。
- 用户签收后，状态变为 `completed_redemption`（已提货）。
- 退款/售后触发后，未提货的卡片变为 `frozen` 或 `expired`；已提货的卡片不允许退款。
- 分享凭证过期且未被领取后，卡片状态恢复为 `pending_claim`（购买人可重新分享或提货）。

**对账场景：**
- 后台履约对账工作台可以按订单号、资产编号、用户 ID 查询完整的履约链路。
- 状态不一致时（如 OMS 已发货但 SMS 仍为 pending），工作台展示异常标记和修复入口。
- 客服可以在工作台中查看某张提货卡的完整历史：创建 -> 发放 -> 领取 -> 提货 -> 发货 -> 签收/退款。

**C 端合规场景：**
- 消费者端资产列表、资产详情、提货状态页不包含任何底层链路字段。
- 消费者端展示的状态文案使用业务语义（"待发货"/"运输中"/"已签收"），不暴露 OMS 内部状态码。
- 合规提示摘要（如"本提货卡仅限个人收藏，不支持交易炒作"）在 C 端可见。

### 一、统一状态机定义与核心流转引擎

#### Task 1 (AC: 1): 在 pkg/digitalcardmint 中定义完整状态枚举和状态机

- [ ] 1.1 在 `pkg/digitalcardmint/constants.go` 中新增提货卡资产状态常量（与现有 `AssetStatus` 字段对齐）：

  - `AssetStatusProcessingRedemption = "processing_redemption"`（提货中）
  - `AssetStatusCompletedRedemption = "completed_redemption"`（已提货）
  - `AssetStatusExpired = "expired"`（已失效）

  - `CanTransition(from, to) bool` 方法
  - `GetAllowedTransitions(status string) []string` 方法
  - 每个转换关联触发条件说明（如 `pending_redemption` -> `processing_redemption` 由 OMS 发货事件触发）

- [ ] 1.3 在 `pkg/digitalcardmint/` 下新增 `asset_state_machine_test.go`，覆盖所有合法/非法转换：

  - 测试非法回退（已提货 -> 待提货应失败）
  - 测试冻结/失效作为终态的不可回退性
  - 测试分享凭证过期后的状态恢复（`claimed` -> `pending_claim` 是否允许）

#### Task 2 (AC: 1): 在 sms 域实现状态流转核心方法

  - 方法签名：`TransitionAssetStatus(ctx, cardInstanceID, targetStatus, reasonCode, reasonText, operatorID)`
  - 实现：查询当前状态 -> 校验转换合法性（调用状态机）-> 更新 `sms_card_instance.asset_status` -> 记录 `sms_card_asset_log`
  - 幂等保护：如果当前状态已经是目标状态，直接返回成功（不重复记录日志）
  - 并发控制：使用 `version` 字段 CAS 更新（参考 10.7 `sms_card_claim_token` 的乐观锁模式）

- [ ] 2.2 在 `rpc/sms/internal/logic/cardredemptionorderservice/` 下完善 `update_redemption_order_status_logic.go`：

    - `failed` -> `claimed`（失败后恢复为已领取）

### 架构约束（必须遵守）

1. **状态机定义必须放在 `pkg/digitalcardmint/` 中作为全系统共享源。** 不允许各个服务各自定义状态枚举。

3. **OMS 状态回传必须通过 MQ 事件，不允许 SMS 直接轮询 OMS 数据库。**

6. **所有新增事件必须遵循统一命名规范：** `{domain}.{entity}.{action}.v{n}`，payload 必须包含 `traceId`、`platformId`、`tenantId`、`merchantId`。

7. **后台人工干预接口必须受平台管理员权限保护，且强制记录操作原因。**

8. **对账任务必须幂等，同一记录多次对账不生成重复告警。**

9. **新增 consumer/job 文件必须同步在 `consumer/internal/svc/service_context.go` 或 `job/internal/logic/job_logic.go` 接线。**

### 技术要求与 Guardrails

1. **不要在 C 端接口中暴露 `sms_card_instance.id` 或内部自增 ID。** C 端只使用 `asset_no`（唯一编号）作为资产标识。

2. **不要让 front-api 直接修改 `sms_card_instance` 状态。** 必须通过 RPC 调用 SMS 的 `TransitionAssetStatus` 方法。

3. **不要忽略 OMS 发货状态变更的幂等性。** 同一发货事件可能被多次消费，必须保证重复消费不产生副作用。

4. **不要在前端自行推断状态。** 所有状态文案和流转判断必须以服务端聚合状态为准。

5. **不要允许已提货的卡片再次提货。** 服务端和前端都必须强制执行此校验。

6. **不要在对账任务中直接修改生产数据。** 对账任务只标记异常和触发修复，修复动作由人工或专门的修复任务执行。

7. **不要把退款处置逻辑耦合到 OMS 中。** OMS 只发布退款事件，SMS 负责决定如何处置关联的提货卡。

8. **C 端新增字段必须通过后端聚合返回，客户端不自行拼装状态。**
