### Dev Notes

## Story

As a 技术运营人员,
I want 对授权范围内的异步链路执行重试、回放、暂停和升级处理,
So that 我可以在不改库和不手工修补数据的前提下恢复业务连续性。

## Acceptance Criteria

1. **Given** 某条链路被判定为可重试或需人工处理 **When** 技术运营在工作台中执行重试、回放、暂停或升级 **Then** 系统按权限执行对应动作 **And** 将处理结果回写到链路状态视图。

2. **Given** 技术运营不具备当前租户或商户的处理权限 **When** 尝试执行链路干预动作 **Then** 系统拒绝操作并提示权限不足 **And** 仍然保留查看异常详情的最小必要能力。

### 一、链路干预动作定义与权限模型

> **⚠️ 前置依赖：** Story 7.5 已建立统一链路监控视图（`chain-monitor`）、补偿链路数据接入（`QueryCompensationChainList` RPC）、一致性阶段模型（`ConsistencyStage`/`ConsistencyResult`）。本 Story 必须在 7.5 监控视图基础上扩展干预能力，而不是重新发明第六套链路状态语义。

#### Task 1: 明确链路干预动作类型与触发条件

**必须复用 7.5 的链路监控视图数据模型：**

| 干预动作 | 触发条件 | 目标链路类型 | 技术实现 |
|---------|---------|------------|---------|
| **重试（Retry）** | 链路处于 `Failed` 状态，`retryCount < maxRetry` | 补偿链路（订单超时关闭） | 调用原补偿 Job 逻辑或直接执行补偿步骤 |
| **回放（Replay）** | 链路处于任意可回放状态，运营需重新触发整条链路 | 补偿链路 / ES 同步 / 支付回调 | 重新发布事件或重新执行补偿 |
| **暂停（Pause）** | 链路处于 `Processing` 或可干预状态 | 补偿链路 | 设置 `paused=true`，后续扫描跳过该链路 |
| **升级（Escalate）** | 链路达到重试上限仍失败，或运营判定需人工介入 | 所有链路类型 | 标记 `manualRequired=true`，进入人工处理队列 |

**必须复用的一致性阶段模型（来自 7.3B）：**


#### Task 2: 定义干预权限模型与主体范围

**必须复用 7.1/7.5 的主体范围过滤模式：**

- 所有链路干预操作必须强制带上 `platformId/tenantId/merchantId` 过滤
- 技术运营角色必须在对应作用域内才能执行干预动作
- 跨租户/跨商户的链路干预必须被拒绝

**干预权限规则：**

| 操作类型 | 最小权限要求 | 允许操作的状态 | 拒绝时的处理 |
|---------|------------|--------------|------------|
| 查看链路详情 | 任意登录用户 | 任意状态 | N/A |
| 重试 | 技术运营（对应作用域） | `result=Failed`，`retryCount < maxRetry` | 提示"已达最大重试次数"或"无权操作" |
| 回放 | 技术运营（对应作用域） | 补偿链路，`stage=4/5/9` | 提示"链路状态不允许回放" |
| 暂停 | 技术运营（对应作用域） | `result=Processing` | 提示"链路状态不允许暂停" |
| 升级 | 技术运营（对应作用域） | `result=Failed` 或已达重试上限 | 提示"无权操作" |

| `platformId/tenantId/merchantId` | 主体范围 | 干预操作的作用域 |
| `reason` | 请求参数 | 干预原因（重试备注/回放原因/暂停原因/升级原因） |
| `beforeState` | OMS 查询 | 干预前的链路状态 |
| `afterState` | OMS 更新 | 干预后的链路状态 |
| `newTraceId` | OMS 返回 | 重试/回放后产生的新 traceId（仅 retry/replay） |
| `newRetryCount` | OMS 返回 | 重试后的新重试次数（仅 retry） |

- [ ] 7.1 所有干预 RPC 返回必须包含新的 `traceId`（用于追踪重试/回放链路）
- [ ] 7.2 admin-api 必须将干预操作写入 `sys_operate_log`（操作类型 = `chain_intervention`）
- [ ] 7.3 web-admin 的干预成功/失败反馈必须包含操作人可理解的错误摘要

#### Task 8: 关键验收场景

| 场景 | 步骤 | 预期结果 |
|------|------|---------|
| 重试成功 | 在监控视图点击重试按钮 | 链路重新执行，`retryCount` +1，`result` 更新 |
| 重试达上限 | 对已达 `retryCount >= maxRetry` 的链路点击重试 | 返回错误"已达最大重试次数" |
| 回放成功 | 在监控视图点击回放按钮 | 重新发布事件，触发完整 MQ 消费链路 |
| 暂停成功 | 对处理中链路点击暂停 | 链路被暂停，Job 扫描时跳过 |
| 暂停后继续 | 对暂停链路点击回放 | 链路继续执行 |
| 升级成功 | 对失败链路点击升级 | `manualRequired=true`，进入人工处理队列 |
| 跨主体拒绝 | 用租户A账号尝试干预租户B的链路 | 返回错误"无权操作" |
| 操作审计 | 执行任意干预操作 | 操作日志记录完整干预上下文 |

## Dev Notes

### 架构约束与边界（继承自 Epic 7 + Architecture）

**约束 1：必须复用 7.5 的链路监控视图，不得重新发明状态语义**

- `ConsistencyStage` / `ConsistencyResult` 是链路状态的唯一表达
- 干预动作的状态变更必须映射回这些枚举，**禁止**发明第五套状态
- 干预动作只是改变链路状态，不改变链路类型的本质定义

**约束 2：主体范围是强制校验条件**

- 所有干预操作必须校验 `platformId/tenantId/merchantId`
- 跨主体的干预请求必须被拒绝
- 查看链路详情的最小能力不受干预权限限制

**约束 3：干预操作必须可审计**

- 所有干预动作必须写入操作日志
- 操作记录必须包含：操作人、时间、目标、原因、干预前状态、干预后状态
- 审计记录必须能通过 `traceId` 关联到完整链路

**约束 4：NFR12 仍然是验收硬约束**

- 干预操作不能破坏"1 分钟识别、10 分钟人工介入"的 SLA
- 重试仍然受 `maxRetry` 限制，超过后必须升级到人工处理
- 暂停操作必须有明确的恢复机制（回放或手动恢复）

**约束 5：Flutter 不是链路干预的承载端**

- 链路干预是**运营侧**需求，由 web-admin 承载
- Flutter 仅需展示链路状态，不需要干预能力
