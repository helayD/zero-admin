# Story 6.6: 客服与履约订单工作台

Status: review

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a 客服或履约人员,
I want 在授权作用域内集中查看订单、退货申请、退货原因和订单设置,
So that 我可以快速定位问题单并执行后续处置。

## Acceptance Criteria

1. **Given** 客服或履约人员进入订单工作台 **When** 按订单状态、售后状态、时间和主体范围筛选 **Then** 系统返回订单、退货申请、退货原因、公司地址和订单设置等信息 **And** 列表和详情始终受当前作用域约束。

2. **Given** 客服或履约人员缺少对应主体权限 **When** 尝试访问不属于其作用域的订单或售后单 **Then** 系统拒绝访问并提示权限不足 **And** 保留操作日志用于后续排查。

#### Task 2: 新建 `api/admin/internal/logic/oms/customer_service_workstation/customer_service_order_list_logic.go`

> **⚠️ 聚合查询逻辑**：
> - 调用 OMS `QueryOrderList` 获取基础订单数据
> - 筛选条件中叠加 `return_status`（需关联 oms_order_return 表，OMS 可能无独立 RPC）
> - 构造 `CustomerServiceOrderItem` 返回（订单+支付状态+售后状态摘要）
>
> **⚠️ 注意：前端展示时，需将 OMS 退货状态与订单是否有关联退货合并为前端合成 `ReturnStatus`**：
> - `ReturnStatus = 0`：无售后（订单无关联退货单）
> - `ReturnStatus = 1`：待审核（OMS `status=0`）
> - `ReturnStatus = 2`：审核通过（OMS `status=1`，退货中/已收货）
> - `ReturnStatus = 3`：审核拒绝（OMS `status=2`）

> ⚠️ **不要把 OMS `status` 值直接暴露给前端，必须做映射**
>
> **⚠️ Scope 过滤**：必须使用 `TenantId` + `MerchantId` 过滤，与现有订单列表 `queryOrderList` 保持一致。

- [x] 2.1 Scope 解析：从 JWT / middleware 获取 `TenantId`、`MerchantId`，叠加到 OMS 查询条件
- [x] 2.2 调用 OMS `OrderService.QueryOrderList`（传入 TenantId/MerchantId 过滤 + OrderNo/OrderStatus/ReceiverName/ReceiverPhone/StartTime/EndTime + PageNum/PageSize）
- [x] 2.3 **退货状态关联**（应用层过滤 ⚠️ 无法走数据库索引）：
  - 收集所有订单 ID
  - 调用 `OrderReturnService.QueryOrderReturnList`（按订单 ID 批量查询，返回每笔订单的退货状态）
  - 构造 `returnStatus` 前端合成映射：
    - `0 = 无售后`（该订单无关联退货单）
    - `1 = 待审核`（OMS `status=0`）
    - `2 = 审核通过`（OMS `status=1`）
    - `3 = 审核拒绝`（OMS `status=2`）
  - **⚠️ 前端筛选 `ReturnStatus`** 在 Go 应用层对 `CustomerServiceOrderItem` 切片过滤，暂不支持 OMS 层下推
  - **性能说明**：若订单量大（>1000），建议后续在 OMS 层做联表查询优化（Epic 7 范围）
- [x] 2.4 **支付状态关联**：
  - 调用 `OrderPaymentService.QueryOrderPaymentList` 获取支付状态（OMS 独立表）
- [x] 2.5 构造 `CustomerServiceOrderItem`：组合订单主信息 + 收货信息 + 物流信息 + 退货状态
- [x] 2.6 返回 `CustomerServiceOrderListResp`

### 架构约束与边界（继承自 Epic 6 + Story 6-1~6-5 实施成果）

**约束 1：OMS 真实状态值（来自 Story 6-1~6-5 确认）**

OMS `order_status`（`rpc/oms/proto/order_main.proto`）：
```
1 = 待支付    (PendingPayment)
2 = 已支付/待发货  (Paid - AwaitingShipment)
3 = 已发货    (Shipped)
4 = 已完成    (Completed)
5 = 已取消    (Cancelled)
6 = 已退款    (Refunded)
7 = 售后中    (InAfterSale)
```

OMS `pay_status`（`rpc/oms/proto/order_payment.proto`）：
```
0 = 待支付, 1 = 支付成功, 2 = 支付失败
```

OMS `return_status`（`rpc/oms/proto/order_return.proto`）：
```
status = 0  // 待审核（PendingReview）
status = 1  // 审核通过（Approved — 退货中/已收货）
status = 2  // 审核拒绝（Rejected）
```
⚠️ **Story 6-4 实现确认**：status 值从 0 开始（不是 1）；前端展示需做映射：OMS 0→前端显示"待审核"，OMS 1→"审核通过"，OMS 2→"审核拒绝"

OMS `operator_type`（`rpc/oms/proto/order_operation_log.proto`）：
```
1 = 用户 (User), 2 = 系统 (System), 3 = 管理员 (Admin)
```

**约束 2：Scope 过滤原则**

- 客服工作台数据必须按 `TenantId` + `MerchantId` 双重过滤
- Scope 参数从 JWT claims 提取，不得由前端直接传无校验的 `TenantId`
- `admin-api` middleware 的 `Scope` 中间件负责校验权限

**约束 3：退货处理边界**

- OMS `OrderReturnService.UpdateOrderReturn` 仅负责更新退货状态（审核通过/拒绝/收货确认）
- 实际退款操作（财务系统扣款）属于 Epic 8（Story 8-1 交易与召回消息提醒）或独立财务模块，本 Story 不实现
- 退款金额展示：默认识别原订单实付金额，可由客服手动调整（以 OMS 字段为准）

**约束 4：Web Admin 页面模式**

- 继续遵循 `index.tsx + service.ts + data.d.ts + components/*` 模式
- 复用现有 `GovernanceScopeBar`（`pages/system/components/GovernanceScopeBar`）

- 复用现有 `OperationInfo`/`ProductInfo`/`CostInfo` 组件

**约束 5：禁止修改 OMS Proto / 生成文件**

- 不修改 `rpc/oms/gen/` 生成文件

- **通信拓扑**：`web-admin → admin-api → OMS RPC`；遵循 REST + gRPC 分层
