# Story 10.10: 提货卡后台配置中心（商业化版）

Status: review-passed (round 2, with follow-ups)

Epic: 10（提货卡 / 数字资产）

## Story

As a 平台 / 租户 / 商户运营人员,
I want 在后台拥有完整的"卡片模板 → 发卡规则 → 商品/SKU 履约模式"配置中心,
so that 我可以独立维护卡片模板、把规则绑定到 SPU/SKU、追溯哪些商品在用哪条规则，并按履约模式筛选商品，无需再依赖 seed 数据或硬编码 mock。

## Acceptance Criteria

1. **Given** 运营人员具备 sms 营销配置权限 **When** 进入"卡片模板"后台页 **Then** 系统提供卡片模板的列表 / 详情 / 新增 / 编辑 / 启停 / 删除完整能力，覆盖 `sms_card_template` 表的全部业务字段（模板名、模板编码、卡面图、版权归属、版权凭证摘要、稀有度、发行上限、展示文案、流转限制摘要、展示状态、内容审核状态），且全部走治理作用域（platform / tenant / merchant）。

2. **Given** 商品 SPU 编辑页选择"提货卡"履约模式 **When** 选择关联发卡规则并保存 **Then** `pms_product_spu.fulfillment_rule_id` 必须真实写入数据库（修复 Bug #1：Antd 同名 FormItem 导致 fulfillmentRuleId 保存为空），重新打开编辑页时回显选中的规则名称。

3. **Given** 发卡规则编辑页的"关联卡片模板"下拉 **When** 运营在 Story 10.10 完成后再增加新模板 **Then** 新模板能在 1 分钟内（不超过列表缓存周期）出现在下拉里，不再依赖 `cardTemplateOptions` 硬编码 mock；下拉项必须按真实模板的（id、名称、稀有度、状态）来源 + 当前作用域过滤。

4. **Given** 商品 SKU 草稿/编辑表单 **When** 运营为某个 SKU 配置不同于 SPU 的履约模式 **Then** 表单可选 `继承 SPU / 实物发货 / 提货卡` 三种值，提货卡时可选发卡规则覆盖；保存后 `pms_product_sku.fulfillment_mode` / `fulfillment_rule_id` 写入正确，订单履约时按 SKU 优先 → SPU 兜底的顺序解析。

5. **Given** 发卡规则列表的"绑定商品数"列 **When** 运营点击数字 **Then** 弹层（或下钻页）展示该规则当前绑定的全部 SPU/SKU 清单（商品名、SPU 货号、SKU 编码、规格、绑定来源 SPU/SKU、上下架状态），并支持解绑、批量解绑（解绑后会把对应 SPU/SKU 的 `fulfillment_rule_id` 置 0 并视情况切回 physical_delivery）。

6. **Given** 商品列表 **When** 运营按"履约模式"筛选 **Then** ProTable 的搜索栏支持选择 `全部 / 实物发货 / 提货卡`，结果列表服务端过滤而非前端过滤；导出与批量操作的目标集合也尊重该过滤条件。

7. **Given** 配置链路中任意一步配置错误（卡片模板被禁用 / 发卡规则被禁用 / 提货卡商品却没绑定规则） **When** 运营尝试发布商品或抽卡活动 **Then** 系统在保存或发布阶段拦截，错误信息明确指出"卡片模板 X 已禁用、请先启用或更换"或"商品 Y 履约模式为 digital_asset 但未绑定有效发卡规则"，不允许进入"已上架"状态。

## 背景与关键风险（必须优先阅读）

> **⚠️ CRITICAL - 当前后台存在一个 HIGH bug 直接破坏闭环：** `web-admin/src/pages/pms/ProductSpu/components/AddModal.tsx` 与 `UpdateModal.tsx` 都把 `fulfillmentRuleId` 注册了两次（一次条件渲染的 Select，一次始终存在的 hidden Input）。Antd Form 同名后注册者覆盖前者，导致用户选完发卡规则保存后，实际写库 `fulfillmentRuleId=0`。这是 Story 10.10 必须最先修掉的 1 行级 bug，先修后做后续大改。

> **⚠️ CRITICAL - 当前发卡规则的"关联卡片模板"下拉是 3 项硬编码 mock：** `RuleForm.tsx` 直接写死 `[{label:'SSR 银河兔', value:920001},...]`。虽然这 3 个 ID 恰好对应 `sms_card_template` 表的 seed 数据，但运营新增第 4 个模板永远选不到。10.10 必须把硬编码替换为真实接口调用，且接口要走作用域过滤，不能让平台模板泄漏到租户/商户视图。

> **⚠️ CRITICAL - sms_card_template 物理表已存在，但 RPC 没有为它建独立 service：** Story 10.1 的 `gen/generator.go` 第 38 行虽然声明要生成 `sms_card_template` model，但 `gen/model/` 下并没有这个 .gen.go 文件（之前未跑 GORM gen）；`drawactivityservice/draw_activity_helper.go` 里只有 raw SQL JOIN，没有独立的查询/CRUD 入口。10.10 需要新建 `cardtemplateservice`，包含 model、logic、server、client wrapper 完整一套。

> **⚠️ CRITICAL - 不允许 goctl / protoc / make gen 自动生成代码：** 仓库 `AGENTS.md` 与历史教训明确禁止使用任何代码生成命令改写本仓代码（曾因 goctl 生成 600+ 垃圾文件、protoc 改写 types.go 风格不一致出过事故）。10.10 涉及的 `*.proto` 改动、`pb.go` 增量、`types.go` 增量、`admin.go` 路由注册全部必须手写，禁止任何 codegen 简化。

> **⚠️ CRITICAL - 卡片模板必须按治理作用域隔离：** 平台模板默认全租户/商户可见，租户模板只在该租户内可见，商户模板只在该商户内可见。前端下拉、列表查询、写入校验必须复用 `rpc/sms/internal/logic/common/governance.go` 与 `pkg/scope` 已有能力，禁止前端自行决定平台/租户/商户归属。

> **⚠️ CRITICAL - SKU 级履约模式覆盖必须保留 NULL 含义"继承 SPU"：** 数据库列 `pms_product_sku.fulfillment_mode VARCHAR(32) DEFAULT NULL`，NULL 不等于 "physical_delivery"，订单履约解析时必须按 `SKU.fulfillmentMode IS NULL ? SPU.fulfillmentMode : SKU.fulfillmentMode` 逻辑读取。前端 Select 的"继承 SPU"对应保存值 `null`，不要保存空字符串 / 'inherit' 等魔术字符串。

> **⚠️ CRITICAL - 不重做 Story 10.6 已建立的发卡规则 CRUD：** `sms_product_fulfillment_rule` 的列表/详情/新增/编辑/启停/删除已经在 10.6 完成，10.10 只在它基础上：（1）补 cardTemplateName JOIN 透出，（2）让"绑定商品数"可下钻，（3）让"关联卡片模板"下拉调真接口。规则表本身的字段不再扩展。

> **⚠️ CRITICAL - 商品列表按履约模式筛选必须做服务端过滤：** ProTable 的搜索栏选择 `digital_asset`/`physical_delivery` 时，必须把这个条件作为查询参数传给 admin-api → pms-rpc，由 pms-rpc 在 SQL `WHERE fulfillment_mode = ?` 阶段过滤，不允许前端拉全量再过滤（提货卡商品上量后会拖垮列表性能）。

- 不重做消费者端提货卡资产展示（属于 10.5 / 10.7 / 10.8）。
- 不实现卡片模板的链上发行、版权存证写链等链上能力（属于 10.4 复用范围，10.10 只在模板表保留 `provider_code / credential_ref` 字段，链上写入由后续 Story 触发）。
- 不在本 Story 顺手升级 go-zero / GORM / Ant Design / Flutter 或引入新中间件。
- 不允许通过 goctl / protoc / make gen 自动生成代码来推进；所有 proto 改动、pb.go 增量、types.go 增量、admin.go 路由注册必须手工最小改动。
