# Story 5.4: 创建订单与金额一致性保护

Status: review

## Story

As a 消费者,
I want 基于确认单创建订单,
So that 我可以把已经核对好的购买信息正式锁定为一笔交易。

## Acceptance Criteria

1. **Given** 消费者已完成确认订单信息核对 **When** 提交创建订单请求 **Then** 系统校验库存、优惠券、积分、商户归属和订单金额 **And** 仅在所有校验通过后创建订单。

2. **Given** 同一确认单被重复提交或创建过程中发生并发冲突 **When** 系统收到重复请求 **Then** 通过幂等机制避免重复建单 **And** 返回可恢复的结果而不是生成多笔重复订单。

### 正确通信拓扑

```
幂等订单创建：
flutter-mall → front-api（带 X-Idempotency-Key header）
  → Redis 检查幂等键
  → [oms/库存预锁 + ums/地址校验 + sms/优惠券预占 + pms/RealStock校验]
  → oms/AddOrder（创建订单主记录）
  → OrderDeliveryService.AddOrderDelivery（存储收货人）
  → sms/UpdateCouponRecord（核销优惠券）→ Saga 补偿点①
  → ums/UpdateMemberPoints（扣除积分）→ Saga 补偿点②
  → oms/SendDelayMessage（延迟消息）
  → 返回订单ID/订单号
  → Redis 写入幂等结果（TTL=24h）

Saga 补偿（单次请求内）：
① 优惠券核销失败 → 回滚订单创建（DeleteOrder）+ 释放库存 + 返回错误
② 积分扣除失败 → 回滚优惠券 + 回滚订单 + 释放库存 + 返回错误
```

### Architecture Compliance

- **通信拓扑**：`flutter-mall → front-api → [Redis幂等 + oms + ums + sms + pms] → MySQL`；遵循 REST + gRPC + DB 分层
- **Logic 层编排**：front-api 层负责幂等检查、Saga 编排和补偿回滚；各 RPC 服务只做单一职责数据存取
- **幂等键设计**：Redis 三状态机，key 格式：`order:idempotent:{IdempotencyKey}`
  - `PROCESSING`（TTL=30s）：处理中，存储 "processing"，第二个请求等待或返回超时
  - `COMPLETED`（TTL=24h）：已完成，存储 `"{orderId}"`，命中则返回原订单
  - `FAILED`（TTL=24h）：失败，存储 `"{errorCode}"`，命中则返回原错误
- **Saga 补偿**：单次请求内串行执行 + 失败时内存级回滚；长期通过 saga_log 表和补偿 Job 实现
- **错误处理**：front-api 使用 `errorx.NewDefaultError(s.Message())` 封装 gRPC 错误，Flutter 层使用后端返回的明确错误码和错误信息
- **Scope 模式**：遵循 Story 5-1/5-2/5-3 已知约束，scope 在 Epic 5 结算链路统一处理
