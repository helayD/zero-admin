# Story 2.3: 商品上架审核与作用域可见性控制

Status: ready-for-dev

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a 平台或租户运营人员,
I want 控制商品上架、审核、推荐和下架状态，
so that 前台只展示在当前作用域内真实可售的商品。

## Acceptance Criteria

1. **Given** 商品已完成基础建档  
   **When** 运营执行审核、上架、下架或推荐状态变更  
   **Then** 系统按平台、租户、商户作用域更新商品可见性  
   **And** 前台列表和详情页只展示当前允许曝光的商品。
2. **Given** 商品被下架、审核驳回或主体停用  
   **When** 消费者访问原商品入口  
   **Then** 系统返回明确的不可售或不可见状态  
   **And** 不会继续展示失效价格、库存或购买动作。

## Tasks / Subtasks

- [ ] 1. 定义商品审核/上架/下架/推荐的统一状态语义与契约（AC: 1, 2）
  - [ ] 盘点 `api/admin/doc/api/pms/`、`rpc/pms/proto/` 与现有 PMS 商品状态字段，明确 `draft / pending-review / approved / rejected / on-shelf / off-shelf / recommended` 等最小状态集合及转换规则
  - [ ] 明确“审核结论”“前台可见性”“是否可售”“是否推荐”之间的关系，避免把多个语义混成单一布尔开关
  - [ ] 为审核意见、审核人、审核时间、上架人、下架原因、推荐状态与作用域来源补齐正式源定义，仅修改 `.api` / `.proto` / SQL 源并走生成链
  - [ ] 保证 2.3 只负责审核与可见性控制，不扩展 2.5 商品详情聚合、2.4 首页/分类浏览和 2.6 专题编排的页面能力

- [ ] 2. 基于 2.2 商品草稿真相源建立“可送审 -> 已审核 -> 可见/不可见”闭环（AC: 1, 2）
  - [ ] 复用 2.2 已定义的最小可发布条件，只有满足主图/基础信息/至少一个有效 SKU/价格库存合法/目录引用有效/主体归属合法的商品才能进入送审
  - [ ] 明确草稿、送审中、审核通过、审核驳回、已上架、已下架之间的状态跃迁和禁止路径，避免直接从草稿跳成前台可见
  - [ ] 审核驳回时保留原因与回修入口，商品仍停留在后台可编辑但前台不可见状态
  - [ ] 上架前再次校验主体启停状态、目录引用有效性和可售 SKU 条件，防止“审核通过但主体已停用”仍然可见

- [ ] 3. 复用 Epic 1 治理底座实现作用域可见性控制（AC: 1, 2）
  - [ ] 复用 Story 1.6A 的查询范围过滤与主体透传，让商品审核列表、待审列表、已上架列表、推荐列表与前台商品查询都自动带上平台 / 租户 / 商户作用域条件
  - [ ] 复用 Story 1.6B 的关键写操作越权校验，对审核、上架、下架、推荐、取消推荐、批量操作执行资源级作用域校验与越权审计
  - [ ] 明确平台级、租户级、商户级作用域冲突时的优先级与屏蔽策略，避免上层下架后下层仍展示，或上层驳回后商户仍能自助暴露商品
  - [ ] 当租户/商户主体被停用时，前台可见性判断必须同步失效，不依赖前端缓存或页面隐藏按钮兜底

- [ ] 4. 打通 admin-api -> rpc/pms -> front-api 的统一可见性判定（AC: 1, 2）
  - [ ] 在 `admin-api` 侧完成审核、上架、下架、推荐等操作的请求映射、错误包装与审计上下文传递
  - [ ] 在 `rpc/pms` 侧提供统一的商品可见性计算 helper，供后台审核链路与前台商品列表/详情查询复用，避免两边各写一套判定
  - [ ] 在 `front-api` 商品列表、详情、搜索和导购聚合链路中复用统一可见性结果，只返回当前作用域内“已通过审核且允许曝光”的商品
  - [ ] 对商品被下架、驳回、主体停用、库存失效等场景返回结构化不可见/不可售原因，供商城端展示明确反馈而非静默 404

- [ ] 5. 建立推荐/导购可见性的最小生效规则（AC: 1）
  - [ ] 明确推荐状态必须建立在“商品审核通过且当前可见”的前提上，禁止推荐一个前台不可见或不可售的商品
  - [ ] 为首页、新品、人气、品牌导购或其他推荐位预留统一 `recommended` / `recommendScope` / `recommendWindow` 语义，避免各模块自定义零散开关
  - [ ] 商品从上架切为下架、主体停用或审核驳回时，相关推荐曝光必须同步失效，不继续展示失效商品卡片
  - [ ] 仅提供 2.4/2.6 所需的下游输出契约，不在本 story 内实现完整导购页面编排

- [ ] 6. 完成交互清晰的审核与状态管理后台体验（AC: 1, 2）
  - [ ] 在 `web-admin/src/pages/pms/` 现有商品管理结构上补齐“待审核/已上架/已下架/推荐中”视图、审核动作、上下架动作与驳回原因展示
  - [ ] 页面持续显示 `Scope Context Bar` 语义，明确当前作用域、影响范围和风险级别
  - [ ] 高风险操作（审核驳回、批量下架、跨作用域推荐调整）提供 `Consequence Preview` 与二次确认，不让运营误伤大范围商品曝光
  - [ ] 审核/上下架/推荐结果采用 `Recovery-first Feedback`：成功时给出状态摘要与下一步建议；失败时明确阻断原因、修复入口与受影响商品

- [ ] 7. 为商城端“不可见 / 不可售 / 已失效”建立统一反馈契约（AC: 2）
  - [ ] 商品原入口访问时，根据驳回、下架、主体停用、推荐失效、库存不可售等原因返回统一状态码与业务语义
  - [ ] 商城端详情页和列表卡片接入统一反馈，不继续展示失效价格、库存或购买 CTA
  - [ ] 对消息唤回、优惠券召回、历史收藏或订单追溯进入的失效商品，返回结构化替代落点或失败说明，避免把用户静默送回首页
  - [ ] 与 2.5 商品详情和 9.x 意图恢复能力对齐输出口径，但不在本 story 内展开完整移动端恢复实现

- [ ] 8. 建立事件、搜索与缓存一致性约束（AC: 1, 2）
  - [ ] 商品审核通过、上架、下架、驳回、推荐状态变化时，发布统一业务事件并带上 `traceId`、作用域字段、操作人和版本信息
  - [ ] 搜索索引、首页导购缓存与商品详情缓存必须感知状态变化，避免前台长期展示已失效商品
  - [ ] 对搜索 / 缓存 / 导购生效滞后提供 `Sync Status Badge` 所需的最小状态字段与观测入口
  - [ ] 对异步同步失败、延迟或人工补偿场景留下可追踪状态，不把可见性问题藏在日志里

- [ ] 9. 补齐测试、回归与跨 story 联调（AC: 1, 2）
  - [ ] 为 `rpc/pms` 增加状态跃迁、作用域越权、主体停用、推荐依赖、前台可见性判定与结构化错误返回测试
  - [ ] 为 `admin-api` 增加审核/上架/下架/推荐接口的 scope 透传与错误映射测试
  - [ ] 为 `front-api` / 商品聚合链路增加“仅返回可见商品”和“失效商品返回明确反馈”的测试

### Story Foundation / Business Context

- Epic 2 的目标是让商户和运营在正确作用域内发布商品与导购内容，让消费者通过首页、分类、品牌、专题与详情页发现可信、可售的商品。2.3 的核心任务是把 2.2 的“可售商品草稿”变成“在正确作用域内允许曝光的商品”。[Source: `_opcos/planning-artifacts/1-new-feature/epic.md#Epic-2-商品目录发布与前台导购可见性`]

- PRD 中 FR6 要求平台、租户或具备对应作用域的运营人员可以配置首页广告、推荐商品、推荐品牌、专题推荐和优选专区；FR7 要求平台可以根据平台级、租户级、商户级的商品上架、审核、推荐和活动状态控制商品在前台的可见性。2.3 正是 FR6 / FR7 在商品域内的首个落地点。[Source: `_opcos/planning-artifacts/1-new-feature/prd.md#商品发现与内容导购`]

### Technical Requirements

- 商品审核与可见性必须以 MySQL 中的商品主状态为真相源，Redis/缓存/搜索索引只做派生读模型；不能让“是否可见”只存在于缓存键或前端判断中。[Source: `_opcos/planning-artifacts/1-new-feature/architecture.md#Data-Architecture`]
- 新增审核状态、上架状态、推荐状态、可见性原因等字段时，必须修改 `.api`、`.proto`、SQL 源并重新生成；不手改 `types.go`、`routes.go`、`pb.go`、`client`、`gen/query` 等生成物。[Source: `_opcos/project-context.md`; `_opcos/planning-artifacts/1-new-feature/architecture.md#Migration--Schema-Evolution`]
- 统一事件命名和 payload 结构，商品审核/上架/下架/推荐状态变化应发布领域事件，并携带 `eventId`、`occurredAt`、`traceId`、作用域字段、`actorId`、`entityId`、`version` 等必要信息，以支持搜索同步、导购缓存失效和监控观测。[Source: `_opcos/planning-artifacts/1-new-feature/architecture.md#Async-Event-Pattern`]
- `front-api` 必须返回结构化的不可见/不可售结果，而不是让商城端靠猜测去决定显示“已下架”“无权限”还是“商品不存在”；同时不能继续暴露失效价格、库存与购买动作。[Inference from AC + UX trusted confirmation flow; Source: `_opcos/planning-artifacts/1-new-feature/epic.md#Story-23-商品上架审核与作用域可见性控制`; `_opcos/planning-artifacts/1-new-feature/ux-design.md#Recovery-first-Feedback`]
