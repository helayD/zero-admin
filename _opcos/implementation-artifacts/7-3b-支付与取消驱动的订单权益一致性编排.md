# Story 7.3B: 支付与取消驱动的订单权益一致性编排

Status: review

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a 技术运营人员,
I want 把支付结果、订单取消和售后状态变化编排成统一的权益同步流程,
So that 用户与运营在前后台看到的订单、库存、优惠券和积分结果不会长期互相矛盾。

## Acceptance Criteria

1. **Given** 支付成功、支付失败、订单取消或售后状态更新触发了库存、优惠券或积分变化 **When** 一致性编排链路执行 **Then** 系统按统一状态语义驱动下游更新 **And** 当前同步阶段对前后台与运营视图都是可见的。

2. **Given** 某个下游状态仍在处理中或出现阶段性失败 **When** 运营人员查看订单详情或链路状态 **Then** 系统展示当前同步阶段、最近结果和待处理提示 **And** 不让不同端长期停留在互相矛盾的最终状态。

## Tasks / Subtasks

### 一、统一支付 / 取消 / 售后触发的一致性编排入口

> **⚠️ 前置依赖：** Story 7.3A 已定义统一交易事件契约与幂等消费基础。7.3B 必须复用该契约推进“订单权益一致性编排”，而不是直接在各处散落补券、返积分、放库存逻辑。

#### Task 1: 梳理当前已存在的编排入口与碎片化实现

**必须优先复用的现有入口：**

- `api/front/internal/logic/order/pay/paymentoperations.go` — 支付成功 / 失败回调、支付状态更新与回调幂等
- `api/front/internal/logic/order/order/order_status_service.go` — OMS 内订单 / 支付状态编排入口（明确不承载 Saga 补偿）
- `consumer/internal/mq/order/order_delay_cancel_logic.go` — 订单取消后的库存释放、优惠券回退、积分返还现有参考链路
- `rpc/oms/internal/logic/orderservice/cancel_order_logic.go` — 订单取消业务事实入口
- `rpc/oms/internal/logic/orderservice/add_order_logic.go` / `confirm_order_logic.go` — 订单创建 / 交易推进触发点

**当前代码真相（必须写进实现 guardrails）：**

- `paymentoperations.go` 当前已在 `AliPayNotify` 中直接更新 `order_status`、`pay_status` 和操作日志，但**没有**统一的“权益一致性阶段”表达
- `order_status_service.go` 明确声明 Saga 补偿（库存 / 优惠券 / 积分）**由调用方处理**，不在该服务内完成
- `order_delay_cancel_logic.go` 当前直接串行调用 `CancelOrder → ReleaseSkuStockLock → UpdateCouponRecord → UpdateMemberPoints`，是现有最接近完整一致性编排的链路
- `consumer/internal/mq/order/order_create_logic.go` / `order_cancel_logic.go` / `order_confirm_logic.go` / `order_return_logic.go` 目前仍基本是占位 consumer，不能假定它们已经承担权益同步职责

- [x] 1.1 形成“支付成功 / 支付失败 / 订单取消 / 售后状态变化”四类触发源到下游副作用的统一映射表
- [x] 1.2 收口编排入口：禁止后续在支付回调、取消逻辑、售后逻辑、job、consumer 中各写一套库存 / 优惠券 / 积分同步逻辑
- [x] 1.3 明确哪些路径属于同步主链路、哪些路径属于异步编排、哪些路径属于补偿/重放，不允许混写
- [x] 1.4 把 7.3A 的统一事件契约作为跨服务传播唯一入口，7.3B 只负责编排和可见性，不再定义第二套事件 payload

#### Task 2: 定义一致性编排阶段模型（不替换 OMS 主状态）

> **核心原则：** `orderStatus` / `payStatus` 仍由 OMS 主状态模型负责；7.3B 只新增“权益一致性阶段”的辅助表达，不能发明与 OMS 冲突的第三套订单主状态机。

**建议最小编排可见字段（名称可等价，但语义必须存在）：**

- `consistencyStage` — 当前一致性阶段（例如：支付确认中 / 取消回退中 / 售后结算中 / 已完成）
- `consistencyResult` — 当前结果（processing / succeeded / failed / manual-required）
- `consistencyMessage` — 用户/运营可理解的当前提示
- `lastConsistencyAt` — 最近阶段更新时间
- `pendingActions` — 尚未完成的库存 / 优惠券 / 积分动作摘要

- [x] 2.1 为支付成功、取消回退、售后结算定义统一的阶段枚举与结果枚举
- [x] 2.2 明确这些阶段字段是“辅助一致性视图”，不得替换或篡改 OMS `order_status` / `pay_status` 语义
- [x] 2.3 优先复用现有 `order_operation_log`、状态快照或详情响应承载阶段信息；只有在现有载体无法表达时才新增持久化结构
- [x] 2.4 为后续 Story 7.5/7.6 留出 `traceId / retryCount / lastError / manualRequired` 等监控字段扩展位

#### Task 3: 明确不同触发场景的副作用边界

- [x] 3.1 **支付成功**：确认哪些动作属于“正常推进”而非“补偿”；禁止支付成功时误触发库存释放或优惠券回退
- [x] 3.2 **支付失败 / 未完成支付**：只更新支付相关状态与提示，不提前把订单推进成“最终一致”完成态
- [x] 3.3 **订单取消 / 超时关闭**：统一定义库存释放、优惠券回退、积分返还的顺序与完成标记
- [x] 3.4 **售后状态变化**：明确是“申请售后”“审核通过”“退款完成”“关闭售后”中的哪几个节点才允许驱动积分/优惠券/库存相关副作用
- [x] 3.5 若某个副作用不适用于某场景（例如支付成功不释放库存），必须在 story 中显式禁止，避免 dev agent 误补逻辑

### 四、测试与验收

#### Task 10: 关键验收场景

| 场景 | 步骤 | 预期结果 |
|------|------|---------|
| 支付成功后订单查询 | 支付回调成功后立即查询订单 | 返回 `orderStatus/payStatus` 与一致性阶段快照，若下游仍在处理中必须可见 |
| 支付成功重复回调 | 同一 `outTradeNo` 重复回调 | 不重复更新 OMS，不重复执行权益副作用 |
| 支付失败 / 未完成支付 | 支付失败、用户中断支付或第三方仍未确认完成后查询订单 | 保持支付相关状态与提示可见，不误报为“已最终一致完成”，并给出继续支付/等待/返回详情的恢复路径 |
| 用户主动取消订单 | 调用取消后查询订单详情 | 可见库存释放 / 优惠券回退 / 积分返还阶段与结果 |
| 超时关闭订单 | delay cancel 触发后查询 | 与用户主动取消使用一致的一致性语义，不出现一条链路成功一条链路无状态 |
| 售后状态推进 | 触发退款/售后关键节点 | 只在允许节点驱动权益同步，且阶段对前后台可见 |
| 下游失败 | 模拟优惠券或积分服务失败 | 订单详情/链路视图显示失败原因、待处理动作和最近更新时间 |
| 重复消息 | 同一编排事件重复到达 | 不重复扣减/返还库存、优惠券、积分 |
| 跨端一致 | 前台支付结果页、订单详情、运营侧详情同时查看 | 一致性阶段语义一致，不出现长期矛盾状态 |
| 售后恢复入口 | 提交售后后查看订单与运营视图 | 可见 `ReturnId / ReturnNo` 或等价恢复入口字段，并能看到售后驱动的一致性阶段 |

## Dev Notes

### 架构约束与边界（继承自 Epic 7 + Architecture）

**约束 1：不要发明第三套订单主状态**

- OMS `order_status` / `pay_status` 仍是订单主状态真相
- 7.3B 只负责“权益一致性阶段”的可见性与编排，不允许新增一套与 OMS 冲突的订单主状态机

**约束 2：支付成功不是补偿，取消回退才是补偿主场景**

- 支付成功后的库存、优惠券、积分处理属于正常推进/确认，不是“释放/回退”
- 订单取消、超时关闭、售后退款完成等才是资源回退或重新结算的主要触发场景

**约束 3：一切跨服务推进都要基于 7.3A 事件契约**

- 不允许 front-api、OMS、consumer、job 各自定义不同的副作用触发消息格式
- 编排逻辑可以拆分，但业务事实来源必须统一

**约束 4：可见性是 story 的一半，不是附带文案**

- 当前 AC 明确要求“同步阶段对前后台与运营视图都是可见的”
- 因此 dev agent 不能只做 MQ 编排，不暴露阶段字段或详情视图

**约束 5：幂等与失败语义必须内建**

- 不允许靠“应该不会重复回调 / 应该不会重复消费”作为设计前提
- 任何阶段失败都必须有明确结果、错误摘要和后续处理入口

### 正确通信拓扑

```text
支付成功 / 支付失败 / 订单取消 / 售后关键状态
  → OMS / front-api 确认业务事实并更新主状态
  → 发布 7.3A 定义的统一交易事件
  → consumer / orchestration 层推进库存、优惠券、积分等副作用
  → 将阶段结果写回一致性快照 / 时间线 / 查询响应
  → front-api / 运营视图读取统一阶段语义
  → 失败或长时间处理中进入 Story 7.4 / 7.5 / 7.6 的补偿、监控、回放链路
```
