# Story 3.3: 收货地址管理

## Status: done

## Story

As a 消费者,
I want 新增、编辑、删除和设置默认收货地址,
So that 我可以在结算时快速选择正确的收货信息。

## FRs Implemented

- **FR10**: 消费者可以管理收货地址，包括新增、修改、删除和默认地址设置。

## Epic Context

**Epic 3: 会员账户、地址与用户资产中心** — 消费者可以完成注册登录、维护个人资料和地址，并查看积分、成长值、优惠券及相关会员资产；运营可以管理会员规则与权益。

- Story 3.1（手机号注册与登录）已完成
- Story 3.2（个人资料与账户概览）已完成
- 本 Story 在此基础上实现完整的收货地址 CRUD 功能

## Acceptance Criteria (ACs)

### AC 1: 地址列表展示

- **Given** 消费者已登录并进入地址管理页面
- **When** 页面加载完成
- **Then** 系统调用 `GET /api/member/queryAddressList` 返回当前用户的所有收货地址
- **And** 列表按默认地址优先排序，展示收件人、手机号、省市区、详细地址和默认标识
- **And** 列表为空时展示空状态引导用户新增地址

### AC 2: 新增收货地址

- **Given** 消费者点击"新增地址"按钮
- **When** 进入地址编辑页，填写收件人姓名、手机号、省/市/区、详细地址、邮政编码、标签（家/公司等）、是否默认
- **Then** 系统调用 `POST /api/member/addAddress` 提交新地址（请求体为 `AddressReq`，`id` 字段省略或传 0）
- **And** 保存成功后返回地址列表页，列表自动刷新
- **And** 若设为默认地址，原默认地址自动取消默认标识（后端事务处理）

### AC 3: 编辑收货地址

- **Given** 消费者在地址列表点击编辑按钮
- **When** 进入地址编辑页，表单预填当前地址数据
- **Then** 修改后调用 `POST /api/member/updateAddress` 提交更新（请求体为同一个 `AddressReq`，`id` 字段必传，来自列表数据）
- **And** 保存成功后返回地址列表页，列表自动刷新
- **And** 编辑时 `id` 字段来自列表数据，不暴露为用户可编辑字段

### AC 4: 删除收货地址

- **Given** 消费者在地址列表点击删除按钮
- **When** 弹出确认对话框并确认删除
- **Then** 系统调用 `GET /api/member/deleteAddress?ids=<id>` 删除地址（`ids` 为 `[]int64` 数组，Dio 默认 `ListFormat.multi` 会序列化为 `ids=1&ids=2`，单条删除传 `[id]` 即可）
- **And** 删除成功后列表自动刷新
- **And** 删除默认地址后，列表中不再有默认标识（需用户重新设定）

### AC 5: 设置默认地址

- **Given** 消费者在地址列表中选择一个非默认地址
- **When** 点击"设为默认"操作
- **Then** 系统调用 `POST /api/member/updateAddressStatus` 更新默认状态
- **And** 原默认地址自动取消默认标识，新地址标记为默认
- **And** 列表即时刷新

### AC 6: 表单校验与错误处理

- **Given** 消费者提交不合法的地址信息
- **When** 保存地址
- **Then** 系统给出表单级校验提示（收件人为空、手机号格式不正确、省市区未选、详细地址为空）
- **And** 网络请求失败时展示 SnackBar 错误提示，不丢失已填内容

### AC 7: 未登录态保护

- **Given** 消费者未登录或 Token 已过期
- **When** 访问地址管理页面
- **Then** `HttpUtil` 401 拦截逻辑自动跳转至登录页
- **And** 登录成功后回到目标页面

## Dev Notes

### 架构约束

1. **认证链路**: `front-api` 使用 JWT 鉴权，`memberId` 从 JWT claims 中提取（通过 `common.GetMemberId(ctx)`），所有地址接口都绑定当前登录用户
2. **API 网关**: Flutter → `front-api`(9999) → `ums-rpc`(8081)，Flutter 不直接访问 RPC
3. **生成代码禁止手改**: `api/front/internal/types/types.go`、`api/front/internal/handler/routes.go` 均为 goctl 生成，如需修改字段需从 `.api` 定义文件重新生成
4. **网络请求统一走 HttpUtil**: Flutter 端使用 `HttpUtil.get()` / `HttpUtil.post()` 发起请求，Token 在 `HttpUtil` 内部自动附加
5. **统一请求结构体**: 新增和更新地址共用同一个 `AddressReq` 结构体（`types.go:15-26`），`id` 字段标记为 `json:"id,optional"`，新增时省略，更新时必传
6. **地址数量无上限**: 当前后端无地址数量上限校验，如后续需要限制需在 RPC 层添加

### 数据库 Schema

地址信息存储在 `ums_member_address` 表，关键字段：

| 字段 | 类型 | 说明 |
|------|------|------|
| id | bigint | 主键 ID |
| member_id | bigint | 会员 ID |
| receiver_name | varchar | 收货人姓名 |
| receiver_phone | varchar | 收货人电话 |
| province | varchar | 省份 |
| city | varchar | 城市 |
| district | varchar | 区县 |
| detail_address | varchar | 详细地址 |
| postal_code | varchar | 邮政编码 |
| tag | varchar | 地址标签：家、公司等 |
| is_default | int | 0-非默认，1-默认 |
| create_time | datetime | 创建时间 |
| update_time | datetime | 更新时间 |
| is_deleted | int | 逻辑删除 |

### API 接口规范

#### 接口总览（所有接口需 Bearer Token）

| 接口 | 方法 | 请求体/参数 | 响应 code | 关键说明 |
|------|------|------------|-----------|----------|
| `/api/member/queryAddressList` | GET | `current`(默认1), `pageSize`(默认20) | `int 0` | 返回 `data[]` 含完整地址字段 |
| `/api/member/addAddress` | POST | `AddressReq`（省略 `id`） | `int 0` | 设默认时后端事务取消旧默认 |
| `/api/member/updateAddress` | POST | `AddressReq`（`id` 必传） | `int 0` | 后端校验 `id+memberId` 归属 |
| `/api/member/deleteAddress` | GET | `ids: []int64`（form 参数） | `int 0` | 后端校验 memberId 归属 |
| `/api/member/updateAddressStatus` | POST | `{"id": int64, "isDefault": int32}` | `int 0` | 后端事务取消旧默认 |
| `/api/member/querAddressDetail` | GET | `id: int64` | `int 0` | 路由名少一个 y，保持一致 |

#### AddressReq 结构体（addAddress 和 updateAddress 共用）

```go
// types.go:15-26
type AddressReq struct {
    Id            int64  `json:"id,optional"`   // 新增时省略，更新时必传
    ReceiverName  string `json:"receiverName"`
    ReceiverPhone string `json:"receiverPhone"`
    Province      string `json:"province"`
    City          string `json:"city"`
    District      string `json:"district"`
    DetailAddress string `json:"detailAddress"`
    PostalCode    string `json:"postalCode"`
    Tag           string `json:"tag"`
    IsDefault     int32  `json:"isDefault"`     // 0-非默认, 1-默认
}
```

#### 响应体统一格式

```json
{"code": 0, "message": "操作成功"}
```

- **code 类型**: `int64(0)` 表示成功，与 `updateMember` 的 `string("000000")` 不同
- **queryAddressList 额外字段**: `current`, `data[]`, `pageSize`, `success`, `total`

### 关键风险与防护

| 风险 | 防护措施 |
|------|----------|
| `id` 被篡改导致操作他人地址 | 后端 `DeleteMemberAddress` 和 `UpdateMemberAddress` 都使用 JWT 中的 `memberId` 做归属校验。`UpdateMemberAddressLogic` 中通过 `q.ID.Eq(in.Id), q.MemberID.Eq(in.MemberId)` 双条件查询确认归属（**已验证安全**） |
| 删除默认地址后结算页无默认地址 | 前端在确认订单页需处理无默认地址的情况，提示用户选择地址 |
| 地址数量无上限 | 当前后端无地址数量限制，用户可无限添加地址。当前阶段不做限制，后续如需可在 RPC 层添加校验 |
| `addAddress` URL 常量末尾有多余空格 | `service_url.dart` 中 `addAddressDataUrl` 末尾有空格需修复：`"$baseUrl/api/member/addAddress "` → `"$baseUrl/api/member/addAddress"` |
| `address_add.dart` 中 `Navigator.pop()` 传参错误 | 当前代码 `Navigator.of(context).pop(MaterialPageRoute(...))` 把 Route 对象作为 pop result 传回，这是 **bug**（不是新功能），重构时必须修正为 `Navigator.pop(context, true)` |
| 地址列表 `createTime` 解析用 `DateTime.parse` | `address_list.dart` 模型中 `createTime` 使用 `DateTime.parse(json["createTime"])`，后端返回格式为 `"2026-01-15 08:30:00"`，需确认此格式可被 Dart 正确解析（标准 ISO 8601 用 `T` 分隔，但 Dart `DateTime.parse` 也支持空格分隔） |
| `address_detail.dart` 模型字段名与后端不一致 | 现有 `AddressDetailData` 使用 `name/phoneNumber/postCode/region`，但后端实际返回 `receiverName/receiverPhone/postalCode/district`。**本 Story 应使用 `AddressListData` 模型（字段已与后端对齐），弃用旧的 `AddressDetailData`** |
| Token 过期导致 401 未正确处理 | `HttpUtil` 已有 401 拦截逻辑（`http_util.dart`），收到 401 时跳转登录页，前端无需额外处理 |
| 响应 code 类型 | 地址相关接口统一返回 `int64(0)` 表示成功，与 `updateMember` 的 `string("000000")` 不同，需注意区分 |
| `deleteAddress` 的 ids 参数格式 | 后端 `DeleteAddressReq.Ids` 类型为 `[]int64`（`form:"ids"`），Flutter 端应使用 `HttpUtil.get(url, queryParameters: {"ids": [id]})`，Dio 默认 `ListFormat.multi` 会序列化为 `ids=1&ids=2` 格式，与后端兼容 |

   - 退出登录时需清除 SharedPreferences 中的 token

6. **提交格式**: `feat(story-X.Y): 描述`
