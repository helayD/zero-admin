# Story 9.2: 移动端统一加载、空态、错误态与弱网壳层

Status: ready-for-dev

> 2026-04-26 变更：Story 9.1 页面异常恢复已退役。本文中关于 recent context / IntentRecoveryShell / pending intent 的约束仅作为历史背景；9.2 不再要求维护页面启动恢复，只保留页面内加载、空态、错误态、弱网反馈。

## Story

As a 消费者,
I want 在核心移动页面看到一致的加载、空态、错误和弱网反馈,
so that 我能判断当前页面是在请求中、失败了，还是可以继续重试。

## Acceptance Criteria

1. **Given** 首页、分类、搜索、商品详情、购物车、确认订单、订单列表 / 详情或售后申请页开始请求数据 **When** 页面进入初次加载、空结果、失败、超时或弱网状态 **Then** 系统统一通过 `Commerce State Shell` 展示结构化反馈 **And** 页面提供刷新、返回或手动重试入口。

2. **Given** 网络恢复或用户主动重试 **When** 页面重新发起请求 **Then** 系统重新拉取服务端状态并提示是否已刷新成功 **And** 不保留误导性的旧状态。

## AC 覆盖矩阵

- **AC1（统一加载 / 空态 / 错误态 / 弱网态 + 恢复入口）**：Task 1.1-1.6、2.1-2.6、3.1-3.9、4.1-4.5
- **AC2（重试后重新拉取服务端状态 + 不保留误导性旧状态）**：Task 2.2-2.6、3.1-3.9、4.1-4.5、5.1-5.5

## 背景与关键风险（必须优先阅读）

> **⚠️ CRITICAL - 当前 Flutter 端状态表达已经分散到多个页面各自维护：** `home_page.dart`、`categories.dart`、`product_list.dart`、`product_detail.dart`、`order_list.dart`、`order_detail.dart`、`apply_after_sales.dart`、`brand_list.dart` 等页面分别使用 `CircularProgressIndicator`、`EmptyStateWidget`、`ErrorRetryWidget`、本地 `_pageState` 或静默吞错。9.2 必须收口为统一的 `Commerce State Shell`，而不是继续在每个页面复制一套状态 UI。
>
> **⚠️ CRITICAL - 首页当前甚至没有稳定的页面级请求状态机，无法真正落地整页壳层：** `flutter-mall/lib/view/home/home_page.dart` 目前请求异常时仅“保持现有数据，不清空”，但缺少独立 `_isLoading / _hasError / hasLoadedOnce` 一类状态来区分首次进入、刷新失败和已有内容后的局部失败。9.2 必须先补首页页面级状态机，再接入 `Commerce State Shell`，不能继续依赖“模块不显示”伪装为成功。
>
> **⚠️ CRITICAL - 购物车当前是“购物车列表 + 促销试算”双阶段加载，但没有页面 ready 判定：** `flutter-mall/lib/view/cart/cart.dart` 先拉购物车列表，再拉促销数据；`_queryBrandListData()` 失败时仅把 `_cartLoadedSuccessfully` 置为 `false`，`_queryPromotionData()` 失败时只打印日志。9.2 必须明确“何时算页面可展示成功态”、以及促销试算失败时如何避免用陈旧 / 缺失优惠信息误导结算。
>
> **⚠️ CRITICAL - 确认订单页仍是 ad-hoc Scaffold 分支，不是共享壳层：** `flutter-mall/lib/view/mine/order/order_submit.dart` 目前用 `_loading` / `_errorMessage` 在 `build()` 内直接切换整页 `Scaffold`。9.2 必须改为复用共享状态壳层，而不是再复制一套订单专用状态骨架。
>
> **⚠️ CRITICAL - 仓库当前没有可确认的独立搜索页：** `flutter-mall/lib/view/home/home_page.dart` 的搜索入口仍是注释掉的 `SearchDetail` 占位，代码扫描未发现稳定的搜索结果页实现。9.2 不得为了“满足 AC 文案”虚构死路由或空页面；应把 `Commerce State Shell` 设计为可复用共享能力，先接入当前已存在页面，并明确为未来搜索页保留直接复用点。
>
> **⚠️ CRITICAL - 弱网态当前不能依赖现成网络监听插件：** `flutter-mall/pubspec.yaml` 现有依赖未包含 `connectivity_plus` 等系统网络状态插件，仅有 `dio`、`provider`、`shared_preferences` 等基础依赖。9.2 的首版弱网态应优先基于 `DioException` 的超时、连接失败、无响应等信号归类，不要凭空引入新的后台监听框架或常驻网络守护进程。
>
> **⚠️ CRITICAL - 订单列表当前把请求错误“吞掉”了，极易导致首屏无反馈或分页语义混乱：** `flutter-mall/lib/view/mine/order/order_list.dart` 的 `_queryOrderList()` 在 `catch` 中只把 loading 标记为 false，并注释“错误由 State Shell 处理”，但当前并没有真正的统一 State Shell。9.2 必须明确区分“首次进入失败”与“加载更多失败”，不能把分页失败误做成整页 error，也不能让首次失败静默无反馈。
>
> **⚠️ CRITICAL - 9.1 已建立恢复底座，9.2 不能破坏“只在成功态写 recent context”的约束：** `AppRecoveryStore`、`AppRecentContext` 已在 `home_page.dart`、`cart.dart`、`product_detail.dart`、`order_list.dart` 等页面建立成功态上下文写入。9.2 的加载态、空态、错误态和弱网态只能影响 UI 呈现与重试行为，不能在失败 / 空白 / 无效目标时覆盖 recent context。
>
> **⚠️ CRITICAL - 401 / 登录恢复仍属于共享网络与恢复链，不应在 State Shell 内重复造一套鉴权流程：** 9.1 已要求 `HttpUtil` + 登录恢复链处理 pending intent / recent context；9.2 只负责请求中、失败、超时、弱网等用户可见反馈，不要在页面壳层里重复弹登录、重复保存 intent 或绕过 `HttpUtil`。

## 明确非目标（本 Story 不做）

- 不在本 Story 中实现 FR62 的消息、活动、优惠券统一意图唤回；该能力由 9.3 落地。
- 不在本 Story 中实现 FR63 权限请求或 FR64 升级闸门；但状态壳层的反馈按钮和文案结构应与后续链路兼容。
- 不重写 Flutter 全局导航体系，不把现有 `MaterialPageRoute` 全量迁移成命名路由。
- 不新增虚构的 `SearchDetail` / `SearchPage` 死页面来“凑覆盖率”；搜索场景先通过共享壳层设计预留接入点。
- 不为了 9.2 顺手扩展 `AppRecentTargetType`、`AppRecentContext` 或 recent context 写入点，把 `confirm_order`、`after_sales`、搜索占位场景强行塞进恢复模型。
- 不引入新的网络层、状态管理框架或本地存储框架；继续复用 `Provider`、`HttpUtil`、`Dio`、`SharedPreferencesUtil`。
- 不为了弱网态一次性引入 `connectivity_plus`、离线缓存框架或后台常驻网络监控；如后续确需系统级监听，必须在独立 Story 中明确评估。
- 不重写所有已有的品牌、评价、物流等非 FR61 核心页面；这些页面可作为参考实现，但本 Story 以 FR61 指定页面为主。

## 实施顺序（必须按序推进）

1. 先定义统一 `Commerce State Shell` 的状态契约、页面级用法、按钮语义和弱网归类规则。
2. 再收口已有 `EmptyStateWidget` / `ErrorRetryWidget`，避免出现第三套状态组件。
3. 再按“首页 / 分类与列表 / 商品详情 / 购物车 / 确认订单 / 订单列表与详情 / 售后申请”的顺序接入核心页面。
4. 最后补齐重试语义、无障碍语义、页面测试与弱网 / 超时 UAT，不让状态壳层只停留在静态展示。

## Tasks / Subtasks

### 一、定义统一 Commerce State Shell 契约与共享状态组件

#### Task 1 (AC: 1): 在共享层建立可复用的页面级状态壳层

**目标：** 先把“页面有哪些状态、每种状态长什么样、按钮怎么表达、哪些页面可以复用”定义清楚，再改各业务页。

- [ ] 1.1 在 `flutter-mall/lib/widgets/` 中新增统一状态壳层，建议路径为：
  - `flutter-mall/lib/widgets/commerce_state_shell.dart`
  - `flutter-mall/lib/utils/commerce_state_resolver.dart`
- [ ] 1.2 统一壳层至少支持以下状态语义：`initialLoading`、`empty`、`error`、`weakNetwork`、`content`。不要把“加载更多”误做成整页 loading；分页追加加载仍保留页尾 loading 表达。
- [ ] 1.3 壳层入参至少覆盖：状态类型、标题 / 摘要文案、失败原因摘要、主按钮文案与回调、副按钮文案与回调、内容区 `child`、是否展示顶部弱网提示 / 说明文案。
- [ ] 1.4 现有 `flutter-mall/lib/widgets/empty_state_widget.dart` 中的 `EmptyStateWidget` 与 `ErrorRetryWidget` 必须复用或吸收进统一壳层；不要在壳层之外再平行创建一套 `StateShellEmptyWidget` / `RetryPanel` 导致重复维护。
- [ ] 1.5 加载态优先使用结构化页面骨架或统一 loading 版式；不能继续让每个页面各自裸写 `Center(child: CircularProgressIndicator())` 作为最终实现。
- [ ] 1.6 状态文案、失败原因摘要、重试按钮、返回入口必须具备可访问语义；至少保证读屏可以读出当前状态与主要操作，而不是只显示图标或骨架。

### 二、统一失败归类、弱网识别与重试语义

#### Task 2 (AC: 1, 2): 基于现有 `Dio` / `HttpUtil` 建立统一状态归类规则

**目标：** 让页面知道“这是空态、普通错误还是弱网 / 超时”，并让重试行为始终重新拉取服务端状态。

- [ ] 2.1 在共享层建立最小失败归类 helper，至少区分：空结果、普通请求失败、超时、连接失败 / 无响应导致的弱网态；分类优先基于 `DioException` / `HttpUtil` 的现有错误信号，不新增平行网络栈。
- [ ] 2.2 `weakNetwork` 的首版判定至少覆盖：`connectionTimeout`、`sendTimeout`、`receiveTimeout`、`connectionError` 或无响应场景；不要因为仓库里没有 `connectivity_plus` 就跳过弱网态。
- [ ] 2.3 所有重试入口必须重新触发当前页面真实请求方法（如 `_queryHomeData()`、`_queryCategoriesData()`、`refreshProductDetail()`、`_loadConfirmOrder()` 等），并在发起新请求前清理误导性的旧错误提示或旧占位态。
- [ ] 2.4 对于已有有效内容的页面，弱网 / 错误态要区分“首次进入失败”和“已有内容后的刷新失败”：
  - 首次进入失败 → 使用整页状态壳层；
  - 已有内容后刷新失败 → 优先保留最后一次有效内容，并通过顶部提示 / 内联提示告知刷新失败，不把页面突然清空成空白。
- [ ] 2.5 成功重试后，页面必须显示已恢复到最新服务端状态，而不是保留陈旧错误摘要、旧价格 / 旧订单信息或已失效的空态占位。
- [ ] 2.6 `order_list.dart` 一类带分页的页面必须额外区分：首次拉取失败 → 整页壳层；加载更多失败 → 页尾提示 / 内联提示 / toast，且保留现有列表内容，不切回整页 error。

### 三、将 State Shell 接入 FR61 指定核心页面

#### Task 3 (AC: 1, 2): 先接入当前仓库中已存在的真实页面，不虚构路由

- [ ] 3.1 `flutter-mall/lib/view/home/home_page.dart`：先补页面级请求状态机（如 `_isLoading`、`_hasError`、`_hasLoadedOnce` 或等价语义），再接入首页首次加载、首次失败与弱网反馈；若首页部分模块为空但页面整体仍可展示，不要误判为整页空态。首页成功加载后保留 9.1 的 recent context 写入时机。
- [ ] 3.2 `flutter-mall/lib/view/category/categories.dart`：将分类页的裸 `CircularProgressIndicator` / `ErrorRetryWidget` / `EmptyStateWidget` 收口到统一壳层；左侧一级分类为空和右侧二级分类为空要区分页面级空态与区域级空态。
- [ ] 3.3 `flutter-mall/lib/view/category/product/product_list.dart`：统一商品列表的首次加载、空态、错误态与重试；列表为空时继续提供“浏览其他分类”或返回动作，不出现静默空白。
- [ ] 3.4 `flutter-mall/lib/view/category/product/product_detail.dart`：将 `loading`、商品不可见 / 请求失败场景统一收口到壳层；同时继续复用已有 `visibility.reasonCode`、`reasonMessage`、`recoveryHint`、`fallbackAction`、`fallbackTarget` 语义，而不是另造第四套错误模型。
- [ ] 3.5 `flutter-mall/lib/view/cart/cart.dart`：新增页面级 loading / empty / error / weakNetwork 壳层，覆盖购物车列表首次加载与促销试算依赖；必须明确页面 ready 条件，是“购物车主数据 + 促销数据均已就绪”还是“主数据可展示、促销失败以内联提示降级”，但无论采用哪种方案，都不能让缺失 / 失败的促销试算被误当成成功态继续展示。保留 `_isSubmitting` 提交遮罩作为“写操作进行中”状态，不要与整页首次加载混淆。
- [ ] 3.6 `flutter-mall/lib/view/mine/order/order_submit.dart`：把当前 `_loading` / `_errorMessage` 的 ad-hoc `Scaffold` 分支替换为共享壳层；加载确认单失败时必须给出明确重试入口和返回动作。**不要**顺手把确认订单页加入 `AppRecentTargetType` 或 recent context 目标类型。
- [ ] 3.7 `flutter-mall/lib/view/mine/order/order_list.dart`、`flutter-mall/lib/view/mine/order/order_detail.dart`：统一订单列表与订单详情的首次加载、空态、错误态、弱网态与重试；订单列表的“加载更多”仍保留页尾加载表达，不能变成整页闪烁或整页错误。
- [ ] 3.8 `flutter-mall/lib/view/mine/order/apply_after_sales.dart`：只把**初始加载失败**与**进入表单前错误态**接入共享壳层；现有 `submitting / success` 业务流状态继续保留，不破坏提交链路语义。
- [ ] 3.9 对“搜索页”必须做现实约束确认：当前仓库若仍无独立搜索页实现，则不新增伪页面；共享壳层 API 必须可直接复用于未来搜索页，并把当前 `product_list.dart` 作为首个列表态参考实现。

### 四、确保与 9.1 恢复底座、共享层和页面数据真相源协同

#### Task 4 (AC: 1, 2): 状态壳层只做 UI 表达与重试编排，不破坏恢复与鉴权边界

- [ ] 4.1 `Commerce State Shell` 不得绕过 `HttpUtil`、不直接创建裸 `Dio`、不在 Widget 内私建新 token 流；所有网络调用继续通过页面既有请求方法与共享层完成。
- [ ] 4.2 失败态、空态、弱网态不得覆盖 recent context；`AppRecoveryStore.saveRecentContext(...)` 仍只允许发生在首页、购物车、商品详情、订单列表 / 详情等成功拿到有效服务端数据之后。
- [ ] 4.3 401 / 登录恢复仍由 `HttpUtil`、登录页与 `Intent Recovery Shell` 负责；页面级壳层只消费“当前请求尚未拿到可展示数据”的结果，不重复弹登录或重复保存 pending intent。
- [ ] 4.4 所有状态至少提供一个明确恢复动作：`重试`、`返回`、`回首页`、`浏览其他分类`、`返回订单` 等；不允许只有 toast、只有插图或无动作占位。
- [ ] 4.5 `confirm_order`、`after_sales`、未来搜索页等未纳入 9.1 恢复契约的页面，在本 Story 中只做状态表达与重试治理，不新增 recent context 类型、不新增启动恢复目标、不修改 `AppRecentContext` 白名单。

## Dev Notes

### 架构约束（必须遵守）

1. **继续复用现有 Flutter 共享层：** 网络仍走 `Provider + Dio + HttpUtil + service_url.dart`，不要在状态壳层里私建网络客户端。
2. **状态壳层是页面级 UI 契约，不是新的业务状态管理框架：** 业务数据源、Provider、页面请求方法仍是单一真相源。
3. **弱网态首版基于现有依赖归类：** 当前 `pubspec.yaml` 未包含 `connectivity_plus`；弱网优先基于 `DioException` 的 timeout / connection error 归类，不要凭空引入新依赖。
4. **复用已有空态 / 错误态组件：** `EmptyStateWidget`、`ErrorRetryWidget` 已在多个页面使用；应围绕它们收口，而不是创建第三套平行状态组件。
5. **分页列表区分“首次加载”和“加载更多”：** `order_list.dart` 等列表页首次加载失败使用整页壳层；滚动触底加载更多只保留尾部 loading 或内联提示，不整页闪烁。
6. **首页与局部模块空态不能混淆：** 首页只要任一关键模块可展示，就不应被判定为整页空态；模块级空数据应就地处理。
7. **商品详情继续复用可见性语义：** `visibility.reasonCode/reasonMessage/recoveryHint/fallbackAction/fallbackTarget` 已经存在，不应再创造另一套不兼容的失败字段。
8. **购物车与订单页写操作状态不能被整页壳层吞掉：** 删除、清空、提交订单等“写操作进行中”仍应使用局部按钮禁用或遮罩，不与首次读取态混为一谈。
9. **购物车页面成功态必须定义清楚：** 购物车列表与促销试算是两个异步阶段；若促销数据缺失或失败，必须明确降级表达，不得继续展示误导性的优惠文案或金额摘要。
10. **确认订单与售后页不是 9.1 的恢复目标：** 本 Story 不得为 `order_submit`、`apply_after_sales`、搜索占位场景扩展 `AppRecentTargetType` 或写 recent context。
11. **优先复用现有 loading 依赖：** 如需要统一 loading 视觉，优先复用仓库已有 `flutter_spinkit` 或 Material 原生组件，不引入新的 skeleton / loading 依赖包。
12. **9.1 的恢复底座不能被破坏：** 失败态、空态、弱网态不写 recent context；成功态仍保留 `AppRecoveryStore.saveRecentContext(...)` 的现有边界。
13. **401 与登录恢复继续由共享层负责：** 不在 `Commerce State Shell` 内重复实现登录弹窗、token 判断或 pending intent 保存。
14. **不要虚构搜索页：** 当前仓库没有稳定 `SearchDetail`；共享壳层需可复用于未来搜索页，但本 Story 不应为了满足文案而新增死路由。

### Previous Story Intelligence

1. **9.1 已建立统一恢复底座：** `AppRecentContext`、`AppRecoveryStore`、`Intent Recovery Shell` 已成为启动恢复、登录恢复和 recent context 的共享基础；9.2 必须在这个基础上做 UI 状态治理，而不是反向改造恢复链。
2. **成功态才允许写 recent context：** `home_page.dart`、`cart.dart`、`product_detail.dart`、`order_list.dart` 等文件已体现这一模式；失败 / 不可见 / 无效目标会清理或拒绝写入。9.2 不能因为引入壳层而把失败页也写成“最近有效上下文”。
3. **当前导航体系仍以 `MaterialPageRoute` 为主：** 9.1 已明确不能放大命名路由假设；9.2 不应在状态壳层按钮里引入新的全局命名路由依赖。
4. **恢复链与状态壳层是串联关系，不是替代关系：** 9.1 负责“回到哪”，9.2 负责“当前页面如何表达请求状态与失败恢复”；两者不能互相吞职责。

### 最新技术信息（2026-04-05 调研）

1. Flutter 官方 `shared_preferences` 文档仍将其定位为**适合保存相对小规模 key-value 数据**的持久化方案，setter 会先同步更新内存，再落盘；这进一步说明 recent context / pending intent 这类轻量状态适合保留在现有 SharedPreferences 方案中，而不是为 9.2 引入更重的存储设施。9.2 的状态壳层也不应把大块页面状态持久化到本地。
2. Flutter 官方 Accessibility 文档强调：**无障碍是高质量应用的关键标准，建议在发版前纳入 accessibility checklist**，且 Flutter 已提供语义与辅助技术支持。这意味着 `Commerce State Shell` 的状态标题、失败原因摘要、按钮标签必须可被读屏识别，不能只靠颜色、插图或骨架表达。
3. 结合当前 `pubspec.yaml`，仓库已有 `dio`、`provider`、`shared_preferences`、`flutter_spinkit`，但没有系统网络状态插件；因此 9.2 首版弱网态应以请求层错误分类为主，保持依赖面最小。
