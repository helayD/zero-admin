# Story 2.5: 商品详情与规格库存优惠摘要

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a 消费者,
I want 在商品详情页查看价格、规格、库存、品牌和优惠信息,
so that 我可以判断这件商品是否值得购买并准备进入加购或结算。

## Acceptance Criteria

1. **Given** 商品已在前台可见  
   **When** 消费者打开商品详情页  
   **Then** 页面展示品牌、卖点、图文详情、规格、库存、价格和可用优惠摘要  
   **And** 金额、状态和时间语义与后台配置保持一致。
2. **Given** 某个规格无库存、价格失效或不支持当前作用域购买  
   **When** 消费者切换到该规格  
   **Then** 系统禁用对应购买动作并说明原因  
   **And** 不允许继续进入错误的结算流程。

### Story Foundation / Business Context

- Epic 2 的目标是让商户和运营在正确作用域内发布商品与导购内容，让消费者通过首页、分类、品牌、专题与详情页发现可信、可售的商品。2.5 是消费者从"浏览商品列表"到"做出购买决策"的最后一个信息确认节点。[Source: `_opcos/planning-artifacts/1-new-feature/epic.md#Epic-2`]
- PRD FR3 要求消费者可以查看商品详情，包括价格、规格、库存、卖点、品牌和图文详情。FR4 要求消费者可以在商品详情中选择规格、数量并决定加入购物车或进入结算流程。FR5 要求消费者可以查看商品可用的优惠券、促销信息和适用范围。本 story 是 FR3 + FR4 + FR5 的核心落地点。[Source: `_opcos/planning-artifacts/1-new-feature/prd.md#商品发现与内容导购`]
- UX 设计把"消费者首单成功"视为商城体验的第一价值证明，商品详情页是首单成交流中的关键节点。UX 强调"消费者在商品详情页应一眼看清规格、库存、价格、优惠与配送影响，不必在多个入口来回确认"，并要求"把关键路径设计成核对流程，而不是填空流程"。[Source: `_opcos/planning-artifacts/1-new-feature/ux-design.md#Critical-Success-Moments`; `_opcos/planning-artifacts/1-new-feature/ux-design.md#Effortless-Interactions`; `_opcos/planning-artifacts/1-new-feature/ux-design.md#Experience-Principles`]
- UX 消费者首单成交流明确定义了商品详情在交易链路中的位置：`商品详情查看规格、库存、优惠与品牌信息 → 购买条件是否明确? → 是 → 加入购物车或立即购买`。[Source: `_opcos/planning-artifacts/1-new-feature/ux-design.md#消费者首单成交流`]

### Technical Requirements

- SKU 级可购买性判定必须在后端完成（或至少提供充分数据让前端判定），不能让 Flutter 端自行猜测某个 SKU 是否可售。后端已返回每个 SKU 的 `stock`、`publishStatus`、`verifyStatus`，前端可基于这些字段做本地判定。[Source: `_opcos/planning-artifacts/1-new-feature/architecture.md#Data-Architecture`]
- 价格展示必须使用后端返回的真实数据。SPU 级 `price` 从 `priceRange` 第一段提取，SKU 级 `price` 从各 SKU 的 `price` 字段获取。切换规格时价格必须实时联动。金额字段后端使用整数最小货币单位。[Source: `_opcos/planning-artifacts/1-new-feature/architecture.md#Format-Patterns`]
- 优惠券查询必须走 SMS RPC (`QueryCouponByScopeId`)，查询失败时不影响商品详情主体返回。当前代码中已用 `couponList, _ :=` 忽略错误，符合降级策略。[Source: `api/front/internal/logic/product/product/query_product_detail_logic.go`]
- 新增或修改 `.api` 源文件后必须通过 `goctl api go` 重新生成，不手改 `types.go`、`routes.go` 等生成物。[Source: `_opcos/project-context.md`]
- 图文详情 HTML 渲染需注意安全：使用 WebView 组件渲染 `detailMobileHtml` 时，应禁止 JavaScript 执行外部脚本，仅作为富文本展示。[Source: `_opcos/planning-artifacts/1-new-feature/architecture.md#Authentication--Security`]

### Architecture Compliance

- 继续遵循 `flutter/front -> front-api -> rpc/pms/sms -> MySQL` 的边界，不让 Flutter 直连 ES 或数据库。[Source: `_opcos/planning-artifacts/1-new-feature/architecture.md#Service-Boundaries`]
- Flutter 端保持 Provider + Dio + `HttpUtil` + `service_url.dart` 模式，不引入新的状态管理或网络层。[Source: `_opcos/planning-artifacts/1-new-feature/architecture.md#Flutter-Mall`]
- Go 侧保持 `handler -> logic -> svc` 分层，共享可见性判定落 `api/front/internal/logic/common/`，商品详情专用构建函数落 `api/front/internal/logic/product/product/`。[Source: `_opcos/planning-artifacts/1-new-feature/architecture.md#Implementation-Patterns`]
- 加购接口调用 OMS RPC (`CartItemService`)，不在 front-api 的商品 logic 中直接操作订单数据。[Source: `_opcos/planning-artifacts/1-new-feature/architecture.md#Project-Structure--Boundaries`]
