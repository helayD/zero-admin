# Story 1.1: 既有仓库基线初始化

Status: ready-for-dev

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a 交付工程师,
I want 基于现有 brownfield 仓库完成初始工程设置和依赖安装,
so that 后续平台治理与多主体能力可以在统一实现基线上继续开发而不重新脚手架。

## Acceptance Criteria

1. **Given** 当前实现基线使用既有仓库而非全新脚手架
   **When** 执行后端构建、Web 依赖安装和 Flutter 依赖安装
   **Then** 后端、管理端和商城端的基础依赖准备完成
   **And** 不创建新的平行工程或脱离仓库基线的初始化结果。
2. **Given** 交付环境需要开始后续平台治理开发
   **When** 初始化完成并校验工程结构
   **Then** 各子系统继续使用既有目录、生成链和配置布局
   **And** 后续 story 仅在需要时创建或修改对应实体、接口和页面。

## Tasks / Subtasks

- [ ] 1. 锁定 brownfield 实现基线，不创建平行工程（AC: 1, 2）
  - [ ] 盘点并确认继续沿用现有根级实现单元：`api/`、`rpc/`、`consumer/`、`job/`、`web-admin/`、`flutter-mall/`、`pkg/`、`docs/`、`script/`
  - [ ] 禁止新增第二套 admin/front/mobile scaffold，禁止把“初始化”实现为新项目迁移
  - [ ] 如需补充初始化说明，仅更新既有 `docs/` 或 `_opcos/` 工件，不新增平行工程目录
- [ ] 2. 在既有链路上完成依赖准备（AC: 1）
  - [ ] 后端使用现有 `make build` / `make deps` 约定准备依赖和构建产物
  - [ ] 管理端在 `web-admin/` 内沿用 `package-lock.json` 执行 `npm install`
  - [ ] 商城端在 `flutter-mall/` 内沿用 `pubspec.lock` 执行 `flutter pub get`
- [ ] 3. 修复阻断基线初始化的显性脚本问题（AC: 1, 2）
  - [ ] 修正 `makefile` 与 `service_manager.sh` 中对不存在 `target/web-api/web-api` 的启动调用
  - [ ] 修正 `service_manager.sh` 中 `"pms"` 分支误调 `oms_service` 的错误
  - [ ] 修正后重新验证基础启动脚本不再引用不存在的服务入口
- [ ] 4. 固化生成链与编辑边界（AC: 2）
  - [ ] `.api`、`.proto`、`rpc/*/gen/generator.go` 仍作为生成源定义；变更后通过 `make gen` / `make model` 回写产物
  - [ ] 不手改 `api/*/internal/handler/routes.go`、`rpc/*/*pb.go`、`rpc/*/gen/query/*` 等生成文件
  - [ ] 在执行 `make gen` 前核对本地 `goctl` 版本，避免 `@latest` 与仓库现有 `goctl 1.9.2` 产物风格漂移
- [ ] 5. 确认后续 story 的扩展落点仍在现有结构内（AC: 2）
  - [ ] 后台治理扩展优先落在 `api/admin/internal/middleware`、`api/admin/internal/svc`、`rpc/sys|ums|pms|oms|sms|cms`
  - [ ] 前台网关扩展优先落在 `api/front/internal/*`，保持 REST gateway + gRPC service + MQ/job 拓扑
  - [ ] Web Admin 继续使用 `index.tsx + service.ts + data.d.ts + components/*` 模式与 Umi `request`
  - [ ] Flutter Mall 继续使用 `Provider + Dio + HttpUtil + service_url.dart`，禁止在 Widget 内私建裸网络栈
- [ ] 6. 输出初始化验收记录（AC: 1, 2）
  - [ ] 记录执行过的命令、发现的脚本缺陷以及残余环境阻塞
  - [ ] 验证不存在新平行工程/新脚手架目录，且既有目录、生成链、配置布局保持可继续开发

### Developer Context

- 当前仓库是 brownfield 多端电商项目，不是空白脚手架。根级已有后端网关、RPC 服务、消息消费者、定时任务、Web Admin、Flutter Mall、共享 `pkg/`、部署脚本和文档工件。
- `make build` 会先复制各服务配置到 `target/<service>/`，再构建 `sys/ums/oms/pms/cms/sms/search`、`admin-api`、`front-api`、`job`、`consumer`。`target/` 是构建产物目录，不是源码目录。[Source: `makefile`]
- `service_manager.sh` 提供按服务构建/重启的本地工作流，后续若只改某个服务，应优先复用此脚本而不是再造一套本地启动脚本。[Source: `service_manager.sh`]
- `web-admin/` 已存在 `package-lock.json` 与 `node_modules/`，`flutter-mall/` 已存在 `pubspec.lock` 与 `build/`；依赖真相源仍应以 lock 文件为准，不以当前工作区缓存目录为准。[Source: `web-admin/package.json`; `flutter-mall/pubspec.yaml`]
- 当前 `pkg/` 实际仅有 `errorx`、`es`、`mq`、`pointerprocess`、`time_util`。架构文档里规划的 `pkg/scope`、`pkg/audit`、`pkg/idempotency` 目前还不存在，因此后续 story 不能假设这些共享包已就绪。[Source: `_opcos/planning-artifacts/1-new-feature/architecture.md#Project-Structure--Boundaries`; `pkg/`]

### Existing Auth / Scope State

- Admin 网关当前通过生成的 `routes.go` + `rest.WithJwt(...)` + `CheckUrl` 中间件工作，后续治理能力必须扩展现有链路，不能新增第二套路由/鉴权入口。[Source: `api/admin/internal/handler/routes.go`; `api/admin/internal/middleware/checkurlmiddleware.go`]
- Admin JWT 当前 claims 仅包含 `userId`、`userName`、`deptID`、`deptName`，尚未承载 `platformId`、`tenantId`、`merchantId`、`dataScope` 等平台化字段。[Source: `rpc/sys/internal/logic/userservice/loginlogic.go`]
- Member JWT 当前 claims 仅包含 `memberId`、`memberName`、`mobile`，尚未承载租户/商户入口上下文。[Source: `rpc/ums/internal/logic/memberinfoservice/createtoken.go`]
- `AddLogMiddleware` 已存在于 `api/admin/internal/middleware`，但当前生成路由实际只挂了 `CheckUrl`；后续审计上下文应沿现有中间件链扩展，而不是旁路实现。[Source: `api/admin/internal/svc/servicecontext.go`; `api/admin/internal/handler/routes.go`; `api/admin/internal/middleware/addloglmiddleware.go`]
- `sys_role.data_scope` 已存在于现有 proto / model / query 生成物中，说明“数据范围”已有既有语义，后续平台化作用域设计应复用而非重造另一套 role scope 词汇。[Source: `rpc/sys/proto/role.proto`; `rpc/sys/gen/model/sys_role.gen.go`; `rpc/sys/gen/query/sys_role.gen.go`]

### Known Baseline Risks

- `make start` 与 `service_manager.sh start` 都会尝试启动不存在的 `target/web-api/web-api`，当前仓库中也不存在 `api/web` 或 `web-api` 源目录。这是基线初始化必须先修掉的脚本阻断项。[Source: `makefile`; `service_manager.sh`]
- `service_manager.sh` 的 `"pms"` case 当前误调 `oms_service`，会导致商品服务增量构建/重启命令落到订单服务上。[Source: `service_manager.sh`]
- `makefile` 会自动安装 `github.com/zeromicro/go-zero/tools/goctl@latest`，但仓库中的已生成路由头仍标记为 `goctl 1.9.2`。若不先对齐生成器版本，执行 `make gen` 很可能引入大面积无关 diff。[Source: `makefile`; `api/admin/internal/handler/routes.go`; `api/front/internal/handler/routes.go`]
- 当前工作区是 dirty tree，且 `_opcos/` 与若干 Flutter 文件已有本地变更。实现本 story 时不得顺手“清理”无关生成物、构建物或用户改动。

### Technical Requirements

- 依赖准备必须围绕现有仓库完成，不允许新建独立 template repo、平行 `admin-web`、平行 `mobile-app` 或临时 `demo-api`。
- 后端初始化默认命令以 `make build` 为准；若只需单服务重启，可用 `service_manager.sh <service>`。不要新增另一套 `scripts/bootstrap-*` 作为主入口。[Source: `makefile`; `service_manager.sh`]
- 若本 story 不涉及 `.api`、`.proto`、GORM 生成源修改，则不要为了“对齐最新工具”主动执行 `make gen` / `make model`。
- `web-admin` 的请求仍需走 `/api/` 代理到 `http://127.0.0.1:8888/`，不要在初始化阶段把 host 写死进页面或 service 模块。[Source: `web-admin/config/proxy.ts`; `_opcos/project-context.md`]
- `flutter-mall` 的网络调用仍需集中走 `HttpUtil` 与 `service_url.dart`，不要把“初始化”做成在 Widget 内部直接 new `Dio` 的临时改法。[Source: `_opcos/project-context.md`; `flutter-mall/lib/utils/http_util.dart`; `flutter-mall/lib/config/service_url.dart`]

### Architecture Compliance

- 继续遵循 Architecture 中已确定的固定拓扑：`REST 网关 + gRPC 服务 + RabbitMQ 异步事件 + Job 补偿`。基线故事不应改变这一通信拓扑。[Source: `_opcos/planning-artifacts/1-new-feature/architecture.md#Core-Architectural-Decisions`]
- 保持 MySQL 为交易与治理真相源，Redis 只做缓存/幂等/协调，Elasticsearch 只做搜索读模型，MongoDB 只用于现有文档/报表型扩展。[Source: `_opcos/planning-artifacts/1-new-feature/architecture.md#Data-Architecture`]
- Admin 与 Front 网关错误封装和中间件链并不对称；基线初始化不能假设两端共享完全相同的运行时行为。[Source: `_opcos/project-context.md`; `_opcos/planning-artifacts/1-new-feature/architecture.md#Authentication--Security`]
- 本 story 完成后，后续平台治理 story 仍应在既有 `handler -> logic -> svc` 和共享 `pkg/` 基础设施模式内增量推进。[Source: `_opcos/project-context.md`; `_opcos/planning-artifacts/1-new-feature/architecture.md#Implementation-Patterns--Consistency-Rules`]
