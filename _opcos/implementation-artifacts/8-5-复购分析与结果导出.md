# Story 8.5: 复购分析与结果导出

Status: ready-for-dev

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a 平台、租户或商户运营人员,
I want 查看复购表现并导出分析结果,
so that 我可以基于留存结果调整消息召回、活动策略和后续经营动作。

## Acceptance Criteria

1. **Given** 平台已累计形成复购相关经营数据 **When** 运营按时间、活动、渠道、租户和商户筛选复购分析 **Then** 系统展示复购相关指标并支持导出分析结果 **And** 导出的数据口径与页面展示保持一致。

2. **Given** 运营角色仅拥有部分主体的查看权限 **When** 导出复购分析结果 **Then** 系统仅导出被授权主体的数据 **And** 不允许跨租户或跨商户导出未授权结果。

## AC 覆盖矩阵

- **AC1（复购指标 + 导出一致性）**：Task 1-4、5.1-5.4
- **AC2（作用域隔离 + 导出权限）**：Task 1.2、1.4、2.1-2.4、3.1-3.4、4.2、5.1-5.3

## 背景与关键风险（必须优先阅读）

> **⚠️ CRITICAL - 复购率口径必须先锁死：** PRD 已明确“复购率按 180 天窗口内完成第二次及以上支付的买家占比计算”。8.5 不能把“累计下单数 > 1”“累计支付次数 > 1”“当前查询窗口内下单两次”混成一个指标；页面、导出、接口注释和测试必须围绕同一口径。
>
> **⚠️ CRITICAL - 会员汇总表不是多主体真相源：** `ums_member_info`、`ums_member_statistics_info` 虽然有订单数、累计消费等字段，但没有 `platform_id / tenant_id / merchant_id`。8.5 只能把它们当展示补充，不能把它们当复购分子/分母来源；复购 cohort 必须来自 `oms_order_main` 的有效支付订单事实。
>
> **⚠️ CRITICAL - 必须复用 8.4 的 scope / channel / activity 契约：** 当前工作区中的 8.4 实现已经沉淀了 `pkg/operatefunnel`、`QueryOperateFunnelDashboard`、`QueryOperateActivityOptions` 和统一 `ResolveQueryGovernanceScope` 透传语义。8.5 不允许再发明另一套渠道枚举、活动类型、时间格式或 scope 解析方式。
>
> **⚠️ CRITICAL - 导出与页面必须走同一条查询链路：** 不能页面走聚合 RPC、导出再手写另一套 SQL，导致“页面 128、导出 131”。导出必须直接复用同一批 query builder / RPC / Admin Logic，并携带相同筛选条件、相同 `trackingStartedAt` / `partialMetrics` 语义。
>
> **⚠️ CRITICAL - 大结果导出必须控制内存并保护敏感字段：** 导出要复用仓库已引入的 `excelize/v2`，在明细行数较大时优先采用流式写法；会员手机号、昵称等展示字段默认脱敏，不能因为“导出方便”而突破最小必要原则。
>
> **⚠️ CRITICAL - 退款 / 取消边界必须显式定义：** 8.5 中“有效支付订单”默认限定为 `pay_time IS NOT NULL`、`is_deleted = 0` 且排除已取消 / 已退款订单，避免把无效交易算进复购率；若后续需要观察“支付后退款”影响，应以单独字段呈现，而不是静默混入复购指标。
>
> **⚠️ CRITICAL - 活动筛选存在可信起点：** 8.4 才开始系统化补齐 `activity_type / activity_id` 与归因字段；当 8.5 按活动筛选复购结果时，如查询窗口早于归因字段稳定落地时间，必须显式返回 `trackingStartedAt` / `partialMetrics`，不得把缺失历史伪装成真实 0。

## 明确非目标（本 Story 不做）

- 不建设离线报表中心、异步导出任务队列或对象存储下载链接；8.5 继续沿用当前后台同步下载模式。
- 不建设“按消息模板 / 推送渠道 / 站内消息 ID”的精细归因模型；本 Story 聚焦订单维度的复购结果与活动 / 渠道筛选。
- 不重写 8.4 的漏斗事实表、漏斗 API 或页面基础布局；8.5 只在既有 `OperateDashboard` 结构上扩展复购分析与导出。
- 不顺手升级 `go-zero`、`goctl`、`echarts`、`antd` 或新增另一套 Excel 导出库。

## 实施顺序（必须按序推进）

1. 先锁定复购口径、有效支付订单定义、导出列和脱敏规则，再开始写 SQL / RPC。
2. 先在 OMS 落复购汇总与明细查询能力，再补 Admin API 聚合、导出 Handler 和权限资源。
3. 再扩展 `OperateDashboard` 页面与导出按钮，确保页面与导出共用同一组筛选参数。
4. 最后补 `trackingStartedAt` 提示、导出一致性校验、跨作用域权限测试和前端下载验证。

## Tasks / Subtasks

### 一、统一复购口径、导出列与共享契约

#### Task 1 (AC: 1, 2): 定义复购指标、有效订单边界与导出字段

**目标：** 先把“什么叫复购、什么叫有效支付、导出到底导什么”写死，再进入实现。

- [ ] 1.1 定义“有效支付订单”：`oms_order_main` 中 `is_deleted = 0`、`pay_time IS NOT NULL`，且默认排除 `order_status = 5(已取消)`、`6(已退款)`；`2/3/4/7` 视为可参与复购分析的有效支付状态。
- [ ] 1.2 定义“复购订单”：在当前查询作用域内，满足筛选条件的分析订单，如果同一 `member_id` 在该订单 `pay_time` 之前 180 天内已有至少 1 笔同作用域的有效支付订单，则该订单记为“复购订单”。
- [ ] 1.2.1 把“同一作用域”写成不可歧义的三层规则：
  - 平台级查询：按 `platform_id` 聚合，可跨该平台下全部 `tenant_id / merchant_id` 回看前序有效支付订单。
  - 租户级查询：固定 `platform_id + tenant_id` 回看，不跨租户。
  - 商户级查询：固定 `platform_id + tenant_id + merchant_id` 回看，不跨商户。
- [ ] 1.3 定义“复购买家”：在当前查询结果中，至少拥有 1 笔复购订单的去重买家；`repeatRate = repeatBuyerCount / paidBuyerCount`。
- [ ] 1.4 复购总览至少返回：`paidBuyerCount`、`repeatBuyerCount`、`repeatRate`、`repeatOrderCount`、`repeatGmv`、`avgDaysToRepeat`；页面与导出不得再临时拼接第二套公式。
- [ ] 1.5 明确活动 / 渠道筛选只作用于“当前分析订单”，而复购判定所依赖的“上一笔订单”只要求同作用域有效支付，不强制与当前订单拥有相同 `activity_type / activity_id / channel`，避免把营销筛选误解释为“同活动复购唯一真相”。
- [ ] 1.6 复购趋势默认按天返回，不做小时级趋势；如果查询窗口较长，前端通过图表抽样展示，不在 8.5 引入新的周 / 月时间桶语义。
- [ ] 1.7 详情表 / 导出列至少包含：`memberId`、`nicknameMasked`、`mobileMasked`、`firstValidPayTime`、`latestRepeatPayTime`、`repeatOrderCount`、`repeatGmv`、`latestChannel`、`latestActivityType`、`latestActivityId`、`platformId/tenantId/merchantId`。
- [ ] 1.8 当查询依赖活动归因字段且历史不完整时，沿用 8.4 的 `trackingStartedAt` / `partialMetrics` 响应模式，并在页面与导出说明中同步体现。

## Dev Notes

### 架构约束（必须遵守）

1. **OMS 订单事实才是复购真相源：** 复购统计从 `oms_order_main` 出发，UMS 只补展示信息，不补口径。
2. **Scope 优先：** 所有 query / export 都先解析当前治理范围，再把 scope 透传到 OMS / UMS / SMS；不允许前端只传 tenant / merchant ID 就直接越权生效。
3. **与 8.4 共用 operate dashboard 契约：** 复购分析沿用 `OperateDashboard` 的活动筛选、作用域筛选、`trackingStartedAt` / `partialMetrics` 提示语义和页面容器，不再平行造一个“复购报表”体系。
4. **生成链优先：** 新增 Admin API / RPC / UMS 批量 brief 查询时，只改 `.api` / `.proto` 源文件并重新生成，不碰生成产物。
5. **导出复用页面查询链路：** 页面查询和导出不能各维护一份 SQL；导出只是同一数据的另一种输出形态。

### 关键数据源与口径说明

| 主题 | 真相源 | 约束 |
| --- | --- | --- |
| 复购判定 | `oms_order_main` | 基于有效支付订单与 180 天回看窗口 |
| 活动筛选 | `oms_order_main.activity_type/activity_id` | 8.4 新补字段，历史存在可信起点 |
| 渠道筛选 | `oms_order_main.source_type` | 继续复用 `pkg/operatefunnel` 的统一映射 |
| 会员展示 | UMS `member_info` RPC | 仅作昵称 / 手机号 / 会员等级补充，默认脱敏 |
| 活动选项 | SMS `QueryOperateActivityOptions` | 复用 8.4 已有活动下拉，不前端硬编码 |
| 导出文件 | Admin API + `excelize/v2` | 页面与导出口径一致，优先流式写入 |
