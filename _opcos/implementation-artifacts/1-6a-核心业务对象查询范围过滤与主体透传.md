# Story 1.6A: 核心业务对象查询范围过滤与主体透传

Status: review

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a 平台管理员,
I want 为商品、订单、优惠券、库存和内容查询链路建立统一主体透传与范围过滤,
so that 不同租户和商户只能看到属于自己的业务对象。

## Acceptance Criteria

1. **Given** 平台级、租户级、商户级主体已经建立
   **When** 用户在对应主体范围内查询商品、订单、优惠券、库存和内容
   **Then** 系统自动透传并校验主体标识
   **And** 仅返回当前主体被授权的数据与聚合结果。
2. **Given** 查询链路经过缓存、搜索读模型或列表过滤链
   **When** 系统生成查询条件、缓存 key 或读模型过滤条件
   **Then** 主体范围信息必须被带入
   **And** 不得发生跨租户、跨商户的数据泄漏。

## Dev Notes

### Scope Guardrails

- 本 story 只负责“读路径”的主体透传与范围过滤，包括列表、详情、聚合、搜索和读缓存，不负责核心写操作的越权校验与治理审计闭环；后者属于 Story 1.6B 与 Story 1.7 的范围。[Source: `_opcos/planning-artifacts/1-new-feature/epic.md#Story-16A-核心业务对象查询范围过滤与主体透传`; `_opcos/planning-artifacts/1-new-feature/epic.md#Story-16B-核心业务对象关键写操作校验与越权审计`; `_opcos/planning-artifacts/1-new-feature/epic.md#Story-17-治理审计与安全事件检索`]
- 不要新建平行的 `query-scope-service`、`merchant-read-gateway` 或第二套主体模型；应复用现有 `pkg/scope/governance.go`、`pkg/scope/role_scope.go`、`rpc/sys/internal/logic/common/governance.go` 的 scope 基线，把能力扩展到 `pms/oms/sms/cms/search` 读链路。[Source: `pkg/scope/governance.go`; `pkg/scope/role_scope.go`; `rpc/sys/internal/logic/common/governance.go`; `_opcos/planning-artifacts/1-new-feature/architecture.md#Project-Structure--Boundaries`]
- 当前仓库没有独立 inventory 领域服务，库存查询实际附着在 `ProductSku` 和商品搜索文档中，所以本 story 的“库存范围过滤”必须覆盖 `product_sku` 读逻辑和搜索读模型，而不是等待未来单独的库存微服务。[Source: `rpc/pms/proto/product_sku.proto`; `rpc/pms/internal/logic/productskuservice/queryproductskulistlogic.go`; `rpc/search/search.proto`]

### Story Foundation / Business Context

- PRD 明确要求平台、租户、商户之间必须实现逻辑隔离，商品、订单、营销、内容、配置和日志都要带显式主体标识；高严重级跨主体数据泄漏缺陷必须为 0。[Source: `_opcos/planning-artifacts/1-new-feature/prd.md#平台租户与多商户治理`; `_opcos/planning-artifacts/1-new-feature/prd.md#非功能需求`]
- FR47 要求用户、商品、订单、营销、内容、配置、日志按租户/商户逻辑隔离；FR49 要求商户管理员只能管理自己的商户数据；FR50/FR51 要求角色、可见菜单与业务对象查询结果和主体范围保持一致。Story 1.6A 是这些 FR 在读链路上的直接兑现。[Source: `_opcos/planning-artifacts/1-new-feature/prd.md#平台租户与多商户治理`]
- UX 要求用户先明确当前上下文，再执行高密度查询与决策；错误反馈必须说明当前范围和恢复动作。对商品、订单、优惠券、专题等后台查询页，这意味着 scope 不只是后端过滤条件，也必须是 UI 可见的工作上下文。[Source: `_opcos/planning-artifacts/1-new-feature/ux-design.md#Journey-Patterns`; `_opcos/planning-artifacts/1-new-feature/ux-design.md#Scope-Context-Bar`; `_opcos/planning-artifacts/1-new-feature/ux-design.md#Recovery-first-Feedback`]

- `sys` 域的用户、角色、岗位、部门、字典、通知等 proto 已经大量使用 `GovernanceScope`，但 `rpc/pms/proto/product_spu.proto`、`rpc/pms/proto/product_sku.proto`、`rpc/oms/proto/order_main.proto`、`rpc/sms/proto/coupon.proto`、`rpc/cms/proto/subject.proto` 仍然没有任何治理范围字段，详情请求大多仍是裸 `id`。[Source: `rpc/sys/proto/user.proto`; `rpc/sys/proto/dept.proto`; `rpc/pms/proto/product_spu.proto`; `rpc/pms/proto/product_sku.proto`; `rpc/oms/proto/order_main.proto`; `rpc/sms/proto/coupon.proto`; `rpc/cms/proto/subject.proto`]

### Technical Requirements

- 主体范围必须在 gateway 或 service 入口处归一化一次，然后沿链路显式透传；不要在每个 repo/query helper 里零散判断 `tenantId != 0`、`merchantId != 0` 去“猜”当前主体。[Source: `pkg/scope/governance.go`; `rpc/sys/internal/logic/common/governance.go`; `_opcos/planning-artifacts/1-new-feature/architecture.md#Authentication--Security`]
- 详情查询必须在读取主记录前后完成 scope 校验，确保“知道全局 ID”也不能跨主体读取；尤其是订单详情、商品详情、优惠券详情、专题详情不能继续接受裸 `id` 后直接出库。[Inference from: `rpc/pms/proto/product_spu.proto`; `rpc/pms/proto/product_sku.proto`; `rpc/oms/proto/order_main.proto`; `rpc/sms/proto/coupon.proto`; `rpc/cms/proto/subject.proto`]
- 平台管理员可以在合法的上下文中查看任一租户/商户范围；租户级和商户级用户只能在自己的 scope 内查询。这个约束需要落在服务端，不得仅靠前端禁用字段。[Source: `_opcos/planning-artifacts/1-new-feature/prd.md#平台租户与多商户治理`; `pkg/scope/role_scope.go`]
- 由于现有业务表没有主体字段，实施顺序必须是：补表结构/回填主体 -> 生成模型 -> 调整 proto/API -> 修改查询逻辑 -> 回归 ES/缓存/页面，而不是反过来先上过滤条件。[Inference from: `script/sql/pms/pms_product_spu.sql`; `script/sql/pms/pms_product_sku.sql`; `script/sql/oms/order_main.sql`; `script/sql/sms/sms_coupon.sql`; `script/sql/cms/cms_subject.sql`]
- `home/index`、推荐位、搜索结果和任何 summary/count 都要与列表数据复用同一 scope 条件，不能把“聚合结果先算好再展示给所有主体”当成例外路径。[Source: `api/front/internal/logic/home/index_logic.go`; `rpc/search/internal/logic/search_logic.go`; `_opcos/planning-artifacts/1-new-feature/ux-design.md#Scope-Context-Bar`]

### Architecture Compliance

- 继续遵循 `admin-api / front-api -> rpc/pms|oms|sms|cms|search -> MySQL/Redis/ES` 的边界，不允许为 scope 过滤引入页面直连数据库、前端拼 SQL 或跨域直接查 ES 的捷径。[Source: `_opcos/planning-artifacts/1-new-feature/architecture.md#Project-Structure--Boundaries`; `_opcos/project-context.md`]
- MySQL 仍然是真相源，ES 只是读模型；因此 scope 字段必须先进入 MySQL 与同步消息，再进入 ES 文档和搜索过滤，而不是把 ES 里额外加个 tenant 字段就宣称隔离完成。[Source: `_opcos/planning-artifacts/1-new-feature/architecture.md#Data-Architecture`; `consumer/internal/mq/product/syn_product_to_es_logic.go`; `rpc/search/search.proto`]
- Redis / 查询缓存 key 要按架构要求包含 scope 前缀，示例格式为 `za:{env}:{scope}:{domain}:{entity}:{id}`。如果 scope 不进入 key，缓存命中本身就是数据泄漏入口。[Source: `_opcos/planning-artifacts/1-new-feature/architecture.md#Data-Architecture`]
- 共享治理 helper 优先放在 `pkg/scope/`、`pkg/audit/` 或网关侧 `common` 目录；不要在 `pms/oms/sms/cms` 四个域里各自复制一份 `BuildTenantWhere` / `CurrentMerchant` 私有实现。[Source: `_opcos/project-context.md`; `pkg/scope/governance.go`; `rpc/sys/internal/logic/common/governance.go`]

### Search / Cache / Async Requirements

- 商品搜索文档当前缺少主体字段，`search` 服务只按类目、品牌和关键字过滤；如果不把 scope 写进文档与查询，任何 tenant/merchant 维度的“搜索结果隔离”都是伪命题。[Source: `rpc/search/search.proto`; `rpc/search/internal/logic/search_logic.go`; `rpc/search/internal/logic/search_simple_logic.go`]
- `SynProductToEs` 当前根据消息中的全局商品 ID 重新查询商品详情并入 ES，这意味着只要商品主表没有 scope、消息没有 scope、ES 文档没有 scope，整条异步链都会天然跨主体。Story 1.6A 必须一次性修这三层。[Source: `consumer/internal/logic/product/add_product_to_es_logic.go`; `consumer/internal/mq/product/syn_product_to_es_logic.go`; `rpc/search/internal/logic/create_logic.go`]
- 前台首页当前直接查询推荐专题、热销商品、新品商品，没有任何 tenant/merchant 过滤。即便后台页做了隔离，如果首页聚合继续走全平台查询，跨主体泄漏仍然存在。[Source: `api/front/internal/logic/home/index_logic.go`; `api/front/internal/logic/product/product/query_product_list_logic.go`]
- 优惠券域存在“双 scope”风险：治理范围要表达租户/商户归属，而 `coupon_scope` 继续表达优惠券适用对象；两者必须在 proto、表结构、变量命名和 UI 文案上明确分离，否则开发和测试都很容易误判“scope 已支持”。[Source: `rpc/sms/proto/coupon_scope.proto`; `api/front/internal/logic/member/coupon/query_coupon_list_by_cart_logic.go`]
