# Story 4.3: 秒杀活动配置

Status: in-progress

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a 运营人员,
I want 配置秒杀活动的时段、商品和作用域,
So that 我可以围绕限时促销组织有明确边界的转化活动。

## Acceptance Criteria

1. **Given** 运营人员拥有营销配置权限 **When** 创建或编辑秒杀活动 **Then** 系统保存活动时段、适用商品和作用域 **And** 后台展示配置当前的可发布状态。

2. **Given** 活动到期、停用或资源配置缺失关键字段 **When** 运营查看或发布配置 **Then** 系统明确标识不可生效原因 **And** 前台不会继续展示失效秒杀内容。

### 状态语义映射（Story 4.3 核心关注点）

**秒杀活动状态（sms_seckill_activity.status）：**
| 数据库值 | DDL 注释 | 本轮 Story 映射 | 前端展示 |
|---------|---------|----------------|---------|
| 0 | 上线 | 已发布/活动中 | 绿色标签"已上线" |
| 1 | 下线 | 草稿/已下线 | 灰色标签"已下线" |

**注意：status 语义方向与优惠券相反**（优惠券 0=草稿, 1=进行中；秒杀 0=上线, 1=下线）。前端 Switch 已适配此逻辑。

**活动可发布状态判断（上线校验）：**
- `end_time` 晚于当前时间
- 至少有一个已上架的秒杀商品
- `is_enabled = 1`
- 不存在同时段的重复活动（可降级）

### Architecture Compliance

- **作用域模型**：`sms_seckill_activity` 表当前缺少 `platform_id`/`tenant_id`/`merchant_id`，需补充 DDL 并在写入时填充作用域（参考 `sms_coupon` 的模式）
- **生成代码约束**：所有 model 通过 `gorm/gen` 生成（`query.SmsSeckillActivity`），不可手改
- **通信拓扑**：`web-admin → admin-api → sms-rpc`，严格遵循 REST + gRPC 分层
- **Logic 层编排**：所有校验逻辑在 sms-rpc `logic` 层或 admin-api `logic` 层，handler 只做参数解析和响应
- **错误处理**：sms-rpc 使用 `logc.Errorf` 记录内部错误 + `errors.New` 返回用户可理解信息；admin-api 使用 `errorx.NewDefaultError(s.Message())` 封装 gRPC 错误
- **前端页面模式**：`index.tsx + service.ts + data.d.ts + components/*`
- **命名约束**：后端使用 `SeckillActivity`（seckill），前端目录使用 `FlashPromotion`，二者已通过 API 路由映射，不要试图统一重命名
