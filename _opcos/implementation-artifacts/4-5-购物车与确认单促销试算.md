# Story 4.5: 购物车与确认单促销试算

## Status: In Progress

## Story

- **As a** 消费者
- **I want** 在购物车和确认订单阶段看到促销、优惠券和积分试算结果
- **So that** 我可以在提交订单前确认最终金额和权益使用方式

## FRs Implemented

FR34

## Acceptance Criteria (AC)

### AC-1: 购物车促销试算展示
**Given** 购物车中存在可参与促销或可用优惠券的商品
**When** 消费者进入购物车页面
**Then** 系统展示每个商品的促销信息（促销类型、优惠金额）和金额试算结果
**And** 折扣、运费和实付金额拆分口径一致

### AC-2: 确认单完整试算
**Given** 消费者从购物车选择商品进入确认订单页
**When** 页面加载完成
**Then** 系统调用 `generateConfirmOrder` API，返回购物车促销信息、收货地址列表、可用/不可用优惠券、积分余额、积分使用规则和金额试算（商品合计、运费、促销优惠、应付金额）
**And** 前端正确展示所有试算结果，不使用硬编码金额

### AC-3: 优惠券失效/门槛不满足处理
**Given** 优惠券失效、门槛不满足或促销规则冲突
**When** 消费者尝试应用优惠
**Then** 系统明确指出不可用原因并重新计算金额
**And** 保留当前上下文而不是让用户从头重新选择

### AC-4: 促销类型完整覆盖
**Given** 商品设置了不同促销类型（0-无促销/1-单品促销/2-会员价/3-阶梯价/4-满减/5-限时购）
**When** 这些商品被加入购物车并进行试算
**Then** 每种促销类型的优惠金额、提示信息、真实库存和赠送积分/成长值都正确计算并返回
**And** 被注释的 `ReduceAmount`、`RealStock`、`Integration`、`Growth` 字段逻辑全部启用

### AC-5: 金额精度与一致性
**Given** 购物车试算和确认单试算使用相同的 `QueryCartListPromotion` 函数
**When** 两个页面分别展示金额
**Then** 相同商品在两个页面上的促销优惠金额完全一致
**And** 金额使用整数分（int64）而非 float32 计算，避免浮点精度丢失

## Tasks / Subtasks

### Task 1: 后端——启用并修复 QueryCartListPromotion 被注释逻辑

**文件**: `api/front/internal/logic/order/cart/query_promotion_list_logic.go`

**Why**: 当前 `QueryCartListPromotion` 中大量关键字段赋值被注释（`RealStock`、`Integration`、`Growth`），促销类型3（阶梯价）和类型4（满减）的 `ReduceAmount` 计算也被注释。这导致前端无法获取真实的优惠金额和库存信息。

**详细变更**:

1.1 **启用所有促销类型的 `RealStock`、`Integration`、`Growth` 赋值**
- 在 `handleNoReduce` 函数和所有 `promotionType` 分支中，取消注释以下三行：
  ```go
  cartPromotionItem.RealStock = skuStock.Stock - skuStock.LockStock
  cartPromotionItem.Integration = product.GiftPoint
  cartPromotionItem.Growth = product.GiftGrowth
  ```
- 涉及位置：`handleNoReduce`、`promotionType==1`、`promotionType==2`、`promotionType==3`（含 productLadder != nil 分支）、`promotionType==5`

1.2 **修复 promotionType==3（阶梯价）的 ReduceAmount 计算**
- 取消注释：`cartPromotionItem.ReduceAmount = skuStock.Price - productLadder.Discount*skuStock.Price`
- **注意类型兼容**：`skuStock.Price` 是 `int64`，`productLadder.Discount` 是 `float64`。需要确保计算正确：
  ```go
  cartPromotionItem.ReduceAmount = int64(float64(skuStock.Price) - productLadder.Discount*float64(skuStock.Price))
  ```

1.3 **修复 promotionType==4（满减）的金额计算**
- 取消注释满减总价计算：
  ```go
  for _, item := range itemList {
      skuStock := getSkuStock(skuStockList, item.ProductSkuId)
      amount = amount + skuStock.Price*int64(item.Quantity)
  }
  ```
- 取消注释满减分摊计算：
  ```go
  cartPromotionItem.ReduceAmount = (skuStock.Price / amount) * productFull.ReducePrice
  ```
- **注意**：当 `amount == 0` 时需要防除零错误

1.4 **校验 `productCartMap` 分组逻辑的 append bug**
- 当前代码第 108-114 行存在 append 后未回写 map 的问题：
  ```go
  // 现有代码（有 bug）
  listData = append(listData, item)
  // 缺少: productCartMap[item.ProductId] = listData
  ```
- 当 `listData` 已存在时，`append` 可能创建新 slice 但未更新 map。需要确保 else 分支中的 append 结果回写到 map。

**验收**:
- 6 种促销类型均返回正确的 `ReduceAmount`、`RealStock`、`Integration`、`Growth`
- `go build ./api/front/...` 编译通过

### Task 2: 后端——修复 GenerateConfirmOrder 金额精度问题

**文件**: `api/front/internal/logic/order/order/generate_confirm_order_logic.go`

**Why**: 当前 `CalcAmount` 使用 `float32`（精度约 7 位有效数字），电商金额计算不应使用浮点数。同时，`CarItemtPromotionListData.Price` 是 `float32` 但 `ReduceAmount` 是 `int64`，混合运算存在隐患。

**详细变更**:

2.1 **统一金额为 int64（单位：分）**
- 修改 `types.go` 中 `CalcAmount` 的字段类型从 `float32` 改为 `int64`：
  ```go
  type CalcAmount struct {
      TotalAmount     int64 `json:"totalAmount"`
      FreightAmount   int64 `json:"freightAmount"`
      PromotionAmount int64 `json:"promotionAmount"`
      PayAmount       int64 `json:"payAmount"`
  }
  ```
- **前提确认**：检查 `CarItemtPromotionListData.Price` 字段——当前是 `float32`。如果后端数据库中价格存储为分（int），则应将 `Price` 也改为 `int64`。如果价格存储为元（float），则保持 `float32` 但 `CalcAmount` 内部计算需要转换。
- **风险评估**：修改 `types.go` 可能影响其他使用 `CalcAmount` 的地方。需要全局搜索 `CalcAmount` 确认影响范围。

2.2 **修正确认单金额计算逻辑**
- 当前计算（第 119-127 行）：
  ```go
  totalAmount = totalAmount + item.Price*float32(item.Quantity)
  promotionAmount = promotionAmount + float32(item.ReduceAmount)*float32(item.Quantity)
  ```
- 根据 Task 2.1 的类型决策，将计算改为统一类型

**验收**:
- 金额计算不使用 `float32` 运算
- 试算结果中 `totalAmount - promotionAmount == payAmount`（运费为0时）

### Task 3: 后端——优惠券门槛提示与不可用原因

**文件**: `api/front/internal/logic/member/coupon/query_coupon_list_by_cart_logic.go`

**Why**: AC-3 要求系统明确指出优惠券不可用原因。当前 `QueryCouponList` 只将优惠券分为 `enableList`/`disableList`，但不返回不可用原因。

**详细变更**:

3.1 **在 `CouponData` 中增加 `disableReason` 字段**
- 在 `types.go` 中的 `CouponData` 结构体增加：
  ```go
  DisableReason string `json:"disableReason,optional"` // 不可用原因
  ```
- 在 `QueryCouponList` 函数中，当优惠券被放入 `disableList` 时，根据判断条件填写原因：
  - 门槛不满足：`"订单金额未满 ¥X.XX"`
  - 时间不在有效期：`"优惠券不在有效期内"`
  - 作用域不匹配：`"该优惠券不适用于当前商品"`

**验收**:
- `disableList` 中每张优惠券都有 `disableReason`
- `enableList` 中 `disableReason` 为空字符串

### Task 4: Flutter——购物车页面对接促销试算 API

**文件变更**:
- `flutter-mall/lib/config/service_url.dart`
- `flutter-mall/lib/model/cart_list.dart`
- `flutter-mall/lib/provider/cart_model.dart`
- `flutter-mall/lib/view/cart/cart.dart`

**Why**: 当前购物车页面只调用 `queryCarItemList`（返回基础购物车数据），不调用 `queryPromotionList`（返回含促销信息的数据）。前端 `CartData` 模型缺少 `promotionMessage`、`reduceAmount`、`realStock` 等促销字段。

**详细变更**:

4.1 **新增促销试算 URL**
- 在 `service_url.dart` 中新增：
  ```dart
  // 购物车促销试算
  const cartPromotionUrl = "$baseUrl/api/order/queryPromotionList";
  // 生成确认单
  const generateConfirmOrderUrl = "$baseUrl/api/order/generateConfirmOrder";
  ```

4.2 **扩展 CartData 模型或新建 CartPromotionData 模型**
- 方案A（推荐）：新建 `flutter-mall/lib/model/cart_promotion.dart`，包含完整的促销字段：
  ```dart
  class CartPromotionData {
    // 基础字段（与 CartData 相同）
    int id, memberId, productId, productSkuId, quantity;
    double price;
    String productName, productSubTitle, productPic, productSkuCode, productAttr, productBrand;
    int productCategoryId;
    // 促销字段
    String promotionMessage;
    int reduceAmount;
    int realStock;
    int integration;
    int growth;
  }
  ```
- 方案B：直接扩展现有 `CartData`，添加 nullable 促销字段

4.3 **更新 CartModel 状态管理**
- 购物车加载后，调用 `queryPromotionList` API 获取促销信息
- 合并促销信息到购物车商品状态中
- 价格计算从 `item.price` 改为 `item.price - item.reduceAmount`

4.4 **更新购物车页面 UI**
- 每个商品项下方显示促销信息标签（如 "满减优惠：满200元减50元"）
- 底部结算栏显示促销后的实付金额
- 库存不足时显示提示

**验收**:
- 购物车商品列表显示促销标签和优惠后价格
- 底部结算金额 = Σ(price - reduceAmount) × quantity
- 无促销商品显示 "无优惠"

## Dev Notes

### 架构合规性
- **生成文件禁令**：不要运行 `goctl api go` 重新生成 `types.go`，直接手动编辑
- **业务逻辑位置**：所有试算逻辑在 `logic` 层，handler 层只做参数解析和转发
- **RPC 调用**：通过 `svcCtx` 中已注册的 service client 调用，不直接操作数据库

### 已知代码缺陷（必须在本 Story 中修复）

1. **`productCartMap` append bug**（`query_promotion_list_logic.go:108-114`）：else 分支 append 后未回写 map，多 SKU 同 SPU 场景会丢失购物车项
2. **满减总价未计算**（`query_promotion_list_logic.go:237-242`）：总价计算被注释，导致满减判断 `amount-item.FullPrice > 0` 永远为 `0-X < 0`，满减永远不生效
3. **限时购 SKU ID 错误**（`query_promotion_list_logic.go:274`）：传入 `item.ProductId`（SPU ID）而非 `item.ProductSkuId`（SKU ID），查询参数名为 `SkuId` 但实际传的是 productId
4. **float32 金额精度**（`generate_confirm_order_logic.go:119-127`）：`float32` 有效精度仅 7 位，金额 ≥ ¥100,000 时出现舍入误差
5. **确认单页面硬编码**（`order_submit.dart:105-111, 327, 344, 405`）：地址、活动优惠 `-200`、优惠券 `-0`、积分 `-0` 全部硬编码

### 从 Story 4-4 吸取的经验教训

1. **字段映射一致性**：前端 model 字段名必须与后端 JSON tag 完全一致，注意 `createTime` vs `createDate` 等细微差异
2. **编译验证先行**：每完成一个 Task 后执行 `go build` 和 `flutter analyze` 确认无编译错误
3. **scope 传递**：所有涉及商品查询的链路都必须经过 `ResolveEffectiveGovernanceScope`
4. **copier 库使用**：`copier.Copy` 不会自动处理类型不匹配字段，需要手动赋值

### 库 / 框架要求
- **后端**：go-zero（已有）、copier（已有）、sonic（已有）
- **前端**：dio（已有）、provider（已有）
- **无需新增依赖**

### 测试要求

1. **后端单元测试**：
   - 测试 6 种 promotionType 的 `ReduceAmount` 计算正确性
   - 测试满减总价为 0 时不触发除零错误

2. **API 集成测试**：
   - `POST /api/order/queryPromotionList` 返回完整促销信息
   - `POST /api/order/generateConfirmOrder` 返回正确的金额试算
   - 金额一致性：`queryPromotionList` 和 `generateConfirmOrder` 中同一商品的优惠金额一致

3. **前端手动验证**：
   - 购物车促销标签正确显示
   - 确认单金额与后端一致
   - 优惠券不可用时显示原因
