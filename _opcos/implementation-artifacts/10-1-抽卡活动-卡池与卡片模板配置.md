# Story 10.1: 大转盘活动、卡池与卡片模板配置

Status: in-progress

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a 平台、租户或商户运营人员,
I want 配置大转盘活动、卡池（每池固定 5 个格位）、卡片模板和合规规则,
so that 我可以在受控作用域内发布一场可审计、可运营的提货卡大转盘活动，消费者每次旋转必然中奖（中奖概率 100%）。

## Acceptance Criteria

1. **Given** 运营人员具备对应作用域的营销配置权限 **When** 创建或编辑大转盘活动 **Then** 系统保存活动基础信息、卡池（每池**固定 5 个格位**，格位序号 `slot_index` 1-5 唯一且连续）、卡片模板、稀有度、发售数量、参与条件和概率披露规则（**各格位概率之和必须精确等于 1**，每次旋转必然中奖，不存在"未中奖"格位） **And** 后台展示当前活动的可发布状态与生效时间。

2. **Given** 活动缺少版权信息、合规规则或审批记录不完整 **When** 运营尝试发布活动 **Then** 系统阻止发布并明确提示缺失项 **And** 保留活动文案、流转限制和审核记录供后续追溯。

## AC 覆盖矩阵

- **AC1（活动/卡池/模板配置 + 作用域保存 + 可发布状态）**：Task 1、2、3、4.1-4.4、5.1-5.3
- **AC2（合规校验 + 发布拦截 + 审计留痕）**：Task 1.2-1.6、2.4-2.6、3.3-3.6、4.3-4.5、5.4-5.6

## 背景与关键风险（必须优先阅读）

> **⚠️ CRITICAL - 这不是给现有秒杀表“多加几个字段”就能完成的能力：** 当前仓库的 `sms_seckill_activity`、`sms_seckill_session`、`sms_seckill_product` 只覆盖简单时段活动和商品挂接，无法承接卡池、模板、概率披露、版权归属、实名门槛与合规快照。10.1 必须新增独立的抽卡活动聚合模型，而不是把复杂字段继续塞进秒杀或优惠券表。
>
> **⚠️ CRITICAL - 作用域必须沿用仓库现有治理链，而不是前端裸传主体 ID：** Admin 侧已有 `api/admin/internal/common/query_scope.go`，SMS 侧已有 `rpc/sms/internal/logic/common/governance.go`、`write_scope.go` 和 `pkg/scope`。10.1 必须复用这套 scope 解析与写入校验能力，禁止页面自行决定平台/租户/商户归属。
>
> **⚠️ CRITICAL - 发布状态必须由服务端聚合计算：** Web Admin 只能展示 `可发布/缺少信息/待审批/已下线` 等结果，不能自己依据几个表单字段拼装“看起来可发布”。版权信息、合规规则、审批状态、上下线时间和卡池库存完整性必须以后端聚合校验结果为准。
>
> **⚠️ CRITICAL - 合规规则必须可追溯，不能靠覆盖更新：** FR71 明确要求保留活动文案、资格规则和流转限制的审核记录。10.1 不能只在主表上改最新值而丢失历史；至少要保留可查询的审计快照、审批摘要和变更时间线。
>
> **⚠️ CRITICAL - 生成链是硬约束：** `.api`、`.proto`、`gorm/gen` 产物都属于源定义派生结果。10.1 只能改 `script/sql/sms/*.sql`、`api/admin/doc/api/sms/*.api`、`rpc/sms/proto/*.proto` 与生成入口，然后执行 `make model` / `make gen`；禁止手改 `rpc/sms/gen/*`、`rpc/sms/sms.proto`、`smsclient/*` 或 `api/admin/internal/types/*`。
>
> **⚠️ CRITICAL - Web Admin 页面必须复用既有 SMS 工作台模式：** 当前 `web-admin/src/pages/sms/SeckillActivity/`、`Coupon/`、`OperateDashboard/` 已经沉淀了 `PageContainer + ProTable + Drawer/Modal + GovernanceScopeBar` 的实现模式。10.1 不要另起一套低密度大表单网站风格页面，而要沿用管理后台的工作台语义。
>
> **⚠️ CRITICAL - 10.1 只负责配置与发布前置，不提前实现前台抽卡、链上发放和资产页：** 消费者参与链路属于 10.2，卡片实例和唯一编号属于 10.3，蚂蚁链 token 发放属于 10.4，资产展示与审计检索属于 10.5。10.1 要为这些后续故事留足字段和状态，但不能把所有功能一起吞进来。
>
> **⚠️ CRITICAL - Flutter 手机端首页必须有明显抽卡入口，但不要新造一套首页流量系统：** 当前 `flutter-mall/lib/view/home/home_page.dart` 已经消费 `advertiseList`、`subjectList` 和首页 Banner/专题流量位。10.1 应为抽卡活动预留“首页显著入口配置”，并优先复用现有首页广告位或专题入口承载大转盘曝光，而不是再造独立的首页转盘 feed。

## 明确非目标（本 Story 不做）

- 不实现消费者大转盘参与、旋转动画、次数扣减、中奖结算或前台活动页（转盘动画与旋转逻辑属于 10.2）。
- 不实现卡片实例生成、唯一编号分配或链上 token 发放。
- 不在本 Story 中接入蚂蚁链 SDK、实名 SDK、内容安全 SDK；这里只预留配置字段、接入引用和发布校验所需的状态。
- 不重构整个 SMS 域已有优惠券、秒杀、广告、推荐位页面；仅在现有营销域中新增抽卡配置能力。
- 不顺手升级 `go-zero`、`goctl`、React、Umi、Ant Design Pro、Flutter 或 GORM 版本。

## 实施顺序（必须按序推进）

1. 先定义抽卡活动聚合模型、DDL、状态机和审计策略，明确哪些字段属于活动、卡池、模板、审核快照。
2. 再补 `.proto` / `.api` 源定义与生成链，保证 RPC、Admin API、类型和路由来源唯一。
3. 然后实现 SMS RPC 与 Admin API 的聚合校验、scope 校验、发布拦截和错误摘要。
4. 再建设 Web Admin 工作台，复用 `GovernanceScopeBar`、`Consequence Preview` 和现有 SMS 页面组织方式。
5. 最后补测试、菜单入口和最小验收命令，确保 story 真正进入可开发状态。

### 三、SMS RPC 与 Admin API 聚合实现

#### Task 3 (AC: 1, 2): 在服务端落地作用域校验、发布拦截和审计留痕

**目标：** 让“配置成功”和“可发布”成为两个不同但可追踪的状态。

- [x] 3.1 在 `rpc/sms/internal/logic/` 下新增聚合逻辑目录，例如 `drawactivityservice/`，并沿用现有 `seckillactivityservice/` 的文件组织方式实现增删改查、状态切换和详情查询。
- [x] 3.2 所有写操作必须复用 `rpc/sms/internal/logic/common/governance.go`、`write_scope.go` 与 `pkg/scope`，由服务端决定最终写入 scope；若请求 scope 超出当前主体范围，应拒绝并记录安全/审计事件。
- [x] 3.3 发布前校验至少覆盖：
  - 上下线时间是否合法
  - 每个卡池格位数是否为 5（`wheel_slot_count = 5`），且 `slot_index` 1-5 不重复、不缺失
  - 卡池各格位概率总和是否精确等于 1（允许 ±0.0001 浮点误差）；大转盘每次旋转必然中奖，**不允许概率总和小于 1**
  - 模板版权信息和内容审核状态是否完整
  - 流转限制是否满足“默认禁止集中竞价、连续挂牌、收益承诺”
  - 审批/审计快照是否齐全
  - **若活动配置 `real_name_required=1`，中奖后不可直接触发链上发放，必须先完成实名认证：`validateMintPrerequisites` 实时查询 `ums_member_identity.real_name_status`，未认证则返回含"实名"关键字的错误；参与逻辑识别后只记日志不回滚（资产实例已创建），待用户实名通过后由补偿扫描 `ScanAndDispatchPendingMintTasks` 自动补发链上任务**
- [x] 3.4 发布失败时要把失败项结构化返回给 Admin API，由网关层整理成可理解的错误摘要；不要在 handler 内写业务判断，也不要只返回底层 SQL/Proto 错误。
- [x] 3.5 所有创建、更新、发布、下线、删除动作都要写入审计记录，且高风险字段变更必须保留前后快照摘要，供 10.5 审计检索复用。
- [x] 3.6 Admin API 目录建议落位到 `api/admin/internal/logic/sms/draw_activity/` 与 `api/admin/internal/handler/sms/draw_activity/`，延续 `sms/seckill_activity` 的目录命名，不要引入与仓库现状不一致的驼峰目录结构。
- [x] 3.7 `svc.ServiceContext` 中新增的依赖必须统一放到 `internal/svc/service_context.go` 注入，禁止在不同 logic 中零散创建 DB helper、RPC client 或审计 writer。

## Dev Notes

### 架构约束（必须遵守）

1. **10.1 属于 `sms` 域配置聚合，不新建独立微服务：** 架构文档已经明确提货卡活动配置、资产台账和链上发放编排都归属 SMS 营销域。
2. **抽卡活动采用“链下主配置真相源”模式：** 10.1 的所有配置、规则、模板和审计信息都应先落 MySQL，不把链上平台或前台页面当真相源。
3. **作用域优先，前端不裁决授权：** scope、资源归属和是否允许修改必须服务端判断。
4. **服务端确认优先：** `可发布状态`、`发布失败摘要`、`审核状态` 由聚合接口统一输出，前端只展示。
5. **生成链不可绕过：** 修改 SQL / `.proto` / `.api` 后必须走既有生成命令。

1. **优先复用 SMS 既有模式，而不是从零定义抽卡模块骨架：**
  - DDL 风格参考 `script/sql/sms/sms_seckill_activity.sql`
  - RPC 逻辑组织参考 `rpc/sms/internal/logic/seckillactivityservice/`
  - Admin API 组织参考 `api/admin/internal/logic/sms/seckill_activity/`

### Architecture Compliance

- **SMS 域归属：** 抽卡活动、卡池、模板与配置层审计统一归 `sms`，不拆出新的 `digital-card` 微服务，也不把治理逻辑塞进 `sys`。
- **链下主真相源：** 配置、规则、模板、审计快照先落 MySQL；链上信息只作为后续 10.4 的回执写回结果，不反向定义 10.1 的配置真相。
- **统一治理链：** 查询 scope 走 `api/admin/internal/common/query_scope.go`，写入 scope 走 `rpc/sms/internal/logic/common/write_scope.go`，审计与安全事件复用 `pkg/audit`。
- **服务端聚合返回：** Web 端列表状态、详情摘要、发布失败项、审核状态都由聚合接口统一返回，前端不自行推断。
- **共享 UI 模式：** 抽卡配置工作台沿用 `GovernanceScopeBar + Consequence Preview + ProTable + Drawer/Modal` 模式，与现有营销管理页面保持一致。

- **首页聚合链保持不变：** Flutter 首页继续通过 `api/front` 的 `/api/home/index` 聚合接口获取 `advertiseList/subjectList` 等首页数据；10.1 如需承接抽卡入口，优先扩展首页聚合数据来源或复用既有广告/专题数据，不让 Flutter 端直接改为调用 SMS 配置接口。
