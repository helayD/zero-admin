# Story 8.4: 经营漏斗与优惠券核销看板

Status: in-progress

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a 平台、租户或商户运营人员,
I want 查看曝光、点击、加购、下单、支付和优惠券核销指标,
So that 我可以先判断当前活动和导购链路的即时转化表现。

## Acceptance Criteria

1. **Given** 平台已产生经营数据 **When** 运营按时间、活动、渠道、租户和商户筛选分析报表 **Then** 系统展示曝光、点击、加购、下单、支付和优惠券核销指标 **And** 指标口径在当前主体范围内保持一致。

2. **Given** 运营角色仅拥有部分主体的查看权限 **When** 查看分析报表 **Then** 系统仅返回被授权主体的数据 **And** 不允许跨租户或跨商户查看未授权漏斗数据。

## AC 覆盖矩阵

- **AC1（筛选 + 6 阶段指标 + 统一口径）**：Task 1-10、11.1-11.3、12.1-12.3
- **AC2（作用域隔离与越权防护）**：Task 1.2、3.1、4.3、4.6、6.1-6.4、7.2-7.4、8.1-8.4、11.1-11.3

## 背景与关键风险（必须优先阅读）

> **⚠️ CRITICAL - 渠道枚举不一致：** `oms_order_main.source_type` 当前使用 `1=APP,2=PC,3=小程序`，而 `oms_cart_item.source` 使用 `1=PC,2=H5,3=小程序,4=APP`。本 Story 必须先建立统一 `channel` 维度映射，禁止前后端直接展示原始枚举值。
>
> **⚠️ CRITICAL - 加购链路没有直接 scope 字段：** `oms_cart_item` 没有 `platform_id / tenant_id / merchant_id`。如果需要按主体统计加购，必须通过 `product_id -> pms_product_spu` 反查主体范围，不能只按 `member_id` 或客户端来源做近似推断。
>
> **⚠️ CRITICAL - 优惠券核销记录没有直接 scope 字段：** `sms_coupon_record` 也没有主体字段。核销指标必须至少通过 `order_id -> oms_order_main` 或 `coupon_id -> sms_coupon` 补齐 scope；不得直接把 `sms_coupon_record` 当成已带租户/商户维度的事实表。
>
> **⚠️ CRITICAL - 现有广告点击/下单计数字段不是统一漏斗：** `sms_home_advertise.click_count / order_count` 只能覆盖首页广告，不覆盖推荐商品、专题推荐、优惠券召回和秒杀等活动，也没有时间桶。不能直接把它当成全局经营漏斗真相源。
>
> **⚠️ CRITICAL - 活动归因字段目前不完整：** 现有 `add_cart_item`、`generate_order` 链路没有稳定透传 `activityType / activityId / intentSource / intentId`。若需要“按活动”筛选，必须在本 Story 中补齐活动归因字段或引入事件事实表，不能靠商品名称、URL 或 Referer 猜测。
>
> **⚠️ CRITICAL - 优惠券核销语义必须先核实：** 当前 `api/front/internal/logic/order/order/generate_order_logic.go` 调用 `CouponRecordService.UpdateCouponRecord` 时没有显式传 `status=1`。在把 `sms_coupon_record.status=1` 作为核销指标之前，必须先验证现有核销写路径是否可靠，不可靠则在本 Story 内一并修正。
>
> **⚠️ CRITICAL - 8.4 与 8.5 的边界：** 8.4 负责“统一漏斗口径 + 聚合查询 + 可视化看板”；8.5 才负责“复购分析 + 结果导出”。本 Story 可以为导出复用结构留接口，但不要把 8.5 的导出需求整体吞进来。

## 明确非目标（本 Story 不做）

- 不交付 8.5 的复购分析、Excel/CSV 导出能力和下载链接。
- 不抽象通用 BI 平台、任意维度钻取引擎或离线数仓编排系统；8.4 只补“当前经营漏斗看板”所需的最小真相层。
- 不伪造历史 `exposure/click/activity attribution` 数据；历史缺失时必须显式返回 `trackingStartedAt` / `partialMetrics`。
- 不升级 `echarts`、`go-zero`、`goctl` 版本，不替换现有图表库或生成链。
- 不绕开现有 `scope` 治理体系额外发明一套权限过滤逻辑。

## 实施顺序（必须按序推进）

1. 先锁定指标口径、时间边界、活动维度与查询/响应 Contract，再开始落数据事实。
2. 先验证并修正 `coupon_redeem`、活动归因、scope 补齐等写路径，再做聚合接口。
3. 先完成 OMS/SMS 聚合 RPC 与 Admin API，再接 Web Admin 页面和菜单资源。
4. 页面联调前必须确认 `.api` / `.proto` / SQL / model 生成链都已走完，避免前后端对着临时字段开发。
5. 最后做越权、回滚、部分数据提示和空态渲染验证，不能用“页面先跑起来”替代验收。

## Tasks / Subtasks

### 一、统一经营漏斗口径与共享契约

#### Task 1 (AC: 1, 2): 定义共享维度、指标枚举与转化公式

**目标：** 先把“看板上每一个数是什么意思”钉死，再开始写聚合代码，避免 OMS/SMS/Admin/Web 各自维护一套口径。

- [ ] 1.1 定义统一漏斗阶段枚举：`exposure`、`click`、`add_cart`、`order_created`、`pay_success`、`coupon_redeem`。
- [ ] 1.2 定义统一渠道枚举 `channel`，至少覆盖：`app`、`pc`、`h5`、`mini_program`、`unknown`，并明确：
  - `oms_order_main.source_type=1` 映射为 `app`
  - `oms_order_main.source_type=2` 映射为 `pc`
  - `oms_order_main.source_type=3` 映射为 `mini_program`
  - `oms_cart_item.source=1` 映射为 `pc`
  - `oms_cart_item.source=2` 映射为 `h5`
  - `oms_cart_item.source=3` 映射为 `mini_program`
  - `oms_cart_item.source=4` 映射为 `app`
- [ ] 1.3 定义统一活动维度：`activity_type` + `activity_id`。首批允许值至少包括：`home_advertise`、`coupon`、`seckill_activity`、`none`。如果后续需要纳入推荐商品/专题推荐，继续在该枚举体系内扩展，而不是另起字段。
- [ ] 1.4 定义统一时间桶：默认按天聚合；当查询范围不超过 48 小时时允许按小时聚合，支撑“即时转化表现”。所有时间解析和时间桶切分统一按 `Asia/Shanghai` 执行，并使用闭开区间 `[startTime, endTime)`，禁止前后端各自猜测边界。
- [ ] 1.5 把转化率公式沉淀到共享响应层，而不是前端页面临时计算：
  - `click_rate = click / exposure`
  - `add_cart_rate = add_cart / click`
  - `order_rate = order_created / add_cart`
  - `pay_rate = pay_success / order_created`
  - `coupon_redeem_rate = coupon_redeem / pay_success`
- [ ] 1.5.1 明确 `coupon_redeem_rate` 在 8.4 中的语义是“支付成功订单中的核销占比”，不是“领券到核销转化率”；页面文案和字段注释必须保持一致。
- [ ] 1.6 明确“无历史数据”和“历史数据缺失”不是同一个状态。响应结构要返回 `dataReadyFrom` 或 `trackingStartedAt`，避免前端把“0”误渲染成“真实零转化”。

### 二、为可观测漏斗补齐事实来源

#### Task 3 (AC: 1, 2): 建立统一经营漏斗事实表或最小事件汇总表

> **目标不是发明第二套 BI 平台，而是在现有仓库里补足“活动/渠道/主体”这三个维度的可查询事实。**
>
> **默认实施决策：** 8.4 先落 `sms_operate_funnel_event` 作为单一真相源；只有在单日查询窗口压测不达标时，才额外引入 `sms_operate_funnel_metric` 作为派生汇总层，禁止一开始双写两套事实来源。

**默认新增表：** `sms_operate_funnel_event`

**仅在性能不达标时追加的派生表：** `sms_operate_funnel_metric`

**最小字段建议：**

- `id`
- `event_type`
- `stat_time`
- `bucket_date`
- `bucket_hour`
- `platform_id`
- `tenant_id`
- `merchant_id`
- `channel`
- `activity_type`
- `activity_id`
- `member_id`
- `product_id`
- `order_id`
- `coupon_id`
- `trace_id`
- `extra_json`
- `create_time`

- [ ] 3.1 新表必须携带完整 scope，不允许后续查询阶段再靠模糊 join 补主体。
- [ ] 3.2 该表只承担经营漏斗事实/汇总，不承载订单、商品、优惠券的业务真相本身。
- [ ] 3.3 为高频查询建立索引，至少覆盖：
  - `(platform_id, tenant_id, merchant_id, stat_time)`
  - `(activity_type, activity_id, stat_time)`
  - `(channel, stat_time)`
  - `(event_type, stat_time)`
- [ ] 3.4 如果采用“事件表 + 聚合查询”方案，确保单日查询窗口内性能可接受；如果采用“实时汇总表”方案，需同步定义幂等更新键，防止重复累计。
- [ ] 3.5 新表 DDL 源文件放在 `script/sql/sms/`，命名遵循现有 `script/sql/<module>/<table>.sql` 规则；建表后通过 `make model` 生成 `rpc/sms/gen/model` / `rpc/sms/gen/query`，禁止手改生成产物。
- [ ] 3.6 事件去重键至少覆盖 `event_type + trace_id + member_id/product_id/order_id/coupon_id + stat_time` 中可用业务键，保证重试、回放和消息重复消费不会双写。

#### Task 4 (AC: 1, 2): 补齐曝光/点击/加购/下单/支付/核销埋点

**必须优先复用的现有入口：**

- `api/front/internal/logic/home/index_logic.go` — 首页广告/活动入口装载

- `api/front/internal/logic/order/order/generate_order_logic.go` — 下单动作
- 支付回调/支付成功链路（现有支付逻辑）
- `rpc/sms/internal/logic/couponrecordservice/update_coupon_record_logic.go` — 优惠券使用状态更新

- [ ] 4.1 曝光事件：在真实营销入口展示时记录，不允许在管理端配置保存时预写曝光。
- [ ] 4.2 点击事件：必须在真实点击营销入口时记录，并携带 `activity_type/activity_id/channel/scope`。
- [ ] 4.3 加购事件：在 `add_cart_item_logic.go` 内补齐活动归因字段；scope 需通过 `product_id -> pms_product_spu` 显式解析。
- [ ] 4.4 下单事件：在 `generate_order_logic.go` 创建订单成功后落盘 `order_created` 事实，并带上统一 `channel` 与活动归因。
- [ ] 4.5 支付事件：以支付成功为准记录 `pay_success`，不得把“发起支付”误算为“支付成功”。
- [ ] 4.6 核销事件：以 `coupon_record.status=1 && use_time != nil` 为准；若现有调用路径没有可靠写入 `status=1`，先修正，再统计。
- [ ] 4.7 取消/回滚场景必须能抵消已写入的错误事实，至少保证：

  - 优惠券回滚后不会继续统计为核销
  - 重复消息不会重复累加

## Dev Notes

### 架构约束（必须遵守）

1. **作用域优先：** 所有查询都必须先解析并约束到当前登录主体允许的范围，再执行聚合。
2. **MySQL 是真相源：** 订单、优惠券和加购事实以现有业务表或新建漏斗事实表为准，不能把前端缓存或页面状态当统计源。
3. **生成链优先：** 新增 Admin API / RPC 消息时优先修改 `.api` / `.proto` 并重新生成，不要手改生成文件。
4. **不跨层偷逻辑：** 页面不自己推导主体权限，不自己拼业务 SQL，不自己发明转化率公式。
5. **8.5 再做导出：** 8.4 只交付查询和看板；如需为 8.5 做准备，只能复用 `excelize` 模式，不在本 Story 直接做导出功能。

### 生成链注意事项（checklist 修复项）

1. 仓库 `goctl` 版本固定为 `v1.9.2`；生成前先确认本地版本一致，避免引入无关 diff。
2. OMS / SMS 的 proto 真正源文件是 `rpc/{service}/proto/*.proto`；修改后必须先运行 `go run ./rpc/{service}/proto/main.go` 合并，再执行 `goctl rpc protoc ...`。
3. Admin API 的源文件是 `api/admin/doc/api/**/*.api`；新增 `sms/operate_dashboard.api` 后通过 `goctl api go -api ./api/admin/doc/api/admin.api -dir ./api/admin/` 统一生成。
4. `api/admin/internal/types/types.go`、`api/admin/internal/handler/routes.go`、`rpc/*/*pb.go`、`rpc/*/client/*`、`rpc/*/internal/server/*`、`rpc/*/gen/query/*` 都视为生成结果，禁止手改。
5. 新增漏斗事实表后通过 `make model` 生成 GORM `model/query` 层，不手写 `gen/model` 或 `gen/query` 产物。

### 关键数据源与口径约束
