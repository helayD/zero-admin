# Story 6.5: 订单状态编排与多角色视图一致

Status: review

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a 平台运营人员,
I want 让支付、履约、退款、售后和关闭动作驱动统一订单状态流转,
So that 消费者、商户、客服和平台都看到同一笔订单的真实状态。

## Acceptance Criteria

1. **Given** 订单发生支付成功、支付失败、发货、退款、售后或关闭动作 **When** 下游状态更新完成 **Then** 系统按统一状态机更新订单主状态和相关子状态 **And** 平台、租户和商户视图展示一致的订单语义。

2. **Given** 某个状态更新失败或等待异步补偿 **When** 相关角色查看订单详情 **Then** 系统展示当前状态、失败提示或待处理提示 **And** 不让不同端长期停留在互相矛盾的状态。

**约束 1：OMS Proto 状态模型（已验证 `rpc/oms/proto/order_main.proto`）**

OMS 订单状态（`rpc/oms/proto/order_main.proto`）：
```
1 = 待支付    (PendingPayment)

OMS 支付状态（`rpc/oms/proto/order_payment.proto`）：

4 = 确认收货   (ConfirmReceive)
5 = 取消订单   (Cancel)
6 = 退款       (Refund)

OMS 操作人类型（`order_operation_log.proto`）：
```
1 = 用户    (User)
2 = 系统    (System)
3 = 管理员  (Admin)

**约束 5：状态机设计原则**

1. **单 OMS 服务内编排**：本 Story 专注 OMS `order_main` + `order_payment` + `order_operation_log` 的状态编排
2. **跨服务状态协同（Epic 7）**：库存/优惠券/积分的 Saga 补偿不属于本 Story 范围（由 Epic 7 Story 7-3a/7-3b/7-4 处理）
3. **补偿链路保留**：`cancel_user_order_logic.go` 中的 Saga 补偿逻辑（库存释放等）必须保留，不能因为引入状态机而删除
4. **幂等保护**：所有状态更新接口必须具备幂等性（使用 `order_id + action` 作为幂等键）
5. **OMS RPC 参数**：`CancelOrderReq` / `ConfirmOrderReq` 使用 `MemberId + OrderId`（⚠️ 不是 OrderNo）
