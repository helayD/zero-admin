# Story 1.5: 商户入驻审核与主体启停

Status: review

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a 平台管理员,
I want 审核商户入驻并控制商户启停状态,
so that 商户可以在合规和授权边界内进入经营状态。

## Acceptance Criteria

1. **Given** 商户入驻申请处于待审核状态
   **When** 平台管理员执行通过、驳回或补充材料动作
   **Then** 系统记录审核结果、原因和处理人
   **And** 商户与租户归属关系及经营状态被正确保存。
2. **Given** 已审核通过的商户被停用或重新启用
   **When** 平台管理员执行主体状态变更
   **Then** 商户后台访问与关键经营能力同步收回或恢复
   **And** 状态变更写入治理审计记录并在监控面板中可见。

## Dev Notes

### Scope Guardrails

- 本 story 只负责把“商户主体入驻审核 + 主体启停”做成正式治理能力，不负责一次性完成商户商品、订单、营销、内容或售后全域经营面；这些能力分别在 Epic 2 / 4 / 6 中继续落地。[Source: `_opcos/planning-artifacts/1-new-feature/epic.md#Story-15-商户入驻审核与主体启停`]
- 本 story 不应把 Story 1.4 的角色/菜单模板治理、Story 1.6 的业务对象作用域隔离、Story 1.7 的审计中心整包重做一遍；它应复用已有 scope 基线，只补足商户主体真相源与审核/启停闭环。[Source: `/Users/helay/Documents/GitHub/zero-admin/_opcos/implementation-artifacts/1-4-作用域角色-菜单模板与数据授权.md`]
- 所有新增能力继续落在 `sys` 域、`admin-api`、`rpc/sys` 与 `web-admin/system` 内，不创建 `merchant-center`、`merchant-admin-service` 或新的平行后台工程。[Source: `_opcos/planning-artifacts/1-new-feature/architecture.md#Project-Structure--Boundaries`]

### Story Foundation / Business Context

- PRD 的平台管理员旅程明确要求平台管理员能够在统一后台完成商户入驻审核、能力启停、作用域控制与快速回收，而不是依赖脚本、线下表格或研发改库。[Source: `_opcos/planning-artifacts/1-new-feature/prd.md#Journey-6-周岚负责租户开通与商户治理的平台管理员`]
- FR48 明确要求平台管理员可以发起商户入驻、审核、启停和清退流程，并维护商户与租户的归属关系、经营状态和可用能力；这正是 Story 1.5 的主 FR 覆盖范围。[Source: `_opcos/planning-artifacts/1-new-feature/prd.md#平台租户与多商户治理`]
- UX 的“平台开通与商户治理流”把这条链路定义为：创建租户 -> 初始化租户管理员 -> 发起商户入驻审核/绑定现有商户 -> 审核 -> 分配能力包、菜单与作用域 -> 商户首次登录。Story 1.5 需要把其中“发起商户入驻审核/绑定现有商户 + 审核 + 主体启停”做成明确的后台工作流。[Source: `_opcos/planning-artifacts/1-new-feature/ux-design.md#平台开通与商户治理流`]
- PRD 与 UX 都强调主体边界不能乱，商户启停和审核动作必须可审计、可恢复、可追踪，否则这不是普通交互问题，而是平台治理事故。[Source: `_opcos/planning-artifacts/1-new-feature/prd.md#Journey-6-周岚负责租户开通与商户治理的平台管理员`; `_opcos/planning-artifacts/1-new-feature/ux-design.md#Journey-Patterns`]

### Technical Requirements

- 商户主体必须以 MySQL 为真相源，并沿用 `sys_*` 表命名、`snake_case` 字段、`created_by/updated_by/created_at/updated_at` 审计字段与 SQL + 生成链协同演进方式。[Source: `_opcos/planning-artifacts/1-new-feature/architecture.md#Data-Architecture`; `_opcos/planning-artifacts/1-new-feature/architecture.md#Implementation-Patterns--Consistency-Rules`]
- 新商户实体必须显式携带 `platform_id`、`tenant_id`、`merchant_id` 语义中的最小必要集合；对 Story 1.5 而言，商户主体至少要落 `platform_id`、`tenant_id` 与商户唯一标识，避免后续商品/订单/营销域只能“借用 merchant_id 但无主体真相源”。
- 审核流与经营状态要拆开，不要用一个状态字段同时表达“待审核、驳回、已启用、已停用、已归档”。否则后续监控、审计、UI 筛选和权限收回都会变得含混。[Inference from: `_opcos/planning-artifacts/1-new-feature/epic.md#Story-15-商户入驻审核与主体启停`; `script/sql/sys/sys_tenant.sql`]
- 商户审核通过前必须校验租户状态；被挂接的租户如果已停用或已归档，不应允许继续审核通过或启用商户。现有 `ValidateTenantWritable` 可以作为起点，但 Story 1.5 很可能需要新增或扩展 merchant 级校验函数，而不是把 merchant 校验硬写进每个 handler/logic。[Source: `rpc/sys/internal/logic/common/governance.go`; `rpc/sys/internal/logic/tenantservice/helpers.go`]
- 对“商户后台访问与关键经营能力同步收回或恢复”的最低实现要求，不只是更新商户表状态，还要同步更新 merchant scope 绑定的激活态、默认作用域解析或权限缓存失效逻辑，确保已停用商户不能继续沿用旧 token / 旧 Redis 权限访问后台。[Source: `script/sql/sys/sys_user_scope.sql`; `rpc/sys/internal/logic/common/governance.go`; `rpc/sys/internal/logic/userservice/loginlogic.go`; `api/admin/internal/middleware/checkurlmiddleware.go`]
- Story 1.5 可以复用现有 `sys_menu_template` 的商户默认模板与角色 scope 基础能力，为“审核通过后下一步分配能力包/菜单与作用域”预留稳定挂点，但不应在本 story 内把整套 merchant 角色授权中心重新实现一遍。[Source: `script/sql/sys/sys_menu_template.sql`; `/Users/helay/Documents/GitHub/zero-admin/_opcos/implementation-artifacts/1-4-作用域角色-菜单模板与数据授权.md`]
- 审计 payload 要对后续 Story 7.5 可消费，至少能表达：商户主键/编码、租户归属、审核动作、前后状态、处理人、请求快照、事件快照和处理结果；建议沿用租户审计表与 `pkg/audit/*` 的模式，不另造完全不同的 JSON 结构。[Source: `script/sql/sys/sys_tenant_audit.sql`; `pkg/audit/tenant.go`; `pkg/audit/governance.go`]
