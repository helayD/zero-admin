# Story 4.6: 配置生效状态与作用域下发校验

Status: ready-for-dev

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a 运营人员,
I want 查看营销和内容配置在前台、购物车和结算链路中的生效状态,
So that 我可以确认配置是否真的影响到了目标用户。

## FRs Implemented

FR36: 平台可以将平台级、租户级和商户级营销配置与内容配置按作用域传递到对应商城前台展示、购物车试算和订单结算链路，并展示配置生效状态。

## Acceptance Criteria (AC)

### AC-1: 配置生效状态展示
**Given** 优惠券、秒杀活动或内容配置已发布
**When** 运营人员查看配置详情
**Then** 系统展示当前启用状态、目标作用域和适用链路摘要
**And** 运营可以据此确认配置理论上会影响哪些页面与结算节点

### AC-2: 发布校验失败原因展示
**Given** 配置条件不满足或发布校验未通过
**When** 运营查看状态页或尝试再次发布
**Then** 系统提供具体失败原因和修正入口
**And** 不会仅显示"保存成功"而缺少可验证的配置结果

### AC-3: 优惠券生效状态与链路摘要
**Given** 优惠券已发布（status=1）
**When** 运营人员在优惠券列表或详情页查看
**Then** 系统展示：启用状态、有效期、已领/已用数量、适用范围（全场/分类/商品）、适用链路（购物车试算/确认单试算）
**And** 过期或被取消的优惠券明确标识为"已失效"而非仍显示"进行中"

### AC-4: 秒杀活动生效状态与链路摘要
**Given** 秒杀活动已上线（status=0）
**When** 运营人员在秒杀活动列表或详情页查看
**Then** 系统展示：上线状态、活动时段、关联商品数、关联场次数、适用链路（前台限时购展示/购物车促销试算）
**And** 过期或下线的活动明确标识为"已下线/已过期"

### AC-5: 首页营销资源生效状态
**Given** 广告、推荐品牌、新品推荐、人气推荐或推荐专题已上线
**When** 运营人员在各管理列表查看
**Then** 每条记录展示当前上下线状态和适用作用域标签
**And** 过期资源自动标识为"已过期"

### AC-6: 专题与优选专区生效状态
**Given** 专题或优选专区已设置为"显示"（showStatus=1）
**When** 运营人员在列表中查看
**Then** 系统展示显示状态、推荐状态和作用域标签
**And** 缺少必填字段的专题在尝试发布时被拦截并给出缺失项列表

### AC-7: 作用域下发一致性
**Given** 配置按平台级、租户级或商户级作用域发布
**When** 前台或试算链路消费该配置
**Then** 只有目标作用域内的用户/商品可见该配置
**And** 后台配置详情页展示的作用域与实际下发一致

### Task 1: 后端——优惠券列表增加生效状态与链路摘要字段 (AC: #1, #3)

**文件**:
- `api/admin/internal/logic/sms/coupon/querycouponlistlogic.go`
- `api/admin/internal/logic/sms/coupon/querycoupondetaillogic.go`
- `api/admin/internal/types/types.go`（admin 端）

**Why**: 当前优惠券列表只返回原始 `status` 字段（0-草稿/1-进行中/2-已结束/3-已取消），运营需要看到：(a) 综合生效状态（含过期自动判定），(b) 适用范围摘要，(c) 影响的前台链路。

**详细变更**:

1.1 **在 admin `types.go` 中 `QueryCouponListData`（行 1434）增加计算字段**
```go
EffectiveStatus  string `json:"effectiveStatus"`  // "草稿"/"生效中"/"已过期"/"已取消"
ScopeSummary     string `json:"scopeSummary"`      // "全场通用" / "指定分类(3)" / "指定商品(5)"
AffectedPaths    string `json:"affectedPaths"`     // "购物车试算, 确认单试算"
```

1.2 **在 `QueryCouponListLogic`（`querycouponlistlogic.go`）返回数据时计算 `EffectiveStatus`**
- status==0 → "未开始"（草稿/未发布）
- status==1 且 endTime > now → "生效中"
- status==1 且 endTime <= now → "已过期"
- status==2 → "已结束"
- status==3 → "已取消"

> **注意**：status 实际语义为 0-未开始, 1-进行中, 2-已结束, 3-已取消（见 types.go:1447 注释）。

1.3 **在 `QueryCouponListLogic` 返回数据时构建 `ScopeSummary`**
- 当前已有 N+1 查询 scope 数量的逻辑（querycouponlistlogic.go:82-94），沿用此模式，在同一循环中额外查询 scopeType：
  - 无 scope → "未配置适用范围"
  - scopeType=0 → "全场通用"
  - scopeType=1 → "指定分类(N)" (N=count)
  - scopeType=2 → "指定商品(N)"
- **不做 N+1 优化**（与现有模式保持一致，后续统一优化）

1.4 **固定 `AffectedPaths`**
- 已发布优惠券的影响路径固定为 "购物车试算, 确认单试算"（因为 `QueryCouponListByCart` 在这两个入口被调用）

**验收**:
- 优惠券列表和详情返回 `effectiveStatus`、`scopeSummary`、`affectedPaths`
- `go build ./api/admin/...` 编译通过

- `api/admin/internal/logic/sms/home_recommend_product/homerecommendproductlistlogic.go`
- `api/admin/internal/logic/sms/home_recommend_subject/homerecommendsubjectlistlogic.go`
- `api/admin/internal/types/types.go`（admin 端）

**Why**: 这四类推荐资源已有 `recommendStatus`（0/1），但列表不展示综合生效状态。

> **❗重要数据模型差异**：
> - `HomeBrand` 使用独立 struct `QueryHomeBrandListData`（types.go:1949）
> - `HomeNewProduct` 和 `HomeRecommendProduct` **复用** `QueryProductSpuListData`（types.go:4015），该 struct 无 `recommendStatus` 字段
> - `HomeRecommendSubject` 使用 `ListHomeRecommendSubjectData`（types.go:871，注意前缀是 `List` 而非 `Query`）
>
> **因此不能在 `QueryProductSpuListData` 上加字段**（会影响所有商品列表场景）。新品推荐和人气推荐的生效状态只能在 logic 层计算后由前端根据 `recommendStatus` 字段自行映射。

**详细变更**:

4.1 **`QueryHomeBrandListData`（types.go:1949）增加字段**
```go
EffectiveStatus string `json:"effectiveStatus"` // "已推荐"/"未推荐"
```
计算逻辑：recommendStatus==1 → "已推荐"；recommendStatus==0 → "未推荐"

4.2 **`ListHomeRecommendSubjectData`（types.go:871）增加字段**
```go
EffectiveStatus string `json:"effectiveStatus"` // "已推荐"/"未推荐"
```
计算逻辑同上

4.3 **新品推荐和人气推荐：不修改 `QueryProductSpuListData`**
- 这两个列表复用了商品 SPU struct，且该 struct 已包含 `recommendStatus` 字段——但它是商品级别的，不是推荐位级别的
- **策略**：前端直接从列表的 `recommendStatus` 字段映射显示 Tag，后端不需要额外加字段

**验收**:
- HomeBrand 和 HomeRecommendSubject 列表返回 `effectiveStatus`
- HomeNewProduct 和 HomeRecommendProduct 列表由前端根据 `recommendStatus` 映射 Tag
- `go build ./api/admin/...` 编译通过

## Story Wrap Up / Agent Handoff Notes

**Estimated Complexity**: Medium（后端为增量计算字段 + 2 处后端校验补齐 + 前端 Tag 列扩展，无复杂数据结构变更）

**核心风险**:
1. **types.go 字段增加**：`admin-api` 的 `types.go` 有5668 行，增加字段时需确认精确行号和 struct 名称（见 Project Structure Notes 映射表）
2. **新品/人气推荐复用 ProductSpu struct**：不能在 `QueryProductSpuListData` 上加 `effectiveStatus`，否则会污染所有商品列表场景
3. **专题发布校验需先查询**：`UpdateSubjectStatusReq` 只携带 ids/showStatus/updateBy/scope，不携带 title/categoryId/pic，必须先查询完整记录再校验
4. **文件命名规则**：所有 Go 文件为 camelCase 无下划线（如 `querycouponlistlogic.go`），目录用 snake_case（如 `sms/home_brand/`），注意 `prefrence_area` 目录有拼写错误但必须沿用
5. **HomeAdvertise 未接入 GovernanceScopeBar**：本 Story 前端 Task 8 实施时可选补齐，或标记 TODO

**不在本 Story 范围内**:
- 配置变更后的实时通知/推送（属于 Epic 8 消息链路）
- 前台实际展示效果的 E2E 验证（属于前台各 Story 的验收）
- 前台 scope 过滤的完整补齐（front-api 的会员端 scope 机制需后续 Story 系统化）
- 配置变更的异步事件发布（属于 Epic 7 事件链路）

**建议实施顺序**: Task 1 → Task 2 → Task 3 → Task 4 → Task 5 → Task 9 → Task 10 → Task 6 → Task 7 → Task 8

后端先做（Task 1-5 增加字段，Task 9 补齐校验，Task 10 scope 审查），再做前端展示（Task 6-8）。
