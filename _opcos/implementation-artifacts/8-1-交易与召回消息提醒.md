# Story 8.1: 交易与召回消息提醒

Status: ready-for-dev

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a 消费者,
I want 接收订单、支付、售后、活动和会员召回消息,
So that 我可以在关键节点回到正确的订单、商品或活动上下文。

## Acceptance Criteria

1. **Given** 订单、支付、售后或活动触发了消息通知条件 **When** 系统生成消息提醒 **Then** 消费者可以在消息入口查看消息摘要和状态 **And** 点击后进入对应订单、商品或活动上下文。

2. **Given** 消息关联的业务对象已失效或状态已变化 **When** 消费者打开消息 **Then** 系统提示当前真实状态 **And** 提供下一步可执行动作而不是跳转到无效页面。

### 一、消息模型与数据库设计

> **⚠️ 前置依赖：** 当前 `rpc/sys` 的 `sys_notice` 表是后台管理用的系统公告，不是用户消息。本 Story 需要新建用户消息表，与系统公告解耦。

#### Task 1: 设计用户消息数据模型

**消息类型枚举（必须定义）：**

```go
// 消息类型
const (
    MessageTypeOrder    int32 = 1 // 订单消息
    MessageTypePayment   int32 = 2 // 支付消息

    MessageTypeActivity  int32 = 4 // 活动消息
```

**用户消息表结构（参考 `sys_notice` 风格，新增 ums 模块）：**

```sql
CREATE TABLE `ums_member_message` (
  `id` bigint NOT NULL AUTO_INCREMENT COMMENT '消息ID',
  `member_id` bigint NOT NULL COMMENT '会员ID',
  `message_type` int NOT NULL DEFAULT 1 COMMENT '消息类型（1:订单,2:支付,3:售后,4:活动,5:会员）',
  `title` varchar(255) NOT NULL COMMENT '消息标题',
  `content` text COMMENT '消息内容',
  `image_url` varchar(500) DEFAULT '' COMMENT '图片URL（可选）',
  `link_type` varchar(50) DEFAULT '' COMMENT '跳转类型(order/product/coupon/activity)',
  `link_id` varchar(100) DEFAULT '' COMMENT '跳转目标ID',
  `related_order_id` bigint DEFAULT 0 COMMENT '关联订单ID',
  `status` int NOT NULL DEFAULT 0 COMMENT '状态（0:未读,1:已读）',
  `read_time` datetime DEFAULT NULL COMMENT '阅读时间',
  `create_time` datetime NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
  `platform_id` bigint NOT NULL DEFAULT 1 COMMENT '平台ID',
  `tenant_id` bigint NOT NULL DEFAULT 1 COMMENT '租户ID',
  `merchant_id` bigint DEFAULT 0 COMMENT '商户ID（商户相关消息时使用）',
  PRIMARY KEY (`id`),
  KEY `idx_member_id` (`member_id`),
  KEY `idx_create_time` (`create_time`),
  KEY `idx_status` (`status`)
) ENGINE=InnoDB COMMENT='会员消息表';
```

### 三、消息生成触发点

> **⚠️ 前置依赖：** 消息生成应在关键业务事件触发时调用 UMS RPC。参考 Epic 7 的事件契约模式。

#### Task 3: 在关键业务事件中触发消息生成

**必须接入消息触发的业务事件：**

| 业务事件 | 消息类型 | 消息标题示例 | 跳转目标 |
|---------|---------|------------|---------|
| 订单创建成功 | 订单消息 | 订单已提交 | order/detail |
| 订单支付成功 | 支付消息 | 支付成功 | order/detail |
| 订单发货 | 订单消息 | 您的订单已发货 | order/detail |
| 订单确认收货 | 订单消息 | 确认收货成功 | order/detail |
| 售后申请提交 | 售后消息 | 售后申请已提交 | afterSales/detail |
| 售后处理完成 | 售后消息 | 售后处理完成 | afterSales/detail |
| 优惠券到账 | 会员消息 | 您有一张新优惠券 | coupon/list |
| 优惠券即将过期 | 会员消息 | 优惠券即将过期 | coupon/list |
| 活动开始/结束 | 活动消息 | 活动提醒 | activity/detail |

**实现约束：**

- 消息生成必须是**异步非阻塞**：消息生成失败不能影响主业务流程
- 使用与 Epic 7 一致的事件发布模式：`pkg/mq/rabbitmq_util.go`
- 消息内容必须包含足够的上下文信息，避免点击后还需要用户重新搜索
- 消息必须携带意图契约字段，用于 Flutter 端跳转路由解析

## Dev Notes

### 架构约束与边界

**约束 1：消息必须与系统公告解耦**

- `sys_notice` 是后台管理用的系统公告
- `ums_member_message` 是消费者消息中心
- 两者数据结构、用途、权限模型完全不同

**约束 2：消息生成必须是异步非阻塞**

- 消息生成失败不能影响主业务流程
- 使用 MQ 模式，与 Epic 7 的事件契约保持一致
- 补偿机制：消息生成失败时记录日志，但不回滚主业务

**约束 3：意图契约必须完整**

- 所有消息必须携带 `intentType`、`targetType`、`targetId`
- Flutter 端必须能根据意图契约正确跳转
- 跳转目标失效时必须提供降级策略

**约束 4：作用域隔离是强制约束**

- 所有消息查询必须校验 `memberId` 与当前登录用户一致
- 跨用户的消息访问必须被拒绝
- 消息表必须携带 `platformId`、`tenantId`

**约束 5：Flutter 实现必须遵循现有模式**

- 使用 `HttpUtil` + `service_url.dart`
- 使用 `if (mounted) { setState(...) }` 模式
- 错误处理使用 `ScaffoldMessenger` + `SnackBar`
