# Story 10.5: 数字卡片资产展示、审计检索与合规处置

Status: review

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a 消费者、客服或运营人员,
I want 查看数字卡片资产状态并对异常资产执行审计与合规处置,
so that 用户能确认资产到账进度，平台也能治理展示、回收和下线风险。

## Acceptance Criteria

1. **Given** 消费者已获得数字卡片资产 **When** 打开我的数字卡片页面 **Then** 系统展示卡面、唯一编号、所属活动、获取时间、链上 token 状态和发放进度 **And** 对处理中资产显示处理中而不是直接判定失败。

2. **Given** 客服或运营按活动、用户、卡片模板、唯一编号和链上状态检索资产 **When** 查看抽卡记录、发卡记录和审计日志 **Then** 系统返回被授权范围内的记录、合规限制和处置动作 **And** 默认禁止集中竞价、连续挂牌和收益承诺相关能力。

## AC 覆盖矩阵

- **AC1（消费者资产列表/详情 + 进度时间线 + 合规提示）**：Task 1.1-1.7、2.1-2.7、3.1-3.7、4.1-4.8
- **AC2（后台审计检索 + 合规处置 + 作用域约束）**：Task 1.2-1.7、2.3-2.8、5.1-5.9、6.1-6.8

## 背景与关键风险（必须优先阅读）

> **⚠️ CRITICAL - 10.5 只能消费 10.3/10.4 已建立的链下真相源，绝不能根据抽卡记录重新推断“这张资产现在是什么状态”。** 当前仓库已经把资产真相源固定在 `sms_card_instance`，把链上发放过程真相源固定在 `sms_card_mint_task`，并把时间线落在 `sms_card_asset_log`。10.5 只能做“聚合查询 + 合规处置 + 用户可见展示”，不能另起一张“资产展示表”或在 Flutter / web-admin 里自行拼状态。
>
> **⚠️ CRITICAL - 10.5 同时面对“消费者可见语义”和“客服/运营审计语义”两类受众，字段可见边界必须分层。** 消费者只需要确认“资产归属、到账进度、受限原因、下一步”；客服/运营则需要看到抽卡记录、发放任务、最近回执摘要、审计动作和合规限制。任何把 `traceId`、`requestId`、原始回执 JSON、内部失败栈等信息直接透给会员端的做法，都会造成越界暴露。
>
> **⚠️ CRITICAL - `asset_status`、`mint_status`、`chain_status` 仍然不够表达 10.5，需要补充“展示/合规处置”语义，但绝不能把五类状态揉成一个字段。** 10.5 至少要清楚区分：
> 1. 资产生命周期：`asset_status`
> 2. 发放阶段：`mint_status`
> 3. 链上结果：`chain_status`
> 4. 前台展示状态：`display_status`
> 5. 合规处置状态：`compliance_status`
> 若把这些含义混在一起，前台会误把“下线展示”当“资产失效”，后台会误把“人工复核中”当“链上失败”。
>
> **⚠️ CRITICAL - 被限制展示、冻结、下线或回收处置的资产不能在会员端“静默消失”。** FR69/FR71 和 UX 都要求用户能确认“这张资产是不是我的、为什么现在不能正常展示”。因此 10.5 更接近“受限可解释展示”，而不是“直接从列表删掉”。只要资产仍然归属于当前会员，就要返回结构化状态和原因摘要，而不是 404 或空列表。
>
> **⚠️ CRITICAL - 10.5 要复用 10.4 的链路监控与动作语义，而不是平行造第二套发卡运维工作台。** 当前仓库已经有：
> - `web-admin/src/pages/sms/DigitalCardChainMonitor/`
> - `api/admin/internal/logic/sms/digital_card_chain/`
> - `retry/freeze/escalate` 动作语义
> 10.5 需要在资产工作台中“关联和复用”这些发放链路动作，而不是重新造一套 `mintRetryAgain`、`pauseAssetChain` 一类的专用词典。
>
> **⚠️ CRITICAL - 合规处置动作必须以资产为中心落库并写审计日志，不能做成前端按钮层面的假动作。** “限制展示 / 下线展示 / 回收处置 / 标记复核”都必须更新 `sms_card_instance` 的当前可见状态或合规状态，并追加 `sms_card_asset_log`。任何只改前端文案、只改缓存、或只靠运营备注表示“这张卡现在受限”的做法，都不满足 FR71。
>
> **⚠️ CRITICAL - Flutter 端不能根据本地倒计时、轮询失败次数或旧缓存自行推导“已到账 / 失败 / 已下线”。** 10.5 必须继续遵守“服务端确认优先”原则：会员端只消费后端聚合后的 `mintStatus` / `chainStatus` / `displayStatus` / `complianceStatus` 及其文案，不允许客户端自定义推理规则。
>
> **⚠️ CRITICAL - 10.5 是 Epic 10 第一条真正把“我的数字卡片资产页”和“后台审计处置页”接出来的 Story，必须沿用现有代码落点。** 当前仓库真实可复用的位置已经很明确：
> - 前台落地页和抽卡结果：`api/front/internal/logic/digital_card/draw_activity/`、`flutter-mall/lib/view/digital_card/`
> - 后台活动配置：`web-admin/src/pages/sms/DigitalCardActivity/`
> - 后台链路监控：`web-admin/src/pages/sms/DigitalCardChainMonitor/`
> 10.5 应在这些基础上增量补“资产页 / 审计工作台 / 合规 banner / 时间线”，不要再起一套孤立入口。
>
> **⚠️ CRITICAL - 本 Story 的“回收”是合规处置语义，不是上链销毁或交易流通。** 当前 PRD 明确默认禁止集中竞价、连续挂牌和收益承诺。10.5 里的“回收处置”只允许表达为平台受控处置状态、展示限制和审计记录，不允许顺手引入钱包、市场、交易撮合或链上 burn 流程。

## 明确非目标（本 Story 不做）

- 不重做抽卡活动配置、实名认证校验、中奖结算和本地资产建账；这些分别属于 10.1、10.2、10.3。
- 不重做 10.4 的发放任务状态机、MQ/Job 兜底和链上执行器；10.5 只能消费其结果并提供关联入口。
- 不建设二级市场、转赠、连续挂牌、收益承诺、积分换购或任何“资产金融化”能力。
- 不在 Flutter 页面、前台 handler 或 web-admin 页面里直连蚂蚁链接口，也不新增钱包或链上浏览器跳转。
- 不把后台活动配置页、发卡链路监控页和资产审计页硬塞成一个巨型页面；应保持“活动配置”“链路监控”“资产审计”三类入口边界清晰，但允许相互跳转。
- 不默认触碰 `.api` / `.proto` / `types.go` / `smsclient` 生成链并批量生成；如实现阶段必须走生成流程，需先得到用户明确许可。

## 实施顺序（必须按序推进）

1. 先补 `sms_card_instance` 的展示/合规快照字段与 `sms_card_asset_log` 动作语义，确保 10.5 的状态基线可落库可追踪。
2. 再补 `sms` 域里的资产聚合查询与合规处置服务，形成“会员可见视图”和“后台审计视图”两套明确输出。
3. 然后补 `front-api` 的会员资产列表/详情接口，并把字段边界收紧到会员真正需要的信息。
4. 再补 Flutter 的“我的数字卡片资产页 / 详情页 / 时间线 / 合规说明”，确保用户能确认到账进度与受限原因。
5. 然后补 admin / web-admin 的资产审计工作台，复用 `DigitalCardChainMonitor` 的治理模式并补充合规处置动作。
6. 最后补专项测试、状态词典校验和最小观测字段，确保 10.5 不会把“处理中 / 补偿中 / 受限展示”渲染错。

## 完成判定（Definition of Done）

- 会员端可以稳定查看自己的数字卡片资产列表和详情，展示卡面、唯一编号、所属活动、获取时间、发放进度和链上状态。
- 对 `mint_processing`、`mint_compensating`、`mint_manual_review`、`mint_frozen` 等场景，会员端均显示明确的“处理中/补偿中/人工复核中/已冻结”语义，而不是误报为失败或成功。
- 后台可以按活动、会员、模板、资产编号、token 状态和合规状态检索资产，并查看抽卡记录、发放任务摘要与审计日志。
- 合规处置动作至少覆盖“标记复核 / 下线展示 / 回收处置”中的最小闭环，并把操作人、原因、traceId、前后状态写入 `sms_card_asset_log`。
- 当资产涉及发放异常时，后台资产工作台可以关联跳转或复用 10.4 的链路动作，不会再发明第二套发卡干预动作。
- 被限制展示、下线或回收处置的资产在会员端不会静默消失；系统会返回受限状态和原因摘要。
- 默认不向会员端暴露 `traceId`、`requestId`、原始回执、内部失败栈等后台审计字段。
- 10.5 的实现不会引入交易/转赠/收益相关 CTA，也不会破坏 PRD 的去金融化约束。
