# Story 7.1: 商品索引同步事件链

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a 技术运营人员,
I want 在商品新增、修改和删除后自动同步搜索索引,
So that 消费者可以基于最新商品状态执行搜索和筛选。

## Acceptance Criteria

1. **Given** 商品完成新增、修改或删除 **When** 业务状态成功写入主数据源 **Then** 系统发布对应同步事件并驱动搜索索引更新 **And** 索引同步链路包含事件标识、主体范围和追踪信息。

2. **Given** 索引同步失败或延迟超出阈值 **When** 技术运营查看链路状态 **Then** 系统显示 lag、失败原因和最近执行时间 **And** 为后续重试或人工介入保留上下文。

3. **Given** 商品新增 **When** PMS `AddProductSpu` 成功写入 MySQL **Then** 系统发布 `pms.product.published.v1` 事件到 RabbitMQ **And** Consumer 消费并同步商品数据到 ES `products` 索引。

4. **Given** 商品修改（包括上下架、审核、推荐、删除等状态变更） **When** PMS `UpdateProductSpu` 成功写入 MySQL **Then** 系统发布 `pms.product.updated.v1` 事件到 RabbitMQ **And** Consumer 消费并更新 ES `products` 索引。

5. **Given** 商品删除 **When** PMS `DeleteProductSpu` 成功写入 MySQL **Then** 系统发布 `pms.product.deleted.v1` 事件到 RabbitMQ **And** Consumer 消费并从 ES `products` 索引中删除对应文档。

6. **Given** 消费者在前台执行搜索 **When** 搜索请求到达 `front-api` **Then** ES 索引中的商品数据与 MySQL 主数据状态一致（延迟 ≤ 5 分钟） **And** 搜索结果只返回当前作用域内可见且可售的商品。

7. **Given** 技术运营进入链路监控视图 **When** 按租户、商户、链路类型和时间筛选 **Then** 系统展示同步链路状态、失败原因、重试次数和最近执行时间。

8. **Given** ES 同步链路失败 **When** 失败次数超出阈值或链路进入死信状态 **Then** 系统生成明显状态提示并保留人工补偿入口。

### 一、核心：PMS 商品写操作 → MQ 事件发布

> **⚠️ 核心设计原则**：
> - PMS 的 `AddProductSpu`、`UpdateProductSpu`、`DeleteProductSpu` 是商品主数据的唯一写入入口，事件必须在此处发布

> - 使用现有 `pkg/mq/rabbitmq_util.go` 的 `SendMessage` 方法，交换机为 `product.event.exchange`
> - 使用 `pkg/audit` 中的 `NewTraceID` 生成 traceId
> - 事件发布必须在 MySQL 写操作**成功之后**，使用 defer 确保即使后续逻辑出错也能记录事件

### 五、错误处理与幂等保护

#### Task 10: 幂等保护机制

```
PMS → MQ 幂等：
- MQ 消息本身具有唯一性（eventId + occurredAt），但这不是主要幂等手段
- ES 文档使用 product_id 作为唯一键，upsert 语义天然幂等

Consumer 消费幂等：
- ES 同步：upsert（PUT /products/{product_id}）—— 重复执行结果一致
- ES 删除：DELETE /products/{product_id} —— 删除不存在文档不报错
- 不依赖消息去重，而是依赖 ES 操作本身的幂等性
```

> **⚠️ 【Critical Issue】Consumer 当前使用 `auto-ack=true`，失败时消息不会 requeue！**
> `pkg/mq/rabbitmq_util.go:143` 中 `channel.Consume` 的第三个参数为 `true`（auto-ack）
> 这意味着 Consumer 处理失败时，消息已被自动确认，**无法重新入队**
> 这是当前实现的已知限制，建议在 Story 7.4/7.5 中改进

- [x] 10.1 ES 操作使用 upsert/delete 幂等操作 — **已验证**

## Dev Notes

### 架构约束与边界（继承自 Epic 7 + Architecture）

**约束 1：ES 是搜索读模型，不是真相源**

- ES 只从 MySQL（PMS）单向同步，不得反向写入 MySQL
- 搜索结果延迟上限：5 分钟（NFR22）
- 同步链路必须具备 lag 指标、失败重试与人工补偿入口（完整补偿视图在 Story 7.5 中实现）

**约束 2：交换机类型与路由键（⚠️ Critical Issue）**

> **⚠️ 【自动修复 2 - Critical Issue】`pkg/mq/rabbitmq_util.go:267` 中 `ExchangeDeclare` 类型为 `"direct"`，不是 Architecture 要求的 `"topic"`

**当前实现**：
- 交换机 `product.event.exchange` 在 `SendMessage` 中声明为 `direct` 类型
- 路由键：`syn.product.key`（新增/更新）和 `delete.product.key`（删除）
- Consumer 使用 `ConsumeSimple`，队列通过 `SendMessage` 中的 `QueueBind` 自动绑定

**方案 A（推荐）：保持 `direct` 类型**
- 路由键：`syn.product.key` / `delete.product.key`
- Consumer 队列：`syn.product.to.es.queue` / `delete.product.from.es.queue`
- ✅ 无需代码修改，当前已能正常工作
- ❌ 不符合 Architecture 事件命名规范 `{domain}.{entity}.{action}.v{n}`

**方案 B（符合 Architecture）：改为 `topic` 类型**

- **位置**：`pkg/mq/rabbitmq_util.go:143` 的 `ConsumeSimple` 方法

#### Enhancement: Consumer traceId 链路追踪丢失

- **问题**：Consumer 使用 `context.Background()`，无法在链路追踪系统中关联 traceId
- **影响**：无法在 OpenTelemetry 等链路追踪系统中关联 PMS → Consumer → ES 全链路

### Architecture Compliance

- **ES 读模型原则**：ES 只承担搜索读模型，不承担交易与配置真相（PMS MySQL 是真相源）
- **事件异步解耦**：商品写操作成功后异步发布事件，不阻塞主业务
- **Scope 透传**：所有事件 payload 包含 `platformId/tenantId/merchantId`，Consumer 和 ES 文档均保留 scope 信息
- **幂等保护**：ES upsert 和 delete 操作天然幂等，MQ 消息失败不影响 MySQL 主业务
- **TraceId 可追踪**：所有日志包含 traceId，可关联 PMS 写操作 → MQ 发送 → Consumer 消费 → ES 同步全链路
- **NFR22 合规**：商品变更到搜索可见的延迟 ≤ 5 分钟
