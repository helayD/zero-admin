# Story 9.4: 场景化权限请求与拒绝后的替代路径

Status: in-progress

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a 消费者,
I want 只在真实业务触发点收到权限请求，并在拒绝后仍能继续主任务,
so that 我不会被无关授权打断购物、售后或评价流程。

## Acceptance Criteria

1. **Given** 用户执行消息提醒订阅、售后凭证上传或评价图片上传 **When** 当前操作首次需要通知、相册或相机权限 **Then** 系统通过 `Permission Request Sheet` 说明权限用途并请求授权 **And** 不在首次启动阶段预取与当前任务无关的权限。

2. **Given** 用户拒绝或永久拒绝权限 **When** 当前任务继续执行 **Then** 系统提供再次授权入口和不阻断当前任务的替代路径 **And** 保留当前表单或订单上下文。

## AC 覆盖矩阵

- **AC1（真实触发点请求权限 + Permission Request Sheet + 不预取无关权限）**：Task 1.1-1.7、2.1-2.6、3.1-3.3、4.1-4.6
- **AC2（拒绝/永久拒绝后的再次授权入口 + 替代路径 + 上下文保留）**：Task 1.5-1.7、2.2-2.6、3.1-3.8、4.3-4.8、5.1-5.6

## 背景与关键风险（必须优先阅读）

> **⚠️ CRITICAL - 当前 Flutter 端权限请求仍是页面级零散实现，完全不满足 Story 9.4 的统一体验要求：** `flutter-mall/lib/view/mine/ping_jia/ping_jia.dart` 与 `flutter-mall/lib/view/mine/order/apply_after_sales.dart` 直接调用 `ImagePicker.pickImage()`，异常处理仅通过 `e.toString().contains('permission')` 粗暴匹配，再弹出“请在设置中授权图片权限”。当前没有统一 `Permission Broker`、没有结构化状态、没有再次授权入口，也没有拒绝后的任务替代路径。
>
> **⚠️ CRITICAL - “消息推送”设置项目前是静态假实现：** `flutter-mall/lib/view/mine/setting/settings.dart` 中的开关固定为 `value: true`，`onChanged` 为空，没有真实权限状态来源、没有用户提醒偏好真相源，也没有消息中心替代路径。9.4 不能把这个假开关继续包装成“已经支持消息通知订阅”。
>
> **⚠️ CRITICAL - 9.1 / 9.3 已建立恢复底座，9.4 不允许再造第二套恢复体系：** `AppRecentContext`、`AppRecoveryStore`、`IntentRecoveryShell`、`AppIntentDispatcher`、`AppRecoveryRouter`、`AppLifecycleProvider` 已经承接最近有效上下文、pending intent、登录恢复与召回 fallback。9.4 只能在现有共享层上扩展“权限流程上下文 / 草稿恢复 / 设置返回后二次检查”，不能新增平行 store、平行 router 或页面私有恢复协议。
>
> **⚠️ CRITICAL - 当前仓库还没处理 image picker 的 lost-data / 进程回收恢复：** `flutter-mall/lib/main.dart` 现阶段只初始化 `SharedPreferences` 后直接 `runApp`，并未接入 `ImagePicker.retrieveLostData()` 或统一的媒体恢复适配层。Android 低内存或相机/相册切后台被系统回收时，评价与售后表单上下文存在真实丢失风险。
>
> **⚠️ CRITICAL - 平台权限配置明显缺口会让“正确请求权限”本身无法落地：** `flutter-mall/ios/Runner/Info.plist` 当前缺少 `NSPhotoLibraryUsageDescription`、`NSCameraUsageDescription`、`NSPhotoLibraryAddUsageDescription`；`flutter-mall/android/app/src/main/AndroidManifest.xml` 当前没有 `POST_NOTIFICATIONS`。9.4 若不补齐这些基础配置，就无法完成符合平台规范的通知 / 相册 / 相机授权流。
>
> **⚠️ CRITICAL - `pubspec.yaml` 只有 `image_picker`，没有统一权限插件，也没有任何推送 SDK：** 当前依赖里有 `image_picker: ^1.0.7`，但没有 `permission_handler`，也没有 FCM / APNs / 厂商推送 SDK。9.4 可以引入共享权限抽象或新增权限插件，但不能借此伪装“真实推送系统已经打通”。
>
> **⚠️ CRITICAL - 前台接口侧目前只有站内消息，没有真实通知订阅接口：** `flutter-mall/lib/config/service_url.dart` 仅存在 `message/list`、`read`、`unreadCount` 等站内消息接口，未发现通知授权同步或设备订阅接口。9.4 必须明确边界：完成“权限请求 + 状态真相 + 替代路径 + 恢复链路”，但不虚构后端推送订阅系统。
>
> **⚠️ CRITICAL - 评价图与售后凭证都是可选字段，拒绝权限后本来就应允许继续主任务：** `PinJia` 与 `ApplyAfterSales` 都支持仅文本/描述提交，这意味着 9.4 的核心不是“必须让用户授权成功”，而是“即便拒绝也不断路、保留当前表单、给出再次授权入口和明确替代路径”。
>
> **⚠️ CRITICAL - 9.2 的统一状态壳层和 9.3 的结构化 failure reason 不能被破坏：** 权限拒绝、设置返回、媒体恢复失败都应继续复用统一状态语义与恢复语义，不允许页面自己乱弹 toast 再静默失败。

## 明确非目标（本 Story 不做）

- 不在本 Story 中接入 FCM、APNs、厂商推送 SDK、远程通知投递平台或完整的服务端设备订阅体系。
- 不在首次启动、首页加载、消息列表打开、登录完成等“非真实触发点”提前申请通知、相册或相机权限。
- 不新增第二套路由、第二套恢复 store、第二套状态壳层或第二套权限弹窗体系；继续复用 Epic 9 已建立的共享层。
- 不把评价图片 / 售后凭证上传从现有 base64 流程升级为 OSS / CDN / 多媒体服务迁移；本 Story 聚焦权限治理与恢复，不做介质链路重构。
- 不伪造“消息推送已开启并能稳定送达”的效果；若当前只有本地授权状态和站内消息替代路径，界面必须诚实表达。
- 不在本 Story 中顺手改造消息中心视觉、设置页整站 UI 或发明独立的通知管理模块。

## 实施顺序（必须按序推进）

1. 先定义统一权限场景模型、结构化状态和 `Permission Request Sheet`，把“什么时候请求、请求后如何返回结果”说清楚。
2. 再把设置页消息提醒、售后凭证上传、评价图片上传三个真实触发点全部接到共享权限编排层。
3. 再补草稿保留、设置返回后二次校验、image picker lost-data 恢复和 telemetry，不让权限流只做到“能弹框”。
4. 最后补平台配置、测试和回归保护，确保 9.1 / 9.2 / 9.3 的恢复与状态基线不被破坏。

## 场景-权限-替代路径矩阵

| 场景 | 真实触发入口 | 平台 / 插件判定 | 拒绝或不可用后的替代路径 | 必须保留的上下文 |
| --- | --- | --- | --- | --- |
| 消息提醒订阅 | `settings.dart` 中开启“消息推送” | iOS、Android 13+ 按通知运行时权限处理；Android `<13` 不得伪造系统授权弹窗，只读取系统通知开关状态与本地提醒偏好 | 保持开关关闭，提供“去设置”入口，并引导继续通过站内消息中心与未读角标获取提醒 | 设置页当前位置、开关意图、来源 scene |
| 评价图片-相册 | `PinJia` 里点击“相册” | Android 13+ 优先系统 Photo Picker；iOS 14+ PHPicker / limited access 属可用态；只有真实需要时才走权限请求 | 若相册不可用，保留“拍照”入口；若用户放弃补图，继续无图评价 | 星级、评价文本、已选图片、商品上下文 |
| 评价图片-拍照 | `PinJia` 里点击“拍照” | 只在拍照 source 请求相机权限，不得因为展示图片底部弹层就一并申请相机和相册权限 | 若相机拒绝，仍保留“相册”入口；若都不用，继续无图评价 | 星级、评价文本、已选图片、商品上下文 |
| 售后凭证-相册 | `ApplyAfterSales` 里点击“相册” | 与评价图片相同，优先最小权限 / 系统 picker 能力 | 若相册不可用，保留“拍照”入口；若用户不补图，继续无图提交 | `orderId`、售后类型、原因、描述、已选图片 |
| 售后凭证-拍照 | `ApplyAfterSales` 里点击“拍照” | 只在拍照 source 请求相机权限 | 若相机拒绝，仍保留“相册”入口；若都不用，继续无图提交 | `orderId`、售后类型、原因、描述、已选图片 |

## Tasks / Subtasks

### 一、统一权限编排模型与共享交互组件

#### Task 1 (AC: 1, 2): 为通知、相册、相机构建统一的 `Permission Broker` 与 `Permission Request Sheet`

**目标：** 先把权限请求从页面私有逻辑抽离到共享层，避免 `settings.dart`、`ping_jia.dart`、`apply_after_sales.dart` 各自判断、各自弹窗、各自丢上下文。

- [x] 1.1 在 `flutter-mall/lib/model/` 中新增结构化权限流程模型，例如 `permission_flow_context.dart`，至少描述：`scene`（消息提醒 / 评价图片 / 售后凭证）、`permissionType`（notification / photos / camera）、`status`、`source`、`returnTarget`、`orderId` / `productId`、`fallbackAction`、`intentId` / `recoveryId`。
- [x] 1.2 在 `flutter-mall/lib/utils/` 中新增共享权限编排层，例如 `permission_broker.dart`；统一承接权限状态查询、首次请求、永久拒绝判断、`openAppSettings()` 跳转和结构化结果映射，禁止页面继续依赖 `e.toString().contains('permission')` 之类的脆弱判断。
- [x] 1.3 新增 `Permission Request Sheet` 组件，例如 `flutter-mall/lib/widgets/permission_prompt_sheet.dart`，必须覆盖 `首次请求`、`已拒绝`、`永久拒绝`、`已授权` 四种状态，并提供：用途说明、主动作、再次授权入口、替代路径说明。
- [x] 1.4 权限请求只能发生在三个真实触发点：
  - 设置页开启“消息提醒”
  - 售后页点击“添加凭证 / 拍照 / 从相册选择”
  - 评价页点击“添加图片 / 拍照 / 从相册选择”
- [x] 1.5 明确禁止在 `main.dart`、欢迎页、首页、消息列表、订单列表或其他非真实触发点预请求通知、相册或相机权限。
- [x] 1.6 权限结果必须统一映射为结构化枚举值，例如：`granted`、`limited`、`denied`、`permanently_denied`、`not_required`、`settings_return_pending`、`picker_lost_data`，供 UI、恢复链路、埋点和测试共用；其中 `limited` 对 iOS 14+ 相册受限授权必须视为“可继续主任务”的可用态，而不是误判为失败。
- [x] 1.7 共享权限层必须按 `source` 区分通知、相册、相机，不允许把“上传图片”粗暴合并成单一照片权限；相机权限只在 `camera` source 请求，`gallery` source 需优先遵循系统 picker / 最小权限策略。
- [x] 1.8 若引入 `permission_handler`，必须把插件调用收口在共享层，并同步落实 `flutter-mall/ios/Podfile` 宏配置、`Info.plist` 用途说明、Android 声明与文档说明；不能在页面里直接散落插件调用。
- [x] 1.9 对“不需要运行时权限”的平台分支必须显式建模：例如 Android `<13` 通知状态检查、Android 13+ Photo Picker、iOS 14+ PHPicker / limited photo access；不得为了满足统一 UI 而伪造一套不存在的系统授权弹窗。

### 二、治理“消息提醒”设置入口，保证状态真实且不打断主任务

#### Task 2 (AC: 1, 2): 把 `settings.dart` 中的静态开关改造成真实、可恢复、可替代的权限入口

**目标：** 9.4 首先要把“消息推送”从假开关改成真实的权限治理入口；即便目前没有完整远程推送后端，也必须保证状态表达不骗人。

- [x] 2.1 重构 `flutter-mall/lib/view/mine/setting/settings.dart` 中的“消息推送”项：开关状态必须来自“系统通知授权状态 + 本地提醒偏好真相源”的组合，而不是固定 `true`。
- [x] 2.2 用户首次尝试开启时，先展示 `Permission Request Sheet` 解释用途，再触发通知权限请求；若用户取消或拒绝，开关保持关闭态，并给出清晰原因说明。
- [x] 2.3 用户拒绝或永久拒绝通知权限时，必须提供：
  - 再次授权 / 打开系统设置入口
  - 不阻断当前购物任务的替代路径
  - 继续依赖站内消息中心与未读角标的说明
- [x] 2.4 从系统设置返回 App 后，必须在共享恢复链路中重新检查通知授权状态，并回到设置页原位置；禁止把用户丢回首页或静默吞掉结果。
- [x] 2.5 当前仓库尚未发现真实设备订阅 / 推送通道接口；因此本 Story 的消息提醒开关只允许表达“系统通知是否授权 + App 是否愿意展示提醒偏好”，不允许宣称远程推送已真正开启。
- [x] 2.6 若为保持状态真相需要新增本地持久化或轻量接口同步，也必须走共享层（`AppRecoveryStore` / `SharedPreferences` / `HttpUtil` / `service_url.dart`），不能把状态硬编码在 widget 本地。
- [x] 2.7 设置页至少要区分并可测试以下状态：`enabled`（系统允许 + 本地偏好开启）、`muted_locally`（系统允许但本地偏好关闭）、`blocked_by_system`（系统权限关闭 / 永久拒绝）；文案和开关呈现必须与真实状态一致。

### 三、为评价与售后上传链路补齐替代路径、草稿保留与媒体恢复

#### Task 3 (AC: 1, 2): 重构 `PinJia` 与 `ApplyAfterSales`，让权限拒绝不再中断任务

**目标：** 把“上传图片”从阻塞点改造成可选增强能力。即使没有授权，用户仍应能保留当前表单、继续提交文字内容，并在之后返回补图。

- [x] 3.1 重构 `flutter-mall/lib/view/mine/ping_jia/ping_jia.dart` 的图片入口：从直接 `ImagePicker.pickImage()` 改为先经过共享权限编排层，再执行图片选择。
- [x] 3.2 重构 `flutter-mall/lib/view/mine/order/apply_after_sales.dart` 的凭证图片入口：同样先走共享权限编排层，再决定进入相册 / 相机。
- [x] 3.3 评价页在权限被拒绝或永久拒绝后，必须保留：星级、评价文本、已选图片列表和商品上下文，并明确支持“继续无图评价”。
- [x] 3.4 售后页在权限被拒绝或永久拒绝后，必须保留：`orderId`、售后类型、退货原因、问题描述、已选凭证图和当前页面状态，并明确支持“继续无图提交售后申请”。
- [x] 3.5 权限流、相册选择器或相机拍摄结束后，必须回到原表单与原订单 / 商品上下文；禁止因为设置跳转、前后台切换或权限拒绝把用户送回首页。
- [x] 3.6 `AppRecoveryStore` 只能扩展，不可复制：若需要存“待恢复权限上下文 / 表单草稿 / pending picker scene”，必须复用现有 `recentContext` / `pendingIntent` 存储体系或其相邻共享层，不得另起炉灶。
- [x] 3.7 必须补齐 image picker lost-data 恢复策略：基于官方 `retrieveLostData()` 能力，在 `main.dart`、`IntentRecoveryShell`、`AppLifecycleProvider` 或共享媒体适配层中恢复已选媒体或给出结构化解释，确保 Android 低内存回收后任务不丢。
- [x] 3.8 继续复用 Story 6.4 / 8.2 的 base64 上传口径；9.4 的重点是权限与恢复体验，不是改写后端上传协议。
- [x] 3.9 必须覆盖“单一 source 被拒绝，另一 source 仍可用”的分支：例如相机拒绝后保留相册入口、相册不可用后保留拍照入口；只有当两条路径都不可用或用户主动放弃时，才回退到纯文本主任务。

### 四、把权限流接入 `Intent Recovery Loop`，补平台配置与遥测

#### Task 4 (AC: 1, 2): 让权限授权、设置返回、媒体恢复都服从同一条恢复链路

**目标：** 权限请求不是一个“独立死胡同”。无论用户去系统设置、被系统回收，还是授权后继续动作，都必须回到 Epic 9 已定义的恢复闭环。

- [x] 4.1 在 `AppRecentContext`、`AppRecoveryStore` 或相邻共享模型中增加权限相关的 `failureReason` / `recoveryHint` / `blocked` / `scene` 语义，但必须维持“只有成功态才写 recent context”的 9.1 基线。
- [x] 4.2 在 `IntentRecoveryShell` / `AppIntentDispatcher` / `AppRecoveryRouter` 中接入权限恢复分支：当用户从系统设置返回、授权状态变化或图片选择器返回时，继续回到原动作。
- [x] 4.3 在 `AppLifecycleProvider` 或共享 telemetry helper 中增加最小指标：`permissionPromptShown`、`permissionGranted`、`permissionDenied`、`permissionSettingsRedirected`、`permissionFallbackUsed`、`permissionLostDataRecovered`，并带上 `scene`、`source`、`intentId/recoveryId`。
- [x] 4.4 继续通过 `HttpUtil` 透传统一客户端上下文，不允许页面级请求私自拼接链路元数据；如果本 Story 需要同步权限相关状态，统一走共享网络层。
- [x] 4.5 更新 `flutter-mall/ios/Runner/Info.plist`，并在引入 `permission_handler` 时同步更新 `flutter-mall/ios/Podfile`：至少补齐 `NSPhotoLibraryUsageDescription`、`NSCameraUsageDescription`，并按实际写入路径判断是否需要 `NSPhotoLibraryAddUsageDescription`，同时确保 iOS 权限宏与实际使用的权限分组一致。
- [x] 4.6 更新 `flutter-mall/android/app/src/main/AndroidManifest.xml`：为 Android 13+ 通知权限补 `POST_NOTIFICATIONS`；同时避免为 Photo Picker 场景机械添加过时的外部存储权限。
- [x] 4.7 平台策略必须与真实插件行为一致：Android 13+ 相册选择优先遵循系统 Photo Picker / 最小权限原则；相机权限和 iOS 用途说明按平台要求配置，不能伪造“会弹权限框却没有声明”的流程。
- [x] 4.8 权限相关错误、fallback 与说明文案必须可读屏、可聚焦、可重复进入，继续遵守 9.2 统一状态与 9.3 结构化恢复语义。

## Dev Notes

### 架构约束（必须遵守）

1. **权限请求必须是场景化触发，不允许预取：** 只有消息提醒订阅、评价图片上传、售后凭证上传可以触发权限请求。
2. **权限流必须接入 `Intent Recovery Loop`：** 去系统设置、授权完成、前后台切换、image picker 返回都要回到原任务，而不是把用户扔回首页。
3. **继续复用 Epic 9 的共享恢复层：** `AppRecoveryStore`、`IntentRecoveryShell`、`AppIntentDispatcher`、`AppRecoveryRouter`、`AppLifecycleProvider` 是第一真相源，不能再造第二套。
4. **拒绝权限后不阻断主任务：** 评价与售后图片都是可选增强，不是阻塞字段；消息提醒被拒绝后仍可继续购物，并通过站内消息中心承接替代路径。
5. **设置页状态必须诚实：** 没有真实系统授权或没有本地提醒偏好时，开关不能假装处于开启状态；没有完整推送后端时也不能暗示“远程通知已生效”。
6. **平台差异必须按官方能力落地：** Android 13+ 通知权限需显式声明；Photo Picker 场景优先遵守最小权限原则；iOS 权限请求必须先具备用途说明键。
7. **image picker low-memory 恢复是正式需求：** 不能把 `retrieveLostData()` 视为“nice to have”；丢失媒体后至少要保住表单和恢复动作。
8. **页面成功后才允许写 recent context：** 权限拒绝、设置返回、picker 中断等失败/中间态都不能污染最近有效上下文。
9. **共享网络层继续承担上下文透传：** 若需要同步权限状态或记录链路，不允许在页面里拼 header 或散落 API 调用元数据。
10. **继续复用 9.2 的统一状态语义：** 权限拒绝、恢复失败、设置返回结果要用统一状态壳层/结果说明表达，不只靠 toast。
11. **不要顺手扩 scope 到推送基础设施建设：** 9.4 解决的是“请求权限的时机与失败后的体验”，不是完整通知平台建设。
12. **如果触达生成式工件，只改源定义：** 若后续确实需要补前台同步接口，仍需遵守 `.api/.proto` 源定义与生成链约束，不手改生成物。
13. **按 source 而不是按页面统一申请权限：** 点击“相册”不应顺手申请相机权限；点击“拍照”不应顺手申请相册权限。
14. **`limited` 与 `not_required` 都是正式状态，不是边角料：** iOS 受限照片访问和系统 picker 免权限场景必须被当成一等公民设计与测试。

### 平台判定细则（自动修复补充）

1. **Android `<13` 通知：** 不得伪造系统运行时授权弹窗；共享权限层只负责读取系统通知是否开启，并结合本地提醒偏好决定 UI 状态。  
2. **Android 13+ 通知：** 通过 `POST_NOTIFICATIONS` 处理运行时权限，请求前仍由 `Permission Request Sheet` 解释用途。  
3. **Android 13+ 相册：** 优先走系统 Photo Picker；若该路径不需要运行时照片权限，则应映射为 `not_required` 或等价可用态，而不是多申请旧式存储权限。  
4. **iOS 14+ 相册：** `limited` 照片访问仍是可继续主任务的成功态；不要把它误判为“已拒绝”。  
5. **相机：** 只在拍照 source 请求相机权限；若被拒绝，仍应保留相册 source 作为替代路径。
