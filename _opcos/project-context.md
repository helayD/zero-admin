## 关键实现规则

### 语言与沟通规则

- 与用户沟通、实施说明、交付总结，以及新增或更新代理使用的项目文档时，默认使用中文；只有在用户明确要求其他语言时才切换。
- Go API/RPC/应用层调用链保持 `handler -> logic -> svc`；handler 只负责解析、分发和响应，不承载业务编排。
- 业务错误统一通过 `pkg/errorx` 或管理端的 `api/admin/internal/common/errorx` 路由，失败日志需结合上下文使用 `logc.Errorf` 或 `logx` 记录。
- 新增请求字段时，应在 `.api` 标签中定义默认值，例如 `default=1`、`default=20`，然后重新生成；不要手改生成后的 `types.go` 默认值。
- RPC 到 API 的字段映射应在 logic 内显式完成；不要在网关 handler 中直接返回 RPC 结构体。
- `web-admin` 的 TypeScript 实际上按严格模式运行（`strict`、`noImplicitReturns`、`noUnusedLocals`）；优先使用带类型的 `request<T>()`，删除无用变量或导入，而不是压制报错。
- Flutter 启动流程默认要求 `SharedPreferencesUtil.init()` 在 UI 或网络相关代码运行前完成；在 `main()` 中必须保持这个顺序。

### 框架与生成链规则

- 标注了 `Code generated by goctl`、`gorm.io/gen`、`protoc` 等内容的文件都属于生成产物；应修改 `.api`、`.proto` 或生成入口后重新生成，而不是直接改 client/model/pb 文件。
- 新增共享依赖和 service client 时，应统一放进 `internal/svc/service_context.go` 并通过 `svcCtx` 传递；不要在不同 logic 中临时重复实例化。
- Admin 网关与 Front 网关并不对称：`admin-api` 安装了自定义 `httpx.SetErrorHandler` 和 `ctx.AddLog`，而 `front-api` 大多沿用默认 `httpx.ErrorCtx`；修改哪个网关，就遵循哪个网关的约束。
- `web-admin` 的网络层统一走 Umi `request`；服务调用应放在 `src/pages/**/service.ts` 或 `src/services/**` 中，并复用现有的 `Authorization` 拦截逻辑。
- `web-admin` 本地开发默认使用相对路径 `/api/`，由 `config/proxy.ts` 转发到 `http://127.0.0.1:8888/`；不要在页面组件或 service 模块里写死后端地址。
- 管理端页面通常遵循 `index.tsx + service.ts + data.d.ts + components/*`，并配合 `PageContainer` 与 `ProTable`；应在该模式上扩展，而不是新造一套页面组织方式。
- `flutter-mall` 将完整接口常量维护在 `lib/config/service_url.dart`，Dio `baseUrl` 为空，并在 `HttpUtil` 中统一处理 `401`；新增接口应复用这些共享层，不要在 Widget 里直接写原始 `Dio` 调用。

### 测试规则

- 每次改动都运行当前表面最小且相关的检查：Go 至少执行 build 或定向校验，`web-admin` 使用 `npm run lint`、`npm run tsc`、`npm run test` 或 `npm run test:e2e`，Flutter 使用 `flutter analyze` 与 `flutter test`。
- `web-admin` 已经具备 Jest 配置（`tests/setupTests.js`）和 Playwright 配置；应复用现有测试基座，不要再平行引入另一套 runner。
- 对菜单、分类等树形或列表页面，既要验证 service 输出，也要验证页面转换后的 UI，因为这些页面常通过 `tree(data, 0, 'parentId')` 重组数据。
- 后端 logic 常在返回前对 RPC 结果做映射和过滤；调整这些流程时，需要同时验证正常路径和空数据/异常回退行为。

### 代码质量与风格规则

- 保留各目录既有约定，不要顺手重排整个模块：Go 文件以 package 为中心并使用 snake_case，React 页面常用 `index.tsx`，Flutter 文件使用 snake_case 且常与 model/widget/provider 同目录组织。
- 对已经使用中文产品文案和作者/日期注释块的文件，应保持现状；不要做全仓库式的“英文清洗”。
- 除非明确是在重新生成，否则不要触碰 `web-admin/src/.umi`、`web-admin/dist`、`flutter-mall/build`、`rpc/**/client`、`rpc/**/gen`、`*_pb.go` 以及 swagger/static 生成目录等构建或生成产物。
- 在 `web-admin` 中，层级数据转换统一复用 `tree(data, 0, 'parentId')`；不要在页面里内联重写造树逻辑。
- Flutter 远程图片优先使用 `CachedImageWidget`，以保持原生端与 Web 端在缓存和代理策略上的一致性。

### 开发工作流规则

- 仓库级后端构建和启停流程统一围绕 `make build`、`make start`、`make stop`；单服务重启由 `service_manager.sh` 负责。
- 代码生成是这里的常规开发步骤：修改 `.api` 或 `.proto` 后执行 `make gen`，修改 GORM 生成源后执行 `make model`。
- 本地开发 `web-admin` 使用 `npm run start:dev`；接口改动必须继续兼容当前代理和登录/token 流程。
- 运行时配置会复制到 `target/<service>/<service>.yaml`；新增或改名服务时，要同步更新复制和构建脚本。
- 如果运行环境是遵守 `.windsurfrules` 的 Windsurf 会话，在结束任务前需要走完 Ask Continue 检查点；这是 IDE 工作流规则，不是应用运行时逻辑。

### 高优先级禁区规则

- 不要把业务逻辑写进 API handler；应保留在 `logic` 和下游 service 层。
- 不要把服务器密码、SSH 凭据或其他密钥写进 `project-context.md` 或其他面向代理的说明文档。
- 不要在每个 `web-admin` 页面里手工复制 token 流程来绕过请求拦截器；应围绕 `app.tsx` 和共享 helper 集中处理。
- Flutter Web 加载外部或 OSS 图片时，不要绕过 `proxyImageUrl()`；直接使用 `Image.network` 可能在 CanvasKit/CORS 下失败。
- 不要假设 admin、front、job、consumer 服务共享同一套错误包装或中间件链。
- 不要手工修改已经声明 `DO NOT EDIT` 的文件；应回到源定义后重新生成。

## 使用说明

**给 AI 代理：**

- 修改后端、`web-admin` 或 Flutter 代码前，先阅读本文件。
- 优先遵循现有生成链和共享 helper，不要用临时捷径替代正式流程。
- 当两个子系统约定不一致时，以你当前正在修改的那个子系统的本地规范为准。
- 当仓库引入新的生成器、框架或容易被忽略的工作流约束时，应同步更新本文件。

**给维护者：**

- 保持本文档简洁，重点记录那些成本高、又容易被代理重复犯错的约束。
- 从本文档中移除密钥、服务器清单和一次性环境说明。
- 当 `go.mod`、`web-admin/package.json` 或 `flutter-mall/pubspec.lock` 发生明显变化时，及时刷新版本信息。
- 定期复查本文档，确保它足够短，代理能在实现前快速读完。
